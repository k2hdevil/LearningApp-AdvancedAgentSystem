## 학습 목표 및 선수 지식

**이 모듈을 마치면 다음을 수행할 수 있습니다.**
- 에이전트의 자율성 범위(대리권)를 판정하고, 범위에 비례하는 보안 제어를 심층 방어 프레임워크로 설계한다.
- Amazon Cognito·AgentCore Identity·IAM·OAuth로 사용자→에이전트, 에이전트→리소스의 엔드투엔드 자격 증명 흐름을 구성한다.
- AgentCore Policy 엔진과 Cedar 정책(허가·금지·조건부)으로 정책 기반 액세스 제어를 구현한다.

- 포괄적인 감사 추적과 규정 준수 모니터링을 설정하고, 각 결정을 Well-Architected Agentic AI Lens 보안 기둥에 근거해 검증한다.

**선수 지식**: 모듈 1(다중 에이전트·AgentCore Runtime/Gateway/Identity), AWS IAM·OAuth 2.0/OIDC 기초, VPC·서브넷·보안 그룹 등 네트워킹 기초, 생성형 AI 보안 개념(프롬프트 인젝션 등).

## 모듈 개요 — 이 모듈이 푸는 4가지 문제

에이전틱 AI 보안은 "기존 보안에 무엇을 더할 것인가"의 문제입니다. 에이전트는 자율적으로 추론하고 도구를 호출하며 상태를 기억하기 때문에, 기존 워크로드의 보안 제어(자격 증명·인프라·데이터·애플리케이션·위협 탐지)를 **그대로 상속**하면서 동시에 **자율성이 만들어내는 새로운 공격 표면**을 다뤄야 합니다. 이 모듈은 결국 네 가지 질문에 답하는 과정입니다.

| 파트 | 핵심 질문 | 산출물 |
| --- | --- | --- |
| 1. 위협 지형 | 에이전트는 *무엇을* 새로 위협하고, 어떤 틀로 방어하는가? | 자율성 범위 판정 + 심층 방어 7계층 프레임워크 |
| 2. 자격 증명·정책 | *누가* 무엇을 하도록 허용하는가? | 엔드투엔드 자격 증명 흐름 + Cedar 정책 |
| 3. 네트워크 격리 | 인프라·데이터를 *어디에* 가두는가? | VPC·PrivateLink·엔드포인트 격리 |
| 4. 감사·규정 준수 | 규정 준수를 *어떻게* 입증하고 위협을 탐지하는가? | 감사 추적 + 규정 준수 모니터링 |

> **Well-Architected 설계 원칙(전제)**: Agentic AI Lens의 네 번째 설계 원칙은 *"자율성에 비례하는 인간 감독(Human oversight proportional to autonomy)"* 입니다. 읽기 전용 연구 에이전트와 프로덕션 DB를 수정하는 자율 에이전트는 **같은 제어를 쓸 수 없습니다.** 이 모듈 전체가 "얼마나 자율적인가"를 먼저 판정하고, 그 범위에 비례해 자격 증명·네트워크·감사 제어의 정교함을 끌어올리는 과정입니다. 보안 기둥은 9개 질문(AGENTSEC01~09)·30개 모범 사례로 구성됩니다.

## 파트 1. 에이전틱 AI 보안 지형 — 위협 모델과 심층 방어

### 1.1 해결할 문제

에이전틱 AI 애플리케이션은 생성형 AI의 **모든** 보안·안전 위험을 그대로 물려받습니다(아키텍처의 중심에 여전히 LLM이 있기 때문입니다). 문제는 여기서 끝나지 않습니다. 에이전트가 수행하는 **자동화된 작업** — 메모리 액세스, 도구 호출, 자율 추론, 데이터·시스템의 읽기를 넘어선 *변경·쓰기* — 이 새로운 공격 표면을 만듭니다.

- **상속된 위험**: 프롬프트 인젝션, 유해 출력, 데이터 유출 등 생성형 AI 위험이 그대로 유효합니다.
- **자율성이 만드는 위험**: 에이전트가 도구를 잘못 호출하거나, 권한을 의도 이상으로 확대하거나, 오염된 메모리로 잘못된 결정을 내릴 수 있습니다.
- **배포 표면의 확장**: 생성형 AI는 주로 "쿼리-응답"이었지만, 에이전트는 사용자가 GitHub에서 받은 MCP 서버·도구를 **로컬에 배포**하고 stdio로 자격 증명 컨텍스트를 전달합니다. 이는 기업이 배포한 에이전트뿐 아니라 사용자 디바이스까지 보안 범위를 넓힙니다.
- **빠른 진화**: 위협·기법이 매주 바뀝니다. 보안 조직은 새로운 위협·트렌드를 지속적으로 추적해야 합니다.

핵심은 하나입니다 — 기존 보안 제어(자격 증명·인프라·데이터·애플리케이션·위협 탐지)는 **여전히 필요하되**, 에이전트의 자율성에 맞춰 *어떻게* 적용할지를 새로 설계해야 합니다.

> **💡 팁 — 출발점 잡기**: "에이전트 보안은 완전히 새로운 분야인가?"라는 질문으로 시작하세요. 답은 "아니요, 기존 보안이 전부 필요하고 + 자율성 위험이 추가됩니다"입니다. AWS Generative AI Security Scoping Matrix, OWASP·MITRE·NIST 자료를 이미 아는 학습자라면, 그 위에 "자동화가 만드는 위험"만 얹으면 된다는 점을 강조하면 부담이 줄어듭니다.

### 1.2 고려해야 할 기술·프레임워크

에이전트 보안을 체계화하는 세 가지 렌즈를 함께 사용합니다.

#### (1) Agentic AI Security Scoping Matrix — 자율성 4범위

에이전트마다 다른 보안·규정 준수 접근이 필요한 이유를 설명하는 프레임워크입니다. **대리권(agency)이 커질수록 위험도 커집니다.**

```ascii
[자율성 4범위]  아래로 갈수록 대리권 + 위험 증가 -->

범위 1 / 대리권 없음 (사람 시작, 변경 없음)
  │
  v
범위 2 / 규정된 대리권 (사람 승인 필요 / HITL)
  │
  v
범위 3 / 감독되는 대리권 (사람 트리거, 자동 실행)
  │
  v
범위 4 / 전체 대리권 (자체 개시, 완전 자율)
```

| 범위 | 대리권 | 일정 예약 예시 | 규정 준수 함의 |
| --- | --- | --- | --- |
| **범위 1** | 대리권 없음 | 에이전트가 빈 시간을 찾고, *사용자가* 예약 | 읽기 전용 · 최소 제어 |
| **범위 2** | 규정된 대리권 | 에이전트가 제안하고, *사람 검토 후* 예약 | 단계별 HITL 승인 필수 |
| **범위 3** | 감독되는 대리권 | 사람이 트리거, 에이전트가 *제약 내 자동* 예약 | 경계·정책 + 사후 감사 |
| **범위 4** | 전체 대리권 | *환경이 트리거*, 에이전트가 자율 예약 | 최고 수준 제어·지속 모니터링 |

모든 범위에서 6가지 핵심 보안 차원을 다뤄야 하며, 범위 1→4로 갈수록 각 차원의 정교함이 상향됩니다 — ① 자격 증명 컨텍스트(AuthN+AuthZ), ② 데이터·메모리·상태 보호, ③ 감사·로깅, ④ 에이전트·FM 제어, ⑤ 대리권 경계·정책, ⑥ 오케스트레이션.

**범위별로 "어디에 보안을 집중할 것인가"** — 6가지 차원은 모든 범위에서 필요하지만, 자율성이 올라갈수록 무게 중심이 이동합니다. 관통하는 첫 번째 원칙은 **최소 권한(scope narrowing)이 1차 제어**라는 것입니다. 에이전트는 자율적으로 행동하므로, 잘못 구성된 권한의 *폭발 반경(blast radius)* 이 사람 사용자보다 훨씬 큽니다. 따라서 "에이전트가 무엇을 읽고·쓰고·실행할 수 있는가"를 필요한 최소로 좁히는 것이 다른 모든 제어에 앞섭니다.

| 보안 차원 | 범위 1·2 집중 (낮은 자율성) | 범위 3·4 집중 (높은 자율성) |
| --- | --- | --- |
| ① 자격 증명 컨텍스트 | 기본 AuthN/AuthZ · 사람 자격 증명 확인 | 에이전트 전용 ID + 권한 교집합 + 지속 검증 |
| ② 데이터·메모리·상태 | **읽기 전용 강제** · 메모리 만료 정책 | **세션 격리** + 무결성 검증 + 포이즈닝 방어 |
| ③ 감사·로깅 | API 수준 작업 로깅 | **+ 의사결정·추론 근거까지 로깅**(완전 감사 가능성) |
| ④ 에이전트·FM 제어 | 기본 가드레일 | 행동 이상 탐지 + 강화된 가드레일 |
| ⑤ 대리권 경계·정책 | **HITL 승인 게이트** | **결정적 정책 시행(Cedar)** + 동적 경계 |
| ⑥ 오케스트레이션 | 단일·단순 흐름 | 에이전트 간 신뢰 경계 + 메시지 서명 |

- **낮은 자율성(범위 1·2)에서 집중할 곳**: 시스템을 바꿀 수 없도록 **읽기 전용을 기술적으로 강제**하고, 변경이 필요하면 **HITL 승인 게이트**로 사람의 명시적 승인을 받습니다. 기본 자격 증명과 API 수준 로깅으로 충분합니다.
- **높은 자율성(범위 3·4)에서 집중할 곳**: 사람이 매 단계 개입하지 않으므로, **결정적 정책 시행(파트 2)** · **세션 격리와 메모리 무결성(파트 3·4)** · **의사결정 근거까지 남기는 감사(파트 4)** · **에이전트 간 신뢰 경계(모듈 1·파트 3)** 가 핵심으로 부상합니다. 여기에 지속 모니터링과 행동 이상 탐지를 더합니다.
- **배포 전략(가장 중요)**: 조직은 **낮은 자율성 시스템부터 배포·검증**한 뒤 점진적으로 높은 범위로 확장하고, 각 범위에 맞는 지속 모니터링을 적용합니다. 자율성을 한 단계 올릴 때마다 위 6개 차원의 제어를 함께 끌어올리는지 재점검합니다.

> 출처: [AWS · The Agentic AI Security Scoping Matrix](https://aws.amazon.com/ko/blogs/security/the-agentic-ai-security-scoping-matrix-a-framework-for-securing-autonomous-ai-systems/)(6가지 보안 차원·범위별 제어). 원문 내용을 라이선스 준수를 위해 재구성했습니다.

> **💡 팁**: 수강생 조직의 실제 에이전트를 각 범위에 매핑하는 연습이 강력합니다. "이 에이전트는 몇 범위인가?"에 이어 **"그렇다면 6개 차원 중 어디에 먼저 투자해야 하는가?"** 를 물으면, 규정 준수를 일률 적용할 수 없다는 점과 "자율성에 비례한 보안 집중"이 동시에 드러납니다. 낮은 범위인데 세션 격리·오케스트레이션 보안에 과투자하거나, 높은 범위인데 API 로깅만 하는 *불일치*를 찾아내는 것이 이 연습의 목표입니다. ([Agentic AI Security Scoping Matrix 블로그](https://aws.amazon.com/ko/blogs/security/the-agentic-ai-security-scoping-matrix-a-framework-for-securing-autonomous-ai-systems/))

#### (2) OWASP Agentic AI — 10대 위협

OWASP 생성형 AI 보안 프로젝트가 식별한 에이전틱 시스템의 10대 취약점입니다. 아래 다이어그램은 각 위협(①~⑩)이 아키텍처의 *어느 지점*에서 발생하는지 표시합니다 — 입력 경계(①②③), 메모리·데이터(④), 에이전트 간 통신(⑤), 에이전트 자체(⑥), 도구·출력(⑦), 그리고 시스템 전반에 걸친 위협(⑧⑨⑩). 번호와 위협의 상세 매핑은 다이어그램 아래 표를 참조하세요.

```ascii
┌─ 입력
│
├──> 사용자 프롬프트
│      1) 목표 하이재킹 (사용자 프롬프트 --> 정책 및 거버넌스)
│      2) 자격 증명/권한 남용 (사용자 프롬프트 --> 에이전트 1)
├──> API
│      3) 인간-에이전트 신뢰 악용 (API --> 에이전트 1)
└──> 외부 에이전트

  │
  v

┌─ 통합 및 처리
│
├──> 정책 및 거버넌스
├──> 휴먼 인 더 루프
├──> 에이전트 1
├──> 에이전트 2
│      6) 악성 에이전트
├──> 연결된 데이터 / RAG
└──> 메모리
       4) 메모리/컨텍스트 포이즈닝

     [이 계층 내부 연결]
       정책 및 거버넌스 <--> 휴먼 인 더 루프
       정책 및 거버넌스 <--> 에이전트 1
       휴먼 인 더 루프 <--> 에이전트 2
       에이전트 1 <--> 에이전트 2
         5) 안전하지 않은 에이전트 간 통신
       연결된 데이터 / RAG <--> 메모리
       에이전트 2 <--> 메모리

  │
  v

┌─ 출력
│
├──> 도구 (에이전트 2 --> 도구)
│      7) 도구 오용/악용
│      도구 --> API 및 리소스
├──> API 및 리소스
└──> 외부 에이전트 (에이전트 2 --> 외부 에이전트)

  │
  v

[시스템 전반 위협]  입력 / 통합 및 처리 / 출력 전체에 걸쳐 발생
  8) 공급망 취약성
  9) 예기치 않은 코드 실행
  10) 연쇄 장애
```

| # | 위협 | 요지 | 주 대응(파트) |
| --- | --- | --- | --- |
| 1 | 에이전트 목표 하이재킹 | 프롬프트 인젝션·오염 데이터로 목표 조작 | 입력 검증(파트 4), 가드레일(파트 2) |
| 2 | 자격 증명·권한 남용 | 위임 체인·역할 상속으로 권한 상승 | 최소 권한·정책(파트 2) |
| 3 | 인간-에이전트 신뢰 악용 | 신뢰를 악용해 조종·정보 추출 | 인간 감독 보호(파트 4) |
| 4 | 메모리·컨텍스트 포이즈닝 | 악성 데이터로 저장 정보 손상 | 메모리 격리·검증(파트 4) |
| 5 | 안전하지 않은 에이전트 간 통신 | 메시지 가로채기·조작·도용 | 메시지 서명·신뢰 경계(모듈 1·파트 3) |
| 6 | 악성 에이전트 | 손상된 에이전트의 목표 이탈 | 행동 이상 탐지·격리(파트 4) |
| 7 | 도구 오용·악용 | 합법 도구 오용 → 데이터 도난 | 도구 권한 부여(파트 2) |
| 8 | 에이전트 공급망 취약성 | 서드파티 구성 요소의 악성 코드 | 도구 레지스트리·보안 평가(파트 4) |
| 9 | 예기치 않은 코드 실행 | 코드 생성 악용 → RCE | 샌드박스·입력 검증(파트 3·4) |
| 10 | 연쇄 장애 | 단일 장애가 네트워크 전반 전파 | 신뢰성 제어(모듈 1·4) |

#### (3) 심층 방어(Defense in Depth) — 7계층

AWS는 보안을 단일 지점이 아니라 여러 계층으로 구축합니다. 중세 성이 벽 하나가 아니라 해자·성문·경비를 겹치는 것과 같습니다. **각 계층은 아래 계층을 전제로 쌓이며, 이 모듈은 이 7계층 지도를 따라 진행됩니다.**

```ascii
[심층 방어 7계층]  아래에서 위로 쌓인다

7. 위협 탐지 및 사고 대응
  ^
6. 데이터 보호
  ^
5. 애플리케이션 보호
  ^
4. 네트워크 및 엣지 보호
  ^
3. 인프라 보호
  ^
2. Identity & Access 관리
  ^
1. 정책, 절차 및 인식 (기반)
```

| 계층 | 역할 | 이 모듈에서 다루는 위치 |
| --- | --- | --- |
| 1. 정책·절차·인식 | 거버넌스·조직 이해의 기반 | 파트 1·4 |
| 2. Identity & Access | 누가 에이전트에, 에이전트가 무엇에 접근하는지 제어 | **파트 2** |
| 3. 인프라 보호 | 런타임 환경 보안 | **파트 3** |
| 4. 네트워크·엣지 | 트래픽 제어·리소스 격리 | **파트 3** |
| 5. 애플리케이션 보호 | 가드레일·안전 제어(계층 1~4가 지원) | 파트 2(정책)로 구현 |
| 6. 데이터 보호 | 암호화·분류·개인정보(모든 계층 조합) | 파트 2·3·4 통합 |
| 7. 위협 탐지·대응 | 모니터링·탐지·대응 | **파트 4** |

> **💡 팁 — 애플리케이션·데이터 보호의 위치**: 계층 5·6은 별도 섹션이 아니라 **다른 계층들의 조합으로 달성**됩니다. 애플리케이션 보호는 파트 2의 AgentCore Policy 가드레일로, 데이터 보호는 파트 2(액세스)+파트 3(암호화·격리)+파트 4(규정 준수)의 결합으로 구현된다는 점을 미리 알려주면 학습자가 "왜 5·6은 따로 안 다루지?"라는 혼란을 겪지 않습니다.

### 1.3 구현 요건 및 절차 — 범위 판정에서 계층 제어까지

1. **자율성 범위 판정**: 대상 에이전트가 Security Scoping Matrix의 어느 범위(1~4)인지 결정한다. "에이전트가 시스템을 *변경*할 수 있는가?", "누가 *개시*하는가(사람/환경)?", "실행 전 *승인*이 필요한가?"를 묻는다.
2. **위협 매핑**: OWASP 10대 위협 중 이 에이전트에 해당하는 것을 식별한다(도구를 쓰면 #7, 메모리를 쓰면 #4, 다중 에이전트면 #5·#6…).
3. **6개 차원 요구 수준 설정**: 판정한 범위에 비례해 6개 보안 차원 각각의 정교함을 정한다(범위 4는 지속 모니터링·다중 검토자까지).
4. **7계층에 제어 배치**: 각 위협·차원을 심층 방어 계층에 매핑한다(자격 증명→계층 2, 격리→계층 3·4, 감사→계층 7).
5. **HITL 경계 정의**: 범위 2·3에서 어떤 작업이 사람 승인을 요구하는지(고액 거래·되돌릴 수 없는 작업 등) 명시한다.

### 1.4 구현 예시 — 범위 판정 워크시트

동일한 "환불 처리 에이전트"라도 설계에 따라 범위가 달라지고, 요구되는 제어가 달라집니다.

```ascii
┌─ Q1. 에이전트가 시스템을 변경(쓰기)하는가?
│
├──> 아니오
│      범위 1 / 대리권 없음 (조회만, 사람이 실행)
│
└──> 예
     │
     ├─ Q2. 실행 전 사람 승인이 필요한가?
     │
     ├──> 예
     │      범위 2 / 규정된 대리권 (단계별 HITL 승인)
     │
     └──> 아니오
          │
          ├─ Q3. 누가 개시하는가?
          │
          ├──> 사람
          │      범위 3 / 감독되는 대리권 (사람 트리거 / 정책 내 자동)
          │
          └──> 환경
                 범위 4 / 전체 대리권 (환경 트리거 / 완전 자율)
```

**적용 예 — 환불 에이전트를 범위 3으로 설계**할 경우 필요한 제어:
- ① 자격 증명: 에이전트 전용 자격 증명 + 사용자 위임 컨텍스트(파트 2)
- ② 정책 경계: "500달러 미만만 자동, 초과는 HITL"을 Cedar 금지·조건부 정책으로(파트 2)
- ③ 네트워크: 환불 API를 프라이빗 엔드포인트로 격리(파트 3)
- ④ 감사: 모든 환불 결정의 추론 체인·자격 증명 컨텍스트 로깅(파트 4)

> **💡 팁**: "범위를 낮추는 것"도 유효한 보안 결정임을 강조하세요. 자동화 이득이 위험을 정당화하지 못하면, 범위 4를 범위 2·3으로 낮춰 HITL을 추가하는 것이 옳은 설계입니다. 자율성은 목표가 아니라 트레이드오프입니다.

### 1.5 모범 사례 (Well-Architected Agentic AI Lens)

- 🏛️ **설계 원칙 "자율성에 비례하는 인간 감독"**: Security Scoping Matrix의 범위 판정이 이 원칙의 직접 실천이다. 범위가 높을수록 승인 게이트·모니터링을 강화한다.
- 🏛️ **AGENTREL02-BP05 계층형 인간 감독·승인 워크플로 / AGENTSEC04-BP02 중대 결정 HITL**: 범위 2·3의 승인 게이트를 이 BP로 구현한다. 되돌릴 수 없거나 고위험 작업은 사람 승인을 강제한다.
- 🏛️ **AGENTSEC 보안 기둥 전반(01~09)**: OWASP 10대 위협은 대부분 AGENTSEC 질문과 대응한다 — 메모리 포이즈닝→AGENTSEC01, 도구 오용→AGENTSEC02, 권한 남용→AGENTSEC03, 목표 하이재킹→AGENTSEC04·08, 에이전트 간 통신→AGENTSEC06, 악성 에이전트→AGENTSEC07.
- 🏛️ **AGENTSEC03-BP03 동적 경계를 가진 최소 권한**: 심층 방어의 계층 2는 정적 권한이 아니라 범위·컨텍스트에 따라 조여지는 동적 최소 권한으로 설계한다(파트 2에서 구현).

## 파트 2. 자격 증명·액세스·정책 (심층 방어 계층 1-2)

### 2.1 해결할 문제

심층 방어의 기반 계층(정책·자격 증명 관리)을 먼저 다룹니다. 이 계층이 다른 모든 보안 제어를 가능하게 하기 때문입니다. 에이전트 아키텍처에서 자격 증명은 **양방향**으로 흐릅니다 — *누가 에이전트를 호출하는가*(인바운드)와 *에이전트가 무엇에 접근하는가*(아웃바운드). 두 방향 모두 보호하지 않으면 다음이 발생합니다.

경계가 없으면 자율 에이전트는 강력한 만큼 위험해집니다.

- **예측 불가능한 런타임 동작**: 에이전트가 의도를 동적으로 해석해 설계 시 예측하지 못한 도구·결과를 만든다.
- **권한 남용**: 적절한 권한 없이 고액 거래 같은 범위 밖 조치를 시도한다.
- **비즈니스 규칙 오해석**: 그럴듯해 보이지만 규정 준수 제약을 위반하는 조치를 취한다.
- **데이터 노출**: 실수로 개인정보를 유출하거나 승인 범위를 벗어난 민감 데이터에 접근한다.

해법은 두 축입니다 — **① 자격 증명으로 "누구/무엇"을 확인**하고, **② 정책으로 "무엇을 해도 되는가"를 결정적으로(deterministic) 시행**하는 것입니다.

> **💡 팁**: "에이전트가 신중하게 설계되었는데도 왜 경계가 필요한가?"를 물으세요. 답은 에이전트의 *동적 특성* 입니다. 프롬프트로 아무리 잘 지시해도 LLM은 확률적이므로, 결정적 정책 엔진(파트 2 후반)이 확률적 행동에 하드 경계를 씌워야 합니다. "지시(soft)"와 "시행(hard)"의 차이를 강조하세요.

### 2.2 고려해야 할 기술·서비스

#### (1) 3가지 자격 증명 서비스

AWS는 에이전틱 AI를 위한 세 가지 핵심 자격 증명 서비스를 제공합니다.

| 서비스 | 역할 | 언제 |
| --- | --- | --- |
| **Amazon Cognito** | 웹·모바일용 사용자 디렉터리, OAuth 2.0 토큰 발급, M2M 인증. 내장 디렉터리·기업 디렉터리·소셜 IdP(Google 등) 연동 | 최종 사용자 인증, 외부 IdP 통합 |
| **AgentCore Identity** | AI 에이전트·자동 워크로드 전용 ID·자격 증명 관리. 보안 토큰 저장소, 인바운드/아웃바운드 인증, 감사 추적 | 에이전트가 사용자 대신 리소스에 접근 |
| **AWS IAM** | AWS 서비스·에이전트 리소스·도구에 대한 세분화된 권한 제어 | AWS 리소스 접근, SigV4 인증 |

#### (2) OAuth 2.0 — 2LO vs 3LO

에이전트의 자격 증명 흐름은 "사용자를 대신하는가"에 따라 둘로 나뉩니다.

**2-Legged(2LO) · 클라이언트 자격 증명 흐름** — 앱이 *자신이 소유한* 리소스에 접근. 사용자 상호작용 없음(M2M).

```ascii
앱 (클라이언트 애플리케이션)
  │
  │  1. 클라이언트 자격 증명 (client_id + secret)
  v
권한 부여 서버
  │
  │  2. 액세스 토큰 (새로 고침 토큰 없음)
  v
앱 (클라이언트 애플리케이션)
  │
  │  3. 토큰으로 리소스 액세스
  v
보호되는 리소스 (서비스/도구)
```

- 사용 사례: 서비스 역할로 동일 계정 DB에 접근하는 에이전트, PR 검토·테스트·배포를 위해 GitLab에 접근하는 개발 에이전트.
- 보안 특성: 클라이언트 암호 필요, 액세스 토큰은 임시, **사용자 컨텍스트 없음**, 권한 부여 엔드포인트를 우회해 토큰 엔드포인트로 직행.

**3-Legged(3LO) · 권한 부여 코드 흐름** — 앱이 *사용자를 대신해* 행위. 사용자 동의 필요.

```ascii
앱 (클라이언트 애플리케이션)
  │
  │  1. 권한 부여 요청
  v
사용자
  │
  │  2. 인증 및 동의
  v
권한 부여 서버
  │
  │  3. 권한 부여 코드
  v
앱 (클라이언트 애플리케이션)
  │
  │  4. 코드 + client_secret --> 토큰 요청
  v
권한 부여 서버
  │
  │  액세스 토큰 / 새로 고침 토큰
  v
앱 (클라이언트 애플리케이션)
  │
  │  5. 토큰으로 사용자 소유 리소스 액세스
  v
보호되는 리소스
```

- 사용 사례: 사용자를 대신해 캘린더·이메일 서비스에 접근.
- 핵심 차이: 사용자 동의 단계가 있고, **새로 고침 토큰**이 발급되며, 사용자 소유 리소스에 접근한다.

> **💡 팁 — 2LO/3LO 판별 질문**: "이 작업에 *사람의 동의*가 필요한가?"가 판별선입니다. 에이전트가 자기 서비스 계정 DB를 읽으면 2LO, 사용자의 Gmail을 읽으면 3LO입니다. 범위(파트 1)와 연결하면: 3LO는 사용자 위임이므로 대개 범위 2·3, 2LO 자동 백엔드는 범위 3·4에서 자주 보입니다.

#### (3) AgentCore Gateway — 양방향 인증(`/mcp`)

AgentCore Gateway는 사용자→게이트웨이(인바운드)와 게이트웨이→백엔드(아웃바운드)를 모두 제어하는 양방향 보안 아키텍처입니다.

```ascii
에이전트 (MCP 클라이언트)
  │
  │  인바운드 / IAM SigV4 또는 OAuth 토큰
  v
┌─ AgentCore Gateway (도구 나열 / 간접 호출 / 검색)
│
├──> AgentCore Identity (토큰 검증)
│      │
│      v
│      자격 증명 공급자 (Cognito / Okta / Auth0)
│
└──> 대상 (Lambda / OpenAPI / Smithy / MCP)
       아웃바운드 / IAM / API 키 / OAuth 토큰
```

- **인바운드 인증 2방식**: ① IAM(SigV4)로 AWS 보안 주체 검증 — 세분화된 제어. ② OAuth 토큰(MCP 권한 부여 사양) — 외부 IdP를 통한 사용자 위임 시나리오.
- **아웃바운드 권한 부여 3방식**: ① AWS IAM(게이트웨이 서비스 역할로 SigV4). ② API 키(보안 토큰 저장소에서 검색). ③ OAuth 토큰(2LO 클라이언트 자격 증명 또는 3LO 권한 부여 코드).

#### (4) AgentCore Policy + Cedar — 결정적 정책 시행

Amazon Bedrock AgentCore Policy는 에이전트-도구 상호작용을 가로채 **결정적으로**(확률적 LLM 판단이 아니라) 권한 부여를 시행합니다. 정책은 **Cedar** 언어로 작성하며, 자연어 프롬프트에서 Cedar로 변환하는 **NL2Cedar**를 지원합니다.

```ascii
에이전트 및 기타 MCP 클라이언트
  │
  │  인바운드 도구 호출
  v
┌─ AgentCore Gateway
│
├──> AgentCore Policy (NL2Cedar / 동적 평가)
│      정책 평가 요청을 보내고 허용 또는 거부 결정을 돌려받는다
│      │
│      v
│      AgentCore Observability (감사 추적)
│
└──> 보호되는 리소스 (도구 / API / 시스템 / 데이터)
       허용된 도구 호출만 전달한다
```

**두 가지 적용 모드**로 안전하게 롤아웃합니다.
- `LOG_ONLY`: 결정을 적용하지 않고 허용/거부 여부만 로깅(섀도 모드 — 정책 검증용).
- `ENFORCE`: 결정을 실제로 적용해 작업을 허용/거부.

> **💡 팁 — 안전한 정책 배포**: 새 정책은 반드시 `LOG_ONLY`로 먼저 배포해 실제 트래픽에 어떤 결정을 내릴지 관찰한 뒤 `ENFORCE`로 승격하라고 강조하세요. 이는 IAM 정책 시뮬레이터·섀도 배포와 같은 원리이며, 잘못된 정책이 프로덕션 에이전트를 마비시키는 사고를 예방합니다.

### 2.3 구현 요건 및 절차

**A. 엔드투엔드 자격 증명·액세스 흐름 구성**

사용자→에이전트→도구의 7단계 흐름을 구성합니다.

```ascii
사용자
  │
  │  1. IdP 인증 (OAuth/OIDC)
  v
에이전트
  │
  v
AgentCore Runtime
  │
  │  2. 도구 호출
  v
┌─ AgentCore Gateway
│
├──> AgentCore Identity
│      3-4. 인바운드/아웃바운드 인증 (JWT 발급)
│
├──> AgentCore Policy
│      5. 정책 평가 요청, 6. 허용 또는 거부 응답
│
└──> 도구
       7. 허용 시 도구 호출
```

1. **사용자 인증**: OAuth 2.0/OIDC로 IdP를 통해 인증 → 상호작용 전반에 쓸 자격 증명 생성.
2. **도구 사용 요청**: 에이전트가 Gateway를 통해 도구를 호출.
3. **인바운드 인증**: AgentCore Identity가 OAuth 2.0으로 인바운드 요청 검증.
4. **아웃바운드 권한 부여**: 보안 토큰 저장소에서 자격 증명 검색 → 다운스트림용 JWT 토큰 발급(권한 부여 컨텍스트 포함).
5. **정책 평가**: Gateway가 JWT와 함께 요청을 AgentCore Policy로 전송 → Cedar 정책으로 평가.
6. **정책 결정**: `allow`/`deny` 반환.
7. **도구 호출 실행**: `allow`면 대상 서비스로 진행.

**B. IAM 기반 인바운드/아웃바운드(AgentCore Runtime)**
1. **인바운드**: 사용자가 SigV4 자격 증명으로 에이전트 호출 → Runtime이 AgentCore Identity에 AuthN/AuthZ 요청 → 각 요청을 암호화 서명·검증, 세션 내내 사용자 자격 증명 보존(감사용).
2. **아웃바운드**: Runtime이 **IAM 실행 역할**을 수임 → 이 역할의 권한 정책이 접근 가능한 AWS 서비스·리소스를 정의 → 표준 SDK 호출로 리소스 접근.

**C. Cedar 정책 작성 절차**
1. 자연어로 규칙을 기술한다("재무 부서 사용자만 500달러 미만 환급 허용").
2. NL2Cedar로 초안을 생성하거나 직접 작성한다 — **효과(permit/forbid) + 범위(principal/action/resource) + 조건(when)**.
3. 정적 속성(자격 증명)과 런타임 파라미터(`context.input`)를 구분해 조건을 설계한다.
4. `LOG_ONLY`로 배포해 결정을 관찰한다.
5. 검증 후 `ENFORCE`로 승격한다.

### 2.4 구현 예시

#### (1) 보안 정책이 포함된 에이전트 정의 파일

에이전트의 권한 경계·에스컬레이션 규칙을 코드가 아닌 **정의 파일(md)** 로 분리하면, 정책과 함께 버전 관리·리뷰할 수 있습니다(모듈 1의 "행동을 코드처럼 취급" 원칙).

```markdown
# 환불 처리 에이전트 (Refund Agent)

## 역할
전자상거래 환불을 처리하는 전문 에이전트. 자율성 **범위 3(감독되는 대리권)** 으로 운영된다.
사람이 워크플로를 트리거하면, 정책 경계 내에서 자동으로 환불을 실행한다.

## 자격 증명 컨텍스트
- 인바운드: 사용자가 OAuth 2.0(3LO)으로 위임한 컨텍스트를 유지한다.
- 아웃바운드: 환불 API 접근은 에이전트 전용 IAM 실행 역할을 수임한다(사용자 권한과 분리).

## 권한 경계 (정책으로 시행 — 아래 Cedar 참조)
- 500달러 **미만** 환불: 자동 처리 허용
- 500달러 **이상** 환불: 사람 승인(HITL)으로 에스컬레이션
- 사기 의심(fraud_detected) 환불: 회사가 개시한 경우에만 처리

## 에스컬레이션 (휴먼 인 더 루프)
다음은 자동 처리하지 않고 사람에게 넘긴다.
- 정책이 거부(deny)를 반환한 모든 작업
- 500달러 이상 또는 사기 의심 건
- 동일 주문에 대한 2회 이상 반복 환불 시도

## 가드레일
- 고객 PII·결제 정보를 응답에 노출하지 않는다.
- 정책 결정을 우회하려는 어떤 추론도 수행하지 않는다(정책이 최종 권한).
- 모든 환불 결정의 추론 체인·자격 증명 컨텍스트를 감사 로그에 남긴다.

## 성공 기준
- 정책 위반 0건, 감사 추적 완전성 100%
```

> **왜 정의와 정책을 함께 두는가**: 에이전트의 프롬프트("~하려고 시도")와 Cedar 정책("~는 절대 불가")은 **역할이 다릅니다.** 프롬프트는 설득이고 정책은 시행입니다. 정의 파일에 경계를 문서화하고, 그 경계를 아래 Cedar 정책으로 *기계적으로 강제*하면 프롬프트가 뚫려도 정책이 막습니다.

#### (2) Cedar 정책 3종 — 허가·조건부 허가·조건부 금지

**① 기본 허가 정책** — "재무 부서 사용자에 한해 500달러 미만 환급 허용".

```cedar
// permit = 허가 효과: 아래 조건을 모두 만족할 때만 작업을 허용
permit (
    principal,                                       // 보안 주체(누가): 모든 주체 대상
    action == MCP::Action::"process_reimbursement",  // 작업(무엇을): 환급 처리 도구 호출
    resource                                         // 리소스(어디에): 모든 리소스 대상
)
when {
    principal.username == "refund-agent" &&          // 조건1: 주체의 username이 refund-agent
    resource.amount < 500                            // 조건2: 환급액이 500달러 미만
};
// 세 부분 구조: 효과(permit) + 범위(principal·action·resource) + 조건(when)
// 범위가 엔터티 속성을 참조하면 그 세부는 when 조건으로 내려간다.
```

**② 조건부 허가 정책(AND 로직)** — "취소 사유가 사기 탐지인 경우, 회사가 개시했을 때만 환불".

```cedar
permit (
    principal,
    action == MCP::Action::"refund_calculator",      // 환불 계산 도구
    resource
)
when {
    // 조건1: 개시자가 '회사'여야 함 (고객·자동화 시스템이 아님)
    context.input.initiated_by == MCP::refund_calculator::Input::initiated_by::"company" &&
    // 조건2: 취소 사유가 정확히 'fraud_detected'여야 함
    context.input.cancellation_reason == MCP::refund_calculator::Input::cancellation_reason::"fraud_detected"
};
// context.input = 도구 호출 시 전달된 '런타임 파라미터'를 평가 → 정적 자격 증명뿐 아니라
// 실제 요청 내용에 기반한 세분화된 권한 부여가 가능하다.
// 실무 의미: 사기 관련 환불은 회사 개시일 때만 자동 허용 → 적절한 승인 워크플로 강제.
```

**③ 조건부 금지 정책(OR + has 검사)** — "18세 미만 또는 85세 초과 고객에게 자동차 보험 견적 금지".

```cedar
// forbid = 금지 효과: 다른 정책이 허용하더라도 이 조건이 맞으면 '무조건 차단'(우선)
forbid (
    principal,
    action == MCP::Action::"quote_generator",        // 견적 생성 도구
    resource
)
when {
    // 조건1: 적용 범위가 '자동차'일 때만 이 정책 적용 (주택·생명 보험은 제외)
    context.input.coverage_type == MCP::quote_generator::Input::coverage_type::"auto" &&
    // 조건2: has 연산자로 age 속성 '존재 여부'를 먼저 확인 (방어적 프로그래밍 — 누락 시 오류 방지)
    context.input.customer_info has age &&
    // 조건3: 괄호로 OR를 하나의 단위로 평가 → 18세 미만 '또는' 85세 초과
    (context.input.customer_info.age < 18 || context.input.customer_info.age > 85)
};
// 괄호가 중요: AND와 결합 전에 OR를 단일 단위로 평가해야 연산자 우선순위 오류를 막는다.
// 금지 정책은 우회 불가능한 하드 경계 → 규제·비즈니스 규칙 위반을 원천 차단.
```

> **💡 팁 — permit vs forbid**: 허가(permit)는 "조건이 맞으면 허용", 금지(forbid)는 "조건이 맞으면 무조건 차단(허가보다 우선)"입니다. 규제 요구(연령 제한 등)는 forbid로, 업무 권한 부여는 permit으로 표현하는 것이 안전합니다. `has` 연산자로 속성 존재를 먼저 확인하는 방어적 패턴을 꼭 짚어주세요.

#### (3) AgentCore Policy 권한 부여 흐름 — JWT에서 결정까지

Gateway는 각 요청의 **JWT 토큰**(사용자 OAuth 클레임)과 **MCP 도구 호출 요청**(도구·인수)을 결합해 Cedar 권한 부여 요청을 구성합니다.

```ascii
[입력 두 소스]  둘 다 Gateway 로 들어간다

1) JWT 토큰 (sub / username / role / department / scope)
1) MCP 도구 호출 (도구 이름 / 인수)
  │
  v
┌─ 2) AgentCore Gateway (Cedar 요청 구성)
│
├──> 3) 엔터티 스토어 (OAuthUser + JWT 클레임을 태그로)
│      클레임을 태그로 변환해 4) Cedar 평가로 전달한다
│
└──> 4) Cedar 평가 (주체 / 작업 / 리소스 / 조건)
       Gateway 요청과 엔터티 스토어 태그를 함께 평가한다
       │
       v
       허용 / 거부
```

**1단계 — 입력 두 소스** (JWT 토큰 + MCP 도구 호출):

```json
// JWT 토큰: 사용자에 대한 OAuth 클레임
{
  "sub": "12345678-1234-1234-1234-123456789012",
  "iss": "https://cognito-idp.us-east-1.amazonaws.com/us-east-1_Vg2efaoGO",
  "username": "refund-agent",
  "scope": "aws.cognito.signin.user.admin refund:write",
  "role": "admin",
  "department": "finance"
}
```

```json
// MCP 도구 호출 요청: 실제 실행하려는 도구와 인수
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "RefundTool__process_refund",
    "arguments": { "orderId": "12345", "amount": 450, "reason": "Defective product" }
  }
}
```

**2단계 — Cedar 권한 부여 요청 구성** (Gateway가 두 소스에서 추출):

```json
{
  // 보안 주체: JWT의 sub 클레임에서 생성
  "principal": "AgentCore::OAuthUser::\"12345678-1234-1234-1234-123456789012\"",
  // 작업: MCP 요청의 도구 이름에서 추출
  "action": "AgentCore::Action::\"RefundTool__process_refund\"",
  // 리소스: 대상 Gateway 인스턴스
  "resource": "AgentCore::Gateway::\"arn:aws:bedrock-agentcore:us-west-2:123456789012:gateway/refund-gateway\"",
  // 컨텍스트: MCP 도구 인수를 그대로 포함 → 정책의 context.input이 참조
  "context": { "input": { "orderId": "12345", "amount": 450, "reason": "Defective product" } }
}
```

**3단계 — 엔터티 스토어** (JWT 클레임을 OAuthUser 엔터티의 **태그**로 저장):

```json
{
  "uid": { "type": "AgentCore::OAuthUser", "id": "12345678-1234-1234-1234-123456789012" },
  "attrs": { "id": "12345678-1234-1234-1234-123456789012" },
  // tags = 모든 JWT 클레임 → 정책이 principal.username, principal.department 등으로 참조 가능
  "tags": {
    "username": "refund-agent",
    "iss": "https://cognito-idp.us-east-1.amazonaws.com/us-east-1_Vg2efaoGO",
    "scope": "aws.cognito.signin.user.admin refund:write",
    "role": "admin",
    "department": "finance"
  }
}
```

**4단계 — Cedar 평가** (체계적 검사, 모두 통과해야 `allow`):

| 검사 | 내용 | 결과 |
| --- | --- | --- |
| 보안 주체 | 주체가 OAuthUser인가? | ✓ 일치 |
| 작업 | 작업이 `RefundTool__process_refund`인가? | ✓ 일치 |
| 리소스 | 리소스가 환불 게이트웨이인가? | ✓ 일치 |
| 조건 | `username == 'refund-agent'`? · `context.input.amount < 500`? (450 < 500) | ✓ 참 |
| **결과** | 모든 검사 통과 | **허용** |

> **💡 팁 — 엔터티 태그가 핵심**: OAuth 인증과 Cedar 평가를 잇는 다리가 **엔터티 태그**입니다. Gateway가 JWT 클레임을 태그로 변환해 저장하기 때문에, 정책이 "재무 부서의 관리자만"처럼 사용자 속성에 기반한 속성 기반 액세스 제어(ABAC)를 표현할 수 있습니다. 검사 중 하나라도 실패하면 `deny`가 반환되어 도구 호출이 차단된다는 점을 강조하세요.

### 2.5 모범 사례 (Well-Architected Agentic AI Lens)

- 🏛️ **AGENTSEC03 에이전트 자격 증명·권한·권한 상승 방지**: BP01 강력한 인증(OAuth/OIDC·SigV4), BP02 **에이전트와 사람 권한 분리**(아웃바운드 IAM 실행 역할을 사용자 권한과 분리), BP03 동적 경계 최소 권한(Cedar 조건부 정책), BP04 정기 권한 감사. 환불 에이전트의 전용 실행 역할이 BP02의 직접 실천이다.
- 🏛️ **AGENTSEC02 도구 사용 제어·보안**: BP01 도구 권한 부여(AgentCore Policy로 도구 호출을 결정적으로 시행), BP02 도구 입출력 검증. Cedar가 `context.input`으로 도구 인수를 평가하는 것이 BP01·BP02의 접점이다.
- 🏛️ **AGENTSEC04 목표 정렬·조작 방지**: BP01 가드레일·정렬 제어(forbid 정책이 규제 위반을 하드 차단), BP02 중대 결정 HITL(500달러 초과·사기 의심 에스컬레이션).
- 🏛️ **AGENTSEC08-BP01 다층 입력 검증·프롬프트 인젝션 방어**: 정책은 프롬프트 인젝션으로 에이전트 추론이 오염돼도 도구 실행 단계에서 결정적으로 차단하는 최후 방어선이다. 프롬프트가 뚫려도 정책은 뚫리지 않는다.
- 🏛️ **AGENTSEC05-BP01 포괄적 로깅·의사결정 아티팩트 저장**: AgentCore Policy → Observability 감사 추적이 모든 정책 결정을 근거와 함께 기록한다(파트 4에서 심화).

## 파트 3. VPC 통합 및 네트워크 보안 (심층 방어 계층 3-4)

### 3.1 해결할 문제

파트 2의 자격 증명·정책 기반 위에, 이제 **인프라 보호(계층 3)와 네트워크·엣지 보호(계층 4)** 를 쌓습니다. 자격 증명이 "누가 무엇을 하는가"를 통제한다면, 네트워크 격리는 "트래픽이 *어디로* 흐르는가"를 통제합니다. 목표는 두 가지입니다.

- **인프라 격리**: 에이전트 런타임 환경을 퍼블릭 인터넷에서 분리해 에이전트 엔드포인트에 대한 무단 접근을 차단한다.
- **데이터 이동 보호**: 에이전트↔AgentCore 서비스 간 트래픽이 퍼블릭 인터넷을 통과하지 않고 AWS 백본 내에 머물게 한다(전송 중 데이터 보호).

특히 의료(PHI)·금융(PCI) 같은 규제 워크로드는 "민감 데이터를 퍼블릭 인터넷에 노출하지 않는다"가 강제 요구 사항이므로, 이 계층이 규정 준수의 전제가 됩니다.

> **💡 팁**: 파트 2·3의 결합을 강조하세요 — 자격 증명 제어(파트 2)는 "인증된 사용자도 잘못된 데이터에 접근 못 하게"이고, 네트워크 격리(파트 3)는 "인증조차 시도할 수 없게 애초에 도달 경로를 없애는" 것입니다. 두 계층이 겹칠 때 심층 방어가 완성됩니다.

### 3.2 고려해야 할 기술·서비스

#### (1) 다중 방어 계층 — 프라이빗 서브넷·보안 그룹·NACL

VPC 인프라 보호의 기본은 여러 제어를 겹치는 것입니다.

```ascii
┌─ VPC
│
├─ 퍼블릭 서브넷
│  │
│  ├─ 인터넷 게이트웨이
│  └─ NAT 게이트웨이
│
├─ 프라이빗 서브넷
│  │
│  ├─ 컴퓨팅 (에이전트)
│  └─ 보안 그룹
│
├─ 네트워크 ACL
└─ 라우팅 테이블
```

| 제어 | 유형 | 특징 | 용도 |
| --- | --- | --- | --- |
| **보안 그룹** | 상태 저장(stateful) | 인스턴스·ENI 수준, 다른 SG 참조 가능, 허용 규칙만 | 세분화된 주 제어 |
| **네트워크 ACL** | 상태 비저장(stateless) | 서브넷 수준, 거부 규칙 가능 | 대략적 가드레일·보조 제어 |

두 제어를 함께 쓰면 하나를 잘못 구성해도 다른 하나가 방어선을 유지합니다.

#### (2) AgentCore Runtime VPC 구성 — 다중 AZ

관리형 VPC를 지정하면 AgentCore Runtime은 **ENI를 통해 VPC에 연결되는 AWS 서비스 계정**에서 컴퓨팅을 실행합니다.

```ascii
┌─ AWS 리전
│
├─ VPC (다중 AZ)
│  │
│  ├─ 가용 영역 1 / 프라이빗 서브넷
│  │  ├─ ENI
│  │  └─ 보안 그룹
│  │
│  ├─ 가용 영역 2 / 프라이빗 서브넷
│  │  └─ ENI
│  │
│  └─ VPC 엔드포인트
│     │
│     │  AWS PrivateLink
│     v
└─ AgentCore Runtime (AWS 서비스 계정)
```

- **다중 AZ**: 서브넷을 여러 가용 영역에 분산해 한 AZ 장애 시에도 계속 작동(고가용성).
- **보안 그룹**: 최소 권한 원칙으로 에이전트 통신에 필요한 포트·프로토콜만 개방.
- **서비스 연결 역할**: `AWSServiceRoleForBedrockAgentCoreNetwork`가 있어야 Bedrock이 ENI 생성·SG 관리를 대신 수행.
- **VPC 엔드포인트**: 인터넷 라우팅 없이 다른 AgentCore 서비스에 프라이빗 연결.

#### (3) AWS PrivateLink — 프라이빗 연결

AWS PrivateLink는 VPC를 인터넷에 노출하지 않고 프라이빗 IP로 AgentCore Gateway 등에 연결합니다.

```ascii
소비자 VPC
  │
  │  프라이빗 IP (인터넷 미경유)
  v
AWS PrivateLink
  │
  │  AWS 프라이빗 네트워크
  v
Amazon Bedrock AgentCore Gateway
```

- 프라이빗 IP로 다른 VPC의 서비스에 접근하며, 트래픽이 Amazon 프라이빗 네트워크에 머문다.
- 두 개념의 결합: **Amazon VPC**(격리된 프라이빗 네트워크) + **서비스로 제공되는 소프트웨어**(제공업체 소유·운영, 소비자 사용).

#### (4) VPC 엔드포인트 — 인터페이스 엔드포인트로 프라이빗 경로

프라이빗 VPC 내 에이전트가 VPC 외부 리소스(예: AgentCore Memory)에 접근하는 경로입니다.

```ascii
에이전트 (프라이빗 서브넷)
  │
  │  아웃바운드 규칙
  v
보안 그룹
  │
  v
ENI
  │
  v
VPC 엔드포인트 (PrivateLink)
  │
  │  AWS 백본
  v
AgentCore 서비스 (예: Memory)
```

AgentCore는 **단일 인터페이스 엔드포인트** `com.amazonaws.region.bedrock-agentcore`로 런타임·내장 도구(코드 인터프리터·브라우저)·메모리·자격 증명을 지원하며, **Gateway만 별도 엔드포인트** `com.amazonaws.region.bedrock-agentcore.gateway`를 사용합니다.

> **💡 팁 — 프라이빗 DNS**: VPC 엔드포인트에 프라이빗 DNS를 켜면, API 호출이 서비스의 *퍼블릭* DNS 이름을 그대로 대상으로 해도 그 이름이 엔드포인트 ENI의 *프라이빗* IP로 확인됩니다. 즉 애플리케이션 코드를 바꾸지 않고도 트래픽이 프라이빗 경로로 흐릅니다. 이 "코드 무변경 격리"가 실무 채택의 핵심 포인트입니다.

### 3.3 구현 요건 및 절차

**A. VPC·네트워크 아키텍처 설계**
1. **다중 AZ VPC**를 만들고 프라이빗 서브넷을 여러 AZ에 배치한다.
2. **보안 그룹**을 최소 권한으로 구성한다(에이전트↔메모리·게이트웨이 트래픽만 허용).
3. **NACL**을 보조 가드레일로 추가한다(서브넷 수준 거부 규칙).
4. **서비스 연결 역할** `AWSServiceRoleForBedrockAgentCoreNetwork` 생성 권한을 확인한다.

**B. PrivateLink·VPC 엔드포인트 구성**
1. 필요한 AgentCore 서비스용 **인터페이스 엔드포인트**를 생성한다(`bedrock-agentcore`, 필요 시 `.gateway`).
2. 활성화한 각 서브넷에 **엔드포인트 네트워크 인터페이스**가 생성된다.
3. **프라이빗 DNS**를 활성화해 기본 리전 이름으로 접근 가능하게 한다.
4. 라우팅 테이블이 AgentCore 트래픽을 인터넷이 아니라 엔드포인트로 보내도록 한다.

**C. 엔드포인트 정책으로 접근 제한**
1. 기본 정책은 전체 접근을 허용하므로, **사용자 지정 엔드포인트 정책**을 연결해 조인다.
2. 허용할 **보안 주체·작업·리소스**를 지정한다.
3. Gateway가 OAuth(비-SigV4) 수신이면 `Principal`을 와일드카드 `*`로, SigV4면 특정 AWS Identity로 지정한다(Runtime도 동일).

**D. 인터넷 없는 프라이빗 VPC의 필수 엔드포인트**
컨테이너 기반 배포 시 다음 엔드포인트가 없으면 작동하지 않는다.
- **Amazon ECR**: `ecr.dkr`(Docker), `ecr.api`(ECR API)
- **Amazon S3**: `s3`(ECR Docker 계층 스토리지, 게이트웨이 엔드포인트)
- **Amazon CloudWatch**: `logs`(로그 엔드포인트)

### 3.4 구현 예시

#### (1) 에이전트의 인터페이스 엔드포인트 접근 경로

```ascii
┌─ 에이전트
│
├──> VPC 엔드포인트
│      com.amazonaws.region.bedrock-agentcore
│      │
│      v
│      Runtime / Identity / Browser / Code Interpreter / Memory
│
└──> VPC 엔드포인트
       com.amazonaws.region.bedrock-agentcore.gateway
       │
       v
       AgentCore Gateway
```

#### (2) VPC 인터페이스 엔드포인트 정책 — AgentCore Memory 접근 제한

특정 IAM 보안 주체가 특정 Memory에 대한 데이터 영역 작업만 하도록 제한하는 정책입니다.

```json
{
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        // 이 계정의 IAM 주체만 허용 (SigV4 기반이므로 특정 Identity 지정 가능)
        "AWS": "arn:aws:iam::ACCOUNT_ID:root"
      },
      "Action": [
        // 이벤트(단기 메모리) 데이터 영역 작업
        "bedrock-agentcore:CreateEvent",
        "bedrock-agentcore:GetEvent",
        "bedrock-agentcore:ListEvents",
        "bedrock-agentcore:DeleteEvent",
        // 메모리 레코드(장기 메모리) 작업
        "bedrock-agentcore:RetrieveMemoryRecords",
        "bedrock-agentcore:GetMemoryRecord",
        "bedrock-agentcore:ListMemoryRecords",
        "bedrock-agentcore:DeleteMemoryRecord",
        "bedrock-agentcore:BatchCreateMemoryRecords",
        "bedrock-agentcore:BatchUpdateMemoryRecords",
        "bedrock-agentcore:BatchDeleteMemoryRecords",
        // 액터·세션 조회
        "bedrock-agentcore:ListActors",
        "bedrock-agentcore:ListSessions"
      ],
      // 특정 Memory 리소스로 범위 한정 (다른 메모리는 이 엔드포인트로 접근 불가)
      "Resource": "arn:aws:bedrock-agentcore:us-east-1:ACCOUNT_ID:memory/MEMORY_ID"
    }
  ]
}
// 핵심: 엔드포인트 정책은 '네트워크 경로 수준'의 최소 권한 — IAM 역할 정책과 겹쳐
//       이중으로 접근을 조인다(심층 방어). Principal·Action·Resource 3요소로 통제.
```

> **💡 팁 — Principal 와일드카드 함정**: 학습자가 자주 혼동하는 부분입니다. Gateway 수신이 **OAuth**면 SigV4 주체가 없으므로 `Principal: "*"`로 둬야 하고(대신 OAuth·정책으로 통제), **SigV4**면 특정 IAM 주체로 좁힐 수 있습니다. "와일드카드 = 무조건 위험"이 아니라, *어느 계층에서 통제하는가*의 문제임을 설명하세요.

#### (3) 종합 흐름 — 프라이빗 경로로 Memory 접근

프라이빗 VPC의 에이전트가 AgentCore Memory에 접근할 때: ① 아웃바운드 규칙이 설정된 **보안 그룹** 통과 → ② 프라이빗 서브넷의 **ENI**(서비스 연결 역할이 자동 생성, 프라이빗 IP 할당) 통과 → ③ **VPC 인터페이스 엔드포인트**로 라우팅(프라이빗 DNS면 퍼블릭 이름도 프라이빗 IP로 확인) → ④ **AWS 백본**을 통해 대상 서비스로 직접 전달. 인터넷 게이트웨이·NAT가 전혀 필요 없어 보안 강화·지연 감소·규정 준수를 동시에 달성합니다.

#### (4) 종합 아키텍처 다이어그램

파트 3에서 다룬 요소 — 다중 AZ 프라이빗 서브넷, 보안 그룹, NACL, ENI, 인터페이스 엔드포인트 2종(+ 필수 인프라 엔드포인트), PrivateLink — 를 하나의 아키텍처로 통합하면 다음과 같습니다.

```ascii
[프라이빗 VPC 안의 AgentCore 에이전트 - 종합 네트워크 아키텍처]

사용자 / 호출자
  │  HTTPS (SigV4 또는 OAuth)
  v
┌─ AWS 리전
│
├─ VPC (다중 AZ, 인터넷 게이트웨이 없음)
│  │
│  ├─ NACL  (서브넷 경계, 상태 비저장, 보조 가드레일)
│  ├─ 라우팅 테이블  (AgentCore 트래픽을 인터넷이 아닌 엔드포인트로)
│  │
│  ├─ 가용 영역 A / 프라이빗 서브넷
│  │  ├─ 에이전트 컴퓨팅  (AgentCore Runtime, microVM)
│  │  ├─ 보안 그룹  (상태 저장, 최소 권한, 필요한 포트만)
│  │  └─ ENI  (프라이빗 IP)
│  │
│  ├─ 가용 영역 B / 프라이빗 서브넷   (HA 를 위한 이중화)
│  │  ├─ 에이전트 컴퓨팅
│  │  └─ ENI
│  │
│  └─ VPC 인터페이스 엔드포인트  (엔드포인트 정책으로 접근 제한)
│     │    프라이빗 DNS on -> 퍼블릭 이름도 엔드포인트 프라이빗 IP 로 해석
│     │
│     ├─ com.amazonaws.<region>.bedrock-agentcore
│     │     -> Runtime / Memory / Identity / Code Interpreter / Browser
│     │
│     ├─ com.amazonaws.<region>.bedrock-agentcore.gateway
│     │     -> AgentCore Gateway  (MCP 도구)
│     │
│     └─ 필수 인프라 엔드포인트  (인터넷 없는 VPC 컨테이너 배포용)
│           -> ECR (ecr.dkr / ecr.api), S3 (게이트웨이 EP), CloudWatch Logs
│
│         모든 트래픽은 AWS PrivateLink 를 통해 AWS 백본에만 머문다
│         (인터넷 게이트웨이 / NAT 불필요, 전송 중 데이터 보호)
│         v
└─ AWS 서비스 계정  (관리형)
     ├─ AgentCore Runtime / Memory / Identity / Gateway
     └─ Amazon Bedrock 기반 모델 (Nova / Claude)
```

이 그림의 핵심은 **에이전트 컴퓨팅이 인터넷 경로 없이 프라이빗 서브넷에만 있고**, 모든 AgentCore·인프라 접근이 인터페이스 엔드포인트와 PrivateLink를 거쳐 AWS 백본에 머문다는 점입니다. 다중 AZ로 가용성을, 보안 그룹·NACL·엔드포인트 정책의 3중 제어로 최소 권한을 확보합니다.

## 파트 4. 규정 준수 및 감사 구현 (심층 방어 계층 5-7)

### 4.1 해결할 문제

심층 방어의 최상위 계층인 **위협 탐지 및 사고 대응(계층 7)** 에 도달했습니다. 이 계층은 앞선 모든 계층(정책·자격 증명·인프라·네트워크)을 기반으로 완전한 가시성과 책임성을 제공합니다. 프로덕션 에이전트는 의료·금융·정부처럼 엄격한 규제 안에서 운영되므로, 두 가지를 동시에 해내야 합니다.

- **규정 준수 입증**: 에이전트가 규정 범위 내에서 작동했다는 **증거**를 남긴다(감사·규제 검토에 제시).
- **위협 탐지**: 정책 위반·무단 접근·안전하지 않은 에이전트 행동을 탐지하고 대응한다.

핵심 통찰은 **"규정 준수는 자율성에 비례한다"** 입니다. 자율성이 낮은 에이전트는 기존 애플리케이션처럼 로컬 활동 로그로 충분하지만, 자율성이 높은 에이전트는 지속적 행동 로깅·패턴 분석·예측 모니터링이 필요합니다. 그리고 **탐지보다 예방** 이 우선입니다 — 위반을 사후에 잡기보다 정책(파트 2)으로 애초에 막습니다.

> **💡 팁**: "규정 준수는 설계의 사후 고려가 아니라 기본(built-in)"임을 강조하세요. 파트 2(자격 증명·정책)와 파트 3(네트워크)에서 구성한 제어가 있어야 이 계층의 탐지가 가능합니다 — 적절한 자격 증명 컨텍스트, 네트워크 가시성, 정책 시행이 확립돼야 "누가·무엇을·어떻게"를 탐지할 수 있습니다. 이 파트는 모듈 4(관찰성·평가)와 직접 이어집니다.

### 4.2 고려해야 할 기술·프레임워크

#### (1) 규정 준수·감사의 4대 구성 요소

```ascii
┌─ 에이전틱 시스템
│
├──> RAI 프레임워크 (위험 평가 / 위협 탐지)
├──> 감사 추적 (전체 시스템 활동 캡처)
├──> 데이터 보호 (자동 분류 / 암호화)
└──> 데이터 거버넌스 (정보 흐름 관리)
```

| 구성 요소 | 역할 |
| --- | --- |
| **RAI 프레임워크 통합** | 포괄적 위험 평가·자동 위협 탐지 |
| **감사 추적 아키텍처** | 플랫폼 네이티브 AWS 기능으로 전체 시스템 활동 캡처 |
| **민감 데이터 보호** | 자동 분류·암호화 전략 |
| **데이터 거버넌스** | 분산 에이전트 네트워크 전반의 정보 흐름 관리 |

#### (2) AWS Well-Architected Responsible AI Lens — 책임 있는 AI

전체 AI 수명 주기(설계→개발→운영)에 책임 있는 AI 관행을 적용하는 렌즈입니다. **8개 핵심 요소·100개 모범 사례**로 구성됩니다.

```ascii
┌─ 설계
│  ├─ 사용 사례
│  ├─ 이점 및 위험
│  └─ 출시 기준
│
v
┌─ 개발
│  ├─ 데이터세트 계획
│  ├─ 시스템 계획
│  └─ 평가 및 출시
│
v
┌─ 운영
│  ├─ 사용자 지침
│  └─ 모니터링
```

책임 있는 AI의 **10개 차원** 중 규정 준수에 직접 연결되는 것:

| 차원 | 규정 준수 연결 |
| --- | --- |
| **개인정보 보호** | GDPR·CCPA — 동의 관리·데이터 주체 권리 |

나머지 차원(제어 가능성, 안전성, 공정성, 진실성·견고성, 설명 가능성)도 자율성에 비례해 정교하게 구현해야 합니다.

> **💡 팁**: 규제와 차원을 매핑하는 표가 강력합니다. "우리 조직은 어떤 규제 대상인가?(HIPAA·PCI·GDPR·EU AI법…)"를 물어, 각 규제를 책임 있는 AI 차원으로 번역하게 하세요. ([AWS Responsible AI Lens](https://docs.aws.amazon.com/wellarchitected/latest/responsible-ai-lens/responsible-ai-lens.html))

#### (3) 감사 추적의 5가지 필수 요소

포괄적 감사 추적은 에이전트가 규정 범위 내에서 운영했다는 증거입니다. 모든 추적에 다음이 포함돼야 합니다.

```ascii
┌─ 에이전트 감사 추적
│
├─ 1) 작업 로깅 (도구 호출 / 수정 / 데이터 접근)
├─ 2) 추론 체인 (왜 그 결정을 내렸는가)
├─ 3) 자격 증명 컨텍스트 (누가 승인했는가)
├─ 4) 시간 데이터 (정확한 타임스탬프)
└─ 5) 세션 추적 (다중 상호작용 연결)
```

**자율성 기반 요구**: 낮은 자율성 → 로컬 활동 로그·변경 추적. 높은 자율성 → 지속적 행동 로깅 + 시간 경과 패턴 분석 + 규정 위반 *전에* 드리프트를 잡는 예측 모니터링.

### 4.3 구현 요건 및 절차

**A. 감사 추적 설계**
1. **5요소 캡처**: 작업·추론·자격 증명·시간·세션을 모든 에이전트 작업에 대해 기록한다.
2. **자격 증명 컨텍스트 전파**: 모든 상호작용에서 호출자 자격 증명을 유지해, 각 작업을 승인한 사람·시스템까지 추적 가능하게 한다(책임성 체인).
3. **자율성에 맞춘 심화**: 범위(파트 1)에 따라 로컬 로그 → 지속 로깅 → 예측 모니터링으로 강화한다.
4. **플랫폼 네이티브 활용**: AgentCore Observability·CloudWatch로 구조화 로깅·감사 추적을 구성한다(모듈 4 심화).

**B. 프로덕션 준비 — 배포 전 검증**
1. **정책 검증**: AgentCore Policy 구성이 조직 정책·규정에 부합하는지 확인한다.
2. **경계 테스트**: 에이전트가 정책 위반을 시도할 때 실제로 차단되는지 테스트한다(경계를 초과할 수 없음을 증명).
3. **감사 완전성**: 모든 에이전트 작업이 적절한 로그를 남기는지 확인한다.
4. **자격 증명 전파**: 모든 작업에 걸쳐 호출자 컨텍스트가 유지되는지 검증한다.

**C. 지속적 규정 준수 운영**
1. **실시간 대시보드**: 규정 준수 지표를 표시한다.
2. **자동 알림**: 위반·비정상 패턴에 대해 경고한다.
3. **정기 보고서**: 이해관계자·감사자를 위한 규정 준수 보고서를 생성한다.
4. **사고 대응 절차**: 검증된 대응 절차를 마련한다.

**성공의 열쇠 3가지**: ① 규정 준수 요구는 에이전트 자율성에 비례하므로, 자율성을 키우면 더 정교한 제어가 필요하다. ② 수동 규정 준수는 에이전트의 속도·규모에서 작동하지 않으므로 **자동화가 필수**다. ③ 탐지·수정보다 **자동화된 보호 장치를 통한 예방**을 우선하고, 문서·감사 추적을 규제 검토의 핵심 아티팩트로 유지한다.

### 4.5 모범 사례 (Well-Architected Agentic AI Lens)

- 🏛️ **AGENTSEC05 관찰성·부인 방지**: BP01 포괄적 로깅·의사결정 아티팩트 저장(5요소 감사 로그 + 정책 결정 근거), BP02 분산 추적(`trace_id`로 다중 에이전트 상호작용 추적). 부인 방지(non-repudiation)는 "누가 승인했는가"를 증명하는 자격 증명 컨텍스트로 달성한다.
- 🏛️ **AGENTSEC07 인간 감독 보호·악성 에이전트 탐지**: BP04 행동 이상 탐지·에이전트 격리(높은 자율성의 예측 모니터링·드리프트 감지), BP05 정기 보안 평가·레드팀. 자율성이 높을수록 이 BP의 정교함을 올린다.
- 🏛️ **AGENTSEC08-BP02 민감 정보 출력 필터링**: 감사·데이터 보호 계층에서 PII·PHI가 로그·응답에 노출되지 않도록 필터링한다(파트 2의 가드레일과 결합).
- 🏛️ **AGENTSEC09 취약점 스캔·침투 테스트**: BP01 AI 기반 취약점 스캔, BP02 다중 에이전트 공격 시뮬레이션 침투 테스트, BP03 지속적 보안 검증·자동 교정, BP05 런타임 위협 탐지·보안 이벤트 상관·자동 교정. "배포 전 경계 테스트 + 지속적 운영 검증"이 이 질문의 실천이다.
- 🏛️ **AGENTOPS05-BP03 구조화 로깅·감사 추적 / AGENTOPS05-BP01 엔드투엔드 추적**: 운영 우수성 기둥과 교차 — 구조화 감사 로그가 규정 준수(보안)와 운영 가시성(운영 우수성)을 동시에 만족한다.
- 🏛️ **AGENTSUS03-BP03 에이전트·에이전틱 시스템의 포괄적 사양 유지**: 감사 추적·정책·정의 파일을 규제 검토의 지속 가능한 아티팩트로 유지한다.

## 파트 5. 프로덕션 구현 종합 체크리스트

파트 1~4의 제어를 프로덕션에 올릴 때 심층 방어 계층 순서로 점검합니다.

- **자율성 범위 판정 우선**: 에이전트를 Security Scoping Matrix 범위(1~4)로 판정하고, 범위에 비례해 이후 모든 제어의 정교함을 정한다. 자동화 이득이 위험을 정당화하지 못하면 범위를 낮춘다. (파트 1)
- **자격 증명 양방향 보호**: 인바운드(사용자→에이전트)와 아웃바운드(에이전트→리소스)를 모두 인증한다. 에이전트 전용 IAM 실행 역할을 사용자 권한과 분리한다. (파트 2)
- **정책을 결정적으로 시행**: 프롬프트(soft)가 아니라 Cedar 정책(hard)으로 경계를 강제한다. 규제 요구는 forbid, 업무 권한은 permit. 새 정책은 `LOG_ONLY`로 검증 후 `ENFORCE`로 승격한다. (파트 2)
- **네트워크 격리**: 다중 AZ 프라이빗 서브넷 + 보안 그룹 + NACL로 이중 방어. PrivateLink·VPC 엔드포인트로 트래픽을 AWS 백본에 가둔다. 엔드포인트 정책으로 최소 권한을 겹친다. 인터넷 없는 VPC는 ECR·S3·CloudWatch 엔드포인트 필수. (파트 3)
- **감사 추적 5요소**: 작업·추론·자격 증명·시간·세션을 모든 작업에 기록한다. 자격 증명 컨텍스트를 전 상호작용에 전파해 책임성 체인을 만든다. 자율성이 높을수록 예측 모니터링을 추가한다. (파트 4)
- **탐지보다 예방**: 위반을 사후 탐지하기보다 정책·경계로 예방한다. 배포 전 정책 검증·경계 테스트·감사 완전성·자격 증명 전파를 검증한다. (파트 2·4)
- **규정 준수는 자율성에 비례**: 범위가 커질수록 제어를 정교화하고, 수동이 아닌 자동화된 규정 준수 운영(대시보드·알림·보고서)을 구축한다. (파트 4)
