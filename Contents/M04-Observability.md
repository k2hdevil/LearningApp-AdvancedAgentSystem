## 학습 목표 및 선수 지식

**이 모듈을 마치면 다음을 수행할 수 있습니다.**

- 각 결정을 Well-Architected Agentic AI Lens 운영 우수성 기둥(AGENTOPS05·06)에 근거해 검증한다.

## 모듈 개요 — 이 모듈이 푸는 4가지 문제

에이전트는 자율적으로 추론하고 도구를 선택하며 여러 단계를 거칩니다. 입력→처리→출력이 명확한 기존 애플리케이션과 달리, 에이전트의 의사결정은 **블랙박스**가 되기 쉽습니다. 관찰성과 평가는 이 블랙박스를 열어 품질·신뢰·비용을 지키는 일이며, 결국 네 가지 질문에 답하는 과정입니다.

| 파트 | 핵심 질문 | 산출물 |
| --- | --- | --- |
| 1. 관찰 대상 | 에이전트 관찰은 기존과 *무엇이* 다른가? | 3핵심 요소 · 3계층 · 성숙도 진단 |
| 2. 계측·수집 | 원격 측정을 *어떻게* 계측·수집·내보내는가? | OTel/ADOT · 세션/트레이스/스팬 지표 |
| 3. 통합·경보·비용 | *어떻게* 엔터프라이즈와 통합·경보하고 비용을 관리하는가? | SIEM/APM 통합 · 루프 탐지 · 샘플링 |
| 4. 평가 | 확률적 에이전트 품질을 *어떻게* 평가하는가? | AgentCore Evaluations · 13지표 · 온라인/온디맨드 |

> **Well-Architected 설계 원칙(전제)**: Agentic AI Lens의 두 번째 설계 원칙은 *"모든 에이전트 행동을 엔드투엔드로 관찰·추적(End-to-end observability and traceability)"* 입니다. 자율 에이전트는 스스로 경로를 정하므로, 관찰성을 **나중에 붙이는 것이 아니라 처음부터 설계**해야 합니다. 이 모듈 전체가 이 원칙의 구체적 실천이며, 모듈 3(보안·감사)의 부인 방지 로깅과 직접 이어집니다. 운영 우수성 기둥은 관찰성(AGENTOPS05)과 테스트·평가·검증(AGENTOPS06)으로 이를 뒷받침합니다.

## 파트 1. 에이전트 관찰성의 본질 — 무엇을·왜 관찰하는가

### 1.1 해결할 문제

기존 애플리케이션 모니터링은 인프라 지표와 API 호출을 캡처하지만, 에이전트의 **추론 프로세스·도구 선택 로직·의사결정 패턴**은 놓칩니다. 에이전트는 능동적으로 행동합니다 — 독립적 의사결정, 목표 지향, 컨텍스트 이해, 경험 기반 적응. 이 자율성 때문에 세 가지 위험이 생깁니다.

- **신뢰성 격차**: 시스템은 "실행 중"이지만 컨텍스트 문제·도구 실패로 결과가 나쁠 수 있고, 표준 APM은 이를 못 본다.
- **비용 사각지대**: 에이전트 루프가 토큰·도구 호출을 반복해 비용을 폭증시켜도, 호출당 비용이 집계되지 않으면 드러나지 않는다.
- **디버깅 불가능성**: 다중 에이전트에서 "에이전트 B가 *왜* 그 방법을 선택했는가", "컨텍스트가 에이전트 간에 어떻게 흘렀는가"를 표준 도구로는 추적할 수 없다.

핵심은 **가시성 확보가 곧 신뢰·품질·비용 관리의 전제**라는 것입니다. 문제를 고객이 알려주기 전에 팀이 먼저 알아야 합니다.

> **💡 팁 — 사각지대 체감시키기**: "에이전트가 느리다/틀렸다는 불평을 받았을 때, 지금 도구로 원인을 30분 안에 찾을 수 있는가?"를 물으세요. 대부분 못 찾습니다. 기존 APM은 "무엇을 했다"는 보여주지만 "왜 그렇게 결정했다"는 못 봅니다. 이 격차가 이 모듈의 출발점입니다.

### 1.2 고려해야 할 기술·개념

#### (1) 관찰성의 3가지 핵심 요소

| 요소 | 답하는 질문 | 에이전트 맥락 예시 |
| --- | --- | --- |
| **지표(Metrics)** | *무엇이* 일어나는가(수치) | 도구 호출당 지연, 태스크당 토큰, 오류율 |
| **로그(Logs)** | *왜* 일어났는가(이벤트·컨텍스트) | 프롬프트 인젝션·훈련 데이터 손상 등 근본 원인 |
| **트레이스(Traces)** | 요청이 *어디를* 거쳤는가(여정) | 여러 도구·에이전트를 가로지르는 추론 경로 |

세 요소는 독립적으로도 유용하지만 **함께 쓸 때** 진가를 발휘합니다 — 지연 급증(지표) → 시간 초과 오류(로그) → 그 오류가 발생한 정확한 위치(트레이스).

#### (2) AgentCore 관찰성의 3계층 모델

AgentCore Observability는 세션 → 트레이스 → 스팬의 계층으로 서로 다른 세분성을 제공합니다.

```ascii
┌─ 세션 (최상위 / 전체 대화 컨텍스트)
│
├─ 트레이스 1 (요청-응답 주기)
│  │
│  ├──> 스팬 / 입력 구문 분석
│  ├──> 스팬 / LLM 계획
│  └──> 스팬 / 도구 실행
│
└─ 트레이스 n
   │
   ├──> 스팬 1
   └──> 스팬 n
```

| 계층 | 범위 | 답하는 질문 | 수집 방식 |
| --- | --- | --- | --- |
| **세션** | 전체 멀티턴 대화 | 사용자 참여는? 총 비용은? | AgentCore Runtime 자동 |
| **트레이스** | 단일 요청-응답 주기 | 이 요청이 왜 느린가? | ADOT 계측 필요 |
| **스팬** | 개별 작업 단위 | 어느 작업이 병목인가? | ADOT 계측(InvokeAgentRuntime 스팬 제외) |

#### (3) 에이전트 성능 지표 — 기존을 넘어서

에이전트 성능은 태스크 복잡성·컨텍스트 품질·협업 요구에 따라 크게 달라지므로, **정적 임계값이 아니라 적응형 기준선(baseline)** 이 필요합니다. 기존 시스템 지표를 넘어 추가로 관찰할 것:
- **추론 효율성**: 목표 달성에 필요한 단계 수·재시도
- **컨텍스트 사용률**: 토큰 예산 대비 실제 사용(모듈 2와 연계)
- **도구 선택 정확성**: 태스크에 맞는 도구를 골랐는가
- **협업 효율성**: 다중 에이전트 핸드오프의 효과

#### (4) 모니터링 성숙도 여정 — 4단계

조직의 관찰성 역량은 데이터 수집에서 사전 예방적 자동 해결로 진화합니다.

```ascii
1단계 / 기본 모니터링 (원격 측정 수집)
  │
  v
2단계 / 중간 모니터링 (분석 / 인사이트)
  │
  v
3단계 / 고급 관찰성 (상관관계 / 이상 탐지)
  │
  v
4단계 / 사전 예방적 관찰성 (자동 근본 원인 / 예방)
```

| 단계 | 답하는 질문 | AgentCore 지원 |
| --- | --- | --- |
| 1. 기본 | 무슨 일이 있었는가? | Runtime 자동 세션 지표 |
| 2. 중간 | 언제 일어났는가? | CloudWatch Observability 대시보드 |
| 3. 고급 | 왜 일어났는가? | 3계층 상관관계 + CloudWatch 이상 탐지 |
| 4. 사전 예방적 | 무엇이 일어날까? 어떻게 예방하나? | AgentCore Evaluations + 자동 문제 해결 |

> **💡 팁**: "모든 조직이 4단계부터 시작하지 않는다"를 강조하세요. 수강생에게 자기 조직이 몇 단계인지 자평하게 하고, 이 여정을 개선 로드맵으로 삼게 합니다. 목표는 즉시 4단계 도달이 아니라 현재 위치를 알고 다음 단계로 나아가는 것입니다.

### 1.3 구현 요건 및 절차 — 성숙도 진단에서 계층 선택까지

1. **성숙도 자평**: 조직이 4단계 중 어디인지 판정하고, 다음 단계로 갈 격차를 식별한다.
2. **핵심 요소 확보**: 지표·로그·트레이스를 모두 수집하는지 점검한다(하나라도 없으면 상관관계 분석 불가).
3. **관찰 계층 결정**: 답하려는 질문에 맞는 세분성을 고른다 — 용량 계획=세션, 요청 디버깅=트레이스, 병목 식별=스팬.
4. **적응형 기준선 설정**: 정적 임계값 대신 태스크 유형별 성능 기준선을 수립한다.

### 1.4 구현 예시

#### (1) 기존 vs 에이전틱 모니터링

```ascii
[기존 모니터링 (선형)]

사용자
  │
  v
애플리케이션 프론트엔드
  │
  v
입력 --> 처리 --> 출력


[에이전틱 시스템 (순환 / 비결정적)]

복잡한 요청
  │
  v
┌─ 에이전틱 루프 (응답 / 추론 / 도구 선택)
│
├──> 모델 호출
│
└──> 도구 및 리소스 (신뢰성 격차? 비용 사각지대?)
       루프와 도구는 양방향으로 오간다 (호출하고 결과를 받아 다시 추론)
```

#### (2) 적절한 세부 수준 선택 — 점진적 문제 해결

"에이전트가 느리다"는 불평을 받으면 상위(세션)에서 하위(스팬)로 드릴다운합니다.

| 지표 차원 | 세션 수준 | 트레이스 수준 | 스팬 수준 |
| --- | --- | --- | --- |
| 세분성 | 전체 대화 | 단일 요청-응답 | 개별 작업 |
| 지연 인사이트 | 호출당 평균 | 엔드투엔드 요청 시간 | 작업별 소요 |
| 사용 사례 | 용량 계획·참여 | 성능 최적화·디버깅 | 병목 식별·외과적 최적화 |
| 관찰 위치 | CloudWatch 대시보드 | CloudWatch Transaction Search | CloudWatch Logs |
| 자동 수집? | 예(Runtime 호스팅) | ADOT 필요 | ADOT 필요(InvokeAgentRuntime 제외) |

**드릴다운 예**: ① 세션 — 호출당 평균 3,200ms(높음!) → ② 트레이스 — 3,000ms 초과 트레이스의 40%가 web_search 관련 → ③ 스팬 — web_search의 HTTP 요청 하위 스팬이 2,400ms(네트워크 지연). 해결: 캐싱·더 빠른 API.

> **💡 팁**: "질문에 맞는 세분성을 쓰라"가 핵심입니다. 세션 지표로 "왜 느린가"를 답하려 하면 실패합니다. 각 수준이 서로 다른 질문에 답한다는 점을, 위 드릴다운 시나리오로 실습시키세요.

### 1.5 모범 사례 (Well-Architected Agentic AI Lens)

- 🏛️ **AGENTOPS05-BP01 엔드투엔드 추적·원격 측정**: 3계층(세션·트레이스·스팬) 모델이 이 BP의 직접 실천이다. 에이전트 행동을 개시부터 종료까지 추적 가능하게 한다.
- 🏛️ **AGENTOPS05-BP02 행동 패턴 모니터링·이상 탐지**: 적응형 기준선으로 정상 패턴을 학습하고 이탈을 탐지한다. 정적 임계값은 에이전트의 가변적 성능에 부적합하다.
- 🏛️ **AGENTOPS05-BP04 에이전트 워크플로 KPI 정의·추적**: 추론 효율·도구 선택 정확성·협업 효율을 KPI로 정의해 추적한다.
- 🏛️ **AGENTPERF01-BP02 포괄적 성능 원격 측정 / AGENTPERF01-BP03 엔드투엔드 지연 프로파일링**: 성능 효율 기둥과 교차 — 스팬 수준 지연 분해가 최적화 대상을 정확히 짚는다.
- 🏛️ **AGENTREL08-BP02 에이전트 처리 전반의 텔레메트리 추적**: 신뢰성 기둥과 교차 — 계층적 추적이 장애 지점 국소화와 복구를 지원한다.

## 파트 2. 계측과 원격 측정 수집 — OpenTelemetry와 3계층

### 2.1 해결할 문제

파트 1에서 "무엇을 관찰할지"를 정했다면, 이제 "그 데이터를 *어떻게* 생성·수집·내보낼지"가 문제입니다. 여기서 두 가지 위험을 피해야 합니다.

- **공급업체 종속(vendor lock-in)**: 특정 관찰성 플랫폼 전용으로 계측하면, 나중에 플랫폼을 바꿀 때 에이전트를 전부 다시 계측해야 한다.
- **계측 누락·과잉**: 세션 지표는 자동이지만 트레이스·스팬은 계측이 필요하고, 무엇을 자동으로 얻고 무엇을 직접 계측해야 하는지 혼동하면 사각지대나 낭비가 생긴다.

해법은 **업계 표준 OpenTelemetry(OTel)** 로 한 번 계측해 어디로든 내보내는 것입니다.

### 2.2 고려해야 할 기술·서비스

#### (1) OpenTelemetry(OTel)와 ADOT

OTel은 원격 측정 데이터를 위한 **공급업체 중립적 오픈 소스 표준**입니다. 3가지 신호 유형(트레이스·지표·로그)을 정의하며, **생성·수집·내보내기에만 집중**하고 스토리지·시각화는 전문 플랫폼에 맡깁니다. 이 관심사 분리 덕분에 "한 번 계측하면 어디든 전송"이 가능합니다.

```ascii
인프라 또는 애플리케이션 (AgentCore 에이전트)
  │
  │  원격 측정 생성
  v
OpenTelemetry / ADOT (계측 / 수집 / 내보내기)
  │
  │  내보내기(OTLP)
  v
관찰성 백엔드 (저장 / 처리)
  ^
  │  쿼리
  │
관찰성 프론트엔드 (대시보드 / 시각화)
```

AgentCore는 **AWS Distro for OpenTelemetry(ADOT)** 로 OTel과 기본 통합됩니다.
- **Runtime 호스팅 에이전트**: ADOT SDK가 자동 주입되어 **계측 코드 없이** 원격 측정이 CloudWatch로 전달됩니다. CloudWatch Transaction Search가 기본 활성화됩니다.
- **비-Runtime 에이전트**(Lambda·EC2 등): ADOT SDK를 코드에 추가하고 OTLP 내보내기 환경 변수를 구성합니다.

두 이점: ① 공급업체 종속 없음(수집기만 재구성하면 플랫폼 전환), ② 미래 대비(새 플랫폼도 OTel 표준을 지원).

#### (2) 3계층별 지표 — 자동 vs 계측 필요

| 계층 | 캡처 대상 | 기본 지표 | 내보내기 대상 |
| --- | --- | --- | --- |
| **세션** | 멀티턴 대화 | 세션 수, 호출 수, 총 소요, 오류율, 리소스 사용, 스로틀 | CloudWatch 지표(`bedrock-agentcore` 네임스페이스) — **자동** |
| **트레이스** | 단일 요청-응답 | 엔드투엔드 지연, 트레이스 상태, 요청 ID, 도구/LLM 호출 수, 토큰 사용 | CloudWatch Logs(`/aws/spans/default`) — **ADOT 필요** |
| **스팬** | 개별 작업 | 도구 호출, 추론 단계, 메모리 검색, 작업별 지연 | CloudWatch Logs(`/aws/spans/default`) — **ADOT 필요** |

> **💡 팁 — 자동/계측 경계 명확히**: 학습자가 가장 혼동하는 지점입니다. Runtime 호스팅이면 **세션 지표는 공짜**지만, **토큰 사용량은 세션 수준에서 자동 수집되지 않습니다**(ADOT 스팬 계측 + 집계 필요). "세션=자동, 트레이스·스팬=ADOT"를 반복해 각인시키세요.

#### (3) AgentCore 서비스별 관찰성

에이전트 애플리케이션 코드는 ADOT로 계측하지만, AgentCore 서비스들은 **로그 대상 구성**이나 **추적 활성화**만으로 자동 관찰성을 제공합니다.

| 서비스 | 관찰 대상 | 활성화 방법 |
| --- | --- | --- |
| **Memory** | 컨텍스트 저장/검색, 추출·통합, 오버플로 | 로그 대상 구성 |
| **Gateway** | 도구 연결·API 성능, 대상 실행 시간, 인증 실패 | 로그 대상 구성 |
| **Code Interpreter** | 코드 실행·샌드박스 성능, 세션 수명, CPU/메모리 | 로그 대상 구성 |
| **Browser** | 웹 자동화 세션, 수동 개입 이벤트, 장기 세션 | 로그 대상 구성 |
| **Policy** | 허용/거부 결정, 불일치 정책, 적용 모드 | Gateway 추적 활성화 |
| **Identity** | 워크로드 토큰, OAuth2 토큰 획득, 실패율 | 로그 대상 구성 |
| **Evaluations** | 13개 평가기 점수, 품질 회귀, 추세 | 평가 작업 구성 |

> **💡 팁 — 계측 vs 구성**: "ADOT는 *에이전트 애플리케이션 코드*를 계측할 때만 필요합니다. Memory·Gateway 등 서비스는 로그 대상만 구성하면 자동으로 스팬·로그를 내보냅니다." 이 구분을 놓치면 학습자가 모든 것에 ADOT가 필요하다고 오해합니다. Policy 지표는 모듈 3의 부인 방지 로깅과 직접 연결된다는 점도 짚어주세요.

### 2.3 구현 요건 및 절차

**A. 계측 설정 (호스팅 모델에 따라)**
1. **Runtime 호스팅**: 별도 작업 없음. ADOT 자동 주입 + Transaction Search 기본 활성화 → CloudWatch로 자동 전송(비활성화 불가).
2. **비-Runtime 호스팅**: ADOT SDK를 코드에 추가 → OTLP 엔드포인트·헤더 환경 변수 구성 → (원하면) `DISABLE_ADOT_OBSERVABILITY=true`로 CloudWatch 내보내기 차단 후 서드파티로만 전송.

**B. 트레이스·스팬 활성화**
1. **CloudWatch Transaction Search 활성화**(일회성 설정).
2. **ADOT SDK 추가** + 모니터링할 작업에 **사용자 지정 스팬 생성**(도구 이름·파라미터·결과 등 메타데이터 포함).
3. LLM 스팬에 모델 이름·입출력 토큰 수·지연을 캡처(비용 추적).

**C. AgentCore 서비스 관찰성 구성**
1. 각 서비스 콘솔에서 **로그 대상**(CloudWatch Logs/S3/Firehose)을 리소스당 한 번 구성한다.
2. Policy는 Gateway 리소스에서 **추적을 활성화**한다.
3. 구성 후에는 서비스 스팬·로그가 자동 내보내진다(ADOT 불필요).

### 2.4 구현 예시

#### (1) 에이전트 트레이스 — OTel 형식

여행 계획 에이전트의 트레이스 예시입니다. 트레이스 ID로 CloudWatch·서드파티에서 검색하고, 세션 ID로 같은 대화의 다른 트레이스와 연결합니다.

```json
{
  "timestamp": "2025-08-07T14:30:22Z",
  "resource_arn": "arn:aws:bedrock-agentcore:us-east-1:123456789012:runtime/travel-agent",
  "session_id": "session-abc123",          // 같은 대화의 여러 트레이스를 묶는 키(멀티턴 컨텍스트)
  "trace_id": "160fc209c3befef4857ab1007d041db0",  // 이 상호작용의 고유 식별자(검색·상관관계용)
  "span_id": "81346de89c725310",
  "operation": "InvokeAgentRuntime",       // Runtime이 자동 생성하는 스팬(ADOT 불필요)
  "request_payload": {
    "prompt": "Plan a weekend trip to Seattle with hotel and restaurant recommendations"
  },
  "response_payload": {
    "message": "I'll help you plan your Seattle weekend...",
    "tools_used": ["weather_check", "hotel_search", "restaurant_finder"]  // 다단계 도구 오케스트레이션
  },
  "latency_ms": 3450,                       // 성능 모니터링·최적화의 기준 지표
  "account_id": "123456789012"
}
// 이 OTel 호환 JSON은 CloudWatch·Datadog·Splunk 어디로든 내보낼 수 있다(공급업체 중립).
// 사용자가 문제를 보고하면: session 검색 → 관련 trace → 어떤 도구를 언제 호출했는지 재구성.
```

#### (2) 서드파티 플랫폼으로 원격 측정 내보내기

Runtime 호스팅 에이전트에서 CloudWatch 대신 Datadog으로 보내는 예입니다.

```bash
# Runtime 호스팅 에이전트의 기본 ADOT(CloudWatch 자동 내보내기)를 끄고 직접 내보낸다
export DISABLE_ADOT_OBSERVABILITY=true                    # 기본 CloudWatch 내보내기 비활성화
export OTEL_EXPORTER_OTLP_ENDPOINT=https://api.datadoghq.com   # OTLP 수신 엔드포인트(대상 플랫폼)
export OTEL_EXPORTER_OTLP_HEADERS="dd-api-key=<YOUR_API_KEY>"  # 인증 헤더(API 키)
export OTEL_SERVICE_NAME=my-agent                         # 이 에이전트를 식별하는 서비스 이름
# 대안(이중 관찰성): ADOT를 끄지 않고 OpenInference/OpenLLMetry/OpenLIT 계측 라이브러리를 추가하면
#                    CloudWatch + 서드파티(Arize·LangSmith·Langfuse)로 동시에 내보낼 수 있다.
```

#### (3) 오류 시나리오 — 점진적 성능 저하(graceful degradation)

잘 설계된 에이전트는 도구 실패 시 전체 트레이스를 실패시키지 않고 복구합니다. 관찰성은 "무엇이 왜 실패했고 어떻게 복구했는가"를 스팬으로 드러냅니다.

| 스팬 | 결과 | 관찰 포인트 |
| --- | --- | --- |
| 입력 구문 분석(10ms) | 성공 | 의도·제약 추출 |
| LLM 계획(875ms) | 성공 | 웹 검색 도구 선택 |
| **도구 실행(5,012ms)** | **실패** | `error.type: InvocationError.Internal`, 5초 타임아웃 |
| LLM 복구(1,120ms) | 성공 | "검색 불가 → 기존 지식으로 대체 제안" |

- **트레이스 상태**: 도구 실패에도 에이전트가 복구했으므로 **성공**(사용자 경험 저하되었으나 중단 안 됨).
- **지연**: 7,017ms(평소의 3.2배) — CloudWatch에서 급증으로 관찰.
- **오류 지표**: 세션 수준 시스템 오류 +1. 도구 오류율 5% 초과 또는 지연 5,000ms 초과에 경보 설정 → 사전 예방 모니터링.

> **💡 팁**: 오류 관찰성의 핵심은 **사용자 오류(4xx)와 시스템 오류(5xx)를 구분**하고 **복구 패턴을 드러내는 것**입니다. "트레이스는 성공인데 그 안의 스팬은 실패"라는 미묘한 상태를, 위 표로 설명하세요. 이것이 모듈 1의 점진적 성능 저하 설계와 어떻게 연결되는지도 짚어주세요.

- 🏛️ **AGENTOPS05-BP01 엔드투엔드 추적·원격 측정**: OTel/ADOT 표준 계측으로 세션·트레이스·스팬을 일관 형식으로 수집한다. 공급업체 중립성이 표준화의 핵심이다.

- 🏛️ **AGENTOPS07-BP01 자동 대응·복구 메커니즘**: 점진적 성능 저하 관찰(도구 실패 → 복구)이 자동 복구 설계의 근거 데이터를 제공한다.

## 파트 3. 엔터프라이즈 통합·경보·비용 최적화

### 3.1 해결할 문제

원격 측정을 수집했다면(파트 2), 이제 프로덕션에서 그것을 **조직 전체와 통합하고, 문제에 경보하고, 비용을 통제**해야 합니다. 세 가지 실전 과제가 있습니다.

- **통합 격차**: 조직은 이미 SIEM·APM·로그 집계에 투자했는데, 에이전트 원격 측정이 이와 분리되면 통합 가시성을 잃는다.
- **경보 피로**: 에이전트의 정상적 탐색 행동과 실제 문제를 구분하지 못하는 임계값 경보는 하루 수천 개의 노이즈를 만들어 중요한 문제를 묻어버린다.
- **비용 폭주**: 에이전트 루프(순환 추론·반복 재시도)가 토큰·도구 호출을 폭증시키고, 모든 트레이스를 캡처하면 관찰성 자체가 큰 비용이 된다.

> **💡 팁 — 실제 사례로 문제 제기**: 소매업체가 에이전트 도입 후 하루 수천 경보로 팀이 마비된 사례, 금융사가 규제 기관에 에이전트 의사결정의 감사 가능 기록을 제공하지 못한 사례, 물류사가 에이전트 *간 경계*의 시스템 실패를 어느 에이전트 탓인지 못 짚은 사례를 던지세요. 기존 모니터링이 "명확한 서비스 경계"를 전제하는 반면 에이전트는 "유동적·협상된 책임"이라 사각지대가 생깁니다.

### 3.2 고려해야 할 기술·서비스

#### (1) 엔터프라이즈 통합 3가지 접근

```ascii
┌─ Runtime 호스팅 에이전트
│
├──> 1) 내장 통합 (기본값)
│       Amazon CloudWatch (기본 / 항상 전송)
│
└──> 2) 서드파티 계측 라이브러리
       │
       v
       ┌─ OTel Collector
       │  3) Collector 내보내기
       │
       ├──> Datadog
       ├──> Splunk
       └──> SIEM
```

| 접근 | 방식 | 언제 |
| --- | --- | --- |
| **① 내장 CloudWatch** | Runtime 호스팅 기본값, 자동 전송 | AWS 관찰성 스택 표준화 조직 |
| **② 서드파티 계측 라이브러리** | OpenInference·OpenLLMetry·OpenLIT를 ADOT와 병행 → 이중 관찰성 | AI 플랫폼(Arize·LangSmith)+AWS 동시 필요 |
| **③ OTel Collector 내보내기** | Collector가 CloudWatch에서 읽어 여러 플랫폼으로 전달 | 관찰성 도구가 여러 개인 복잡 환경 |

세 접근 모두 **OTLP 표준**을 쓰므로 아키텍처 종속이 없습니다. CloudWatch로 시작해 나중에 서드파티를 추가하거나 전환해도 에이전트를 다시 계측하지 않습니다. 네트워크 보안을 위해 원격 측정 트래픽에 **VPC 엔드포인트·PrivateLink**(모듈 3)를 적용합니다.

#### (2) 경보·알림 — 3계층 에스컬레이션

에이전트 실패는 미묘합니다(실행 중이지만 결과가 나쁨). 문제 유형에 따라 적절한 대상으로 라우팅합니다.

```ascii
계층 1 / 자동 응답 (컨텍스트 새로 고침 / 도구 재연결)
  │
  │  에스컬레이션
  v
계층 2 / 기술 팀 (성능 문제 / 시스템 진단)
  │
  │  에스컬레이션
  v
계층 3 / 비즈니스 이해관계자 (품질 문제 / 비즈니스 영향)
```

경보 상관관계가 분산 시스템의 관련 경보를 연결해 **증상이 아닌 근본 원인**을 짚습니다.

#### (3) 루프 탐지·비용 보호 경보

에이전트 루프는 프로덕션의 주요 위험입니다. 4범주 경보 전략으로 대응합니다.

| 범주 | 경보/제어 | 임계값 예시 |
| --- | --- | --- |
| **사전 예방적 방지** | 수명 주기 구성(유휴 타임아웃·최대 수명), 상태 확인 | 유휴 15분, 최대 8시간 |
| **루프 탐지** | 세션 지속 이상, 호출 급증, 반복 도구 패턴 | 30분 초과, 5분간 50회 초과, 동일 도구 10회 연속 |
| **비용 보호** | 토큰 임계값, 오류율, 스로틀 감지 | 기준선 2배, 5% 초과 |
| **응답 조치** | 자동 세션 종료, 경보 에스컬레이션, 회로 차단기 | SNS/PagerDuty, Systems Manager 자동 복구 |

#### (4) 비용 최적화 — 샘플링·계층형 보존

프로덕션에서 모든 트레이스를 캡처할 필요는 없습니다.

| 전략 | 구현 | 비용 영향 |
| --- | --- | --- |
| **샘플링** | 프로덕션 트래픽의 10~20% 평가 | 80~90% 감소 |
| **계층형 보존** | 7일 상세 · 30일 집계 · 1년 요약 | 60~70% 감소 |
| **헤드 기반 샘플링** | 트레이스 시작 시 규칙 기반(성공 10%·오류 100%) | 예측 가능한 비용 |
| **테일 기반 샘플링** | 완료 후 오류 기반 → 오류 트레이스 전량 유지 | 문제에 집중 |
| **로그 압축** | gzip 내보내기 | 대역폭 60~80% 감소 |

> **💡 팁 — 관찰성 비용도 관찰하라**: 개발 단계는 전체 계측으로 최대 가시성을 확보하고, 프로덕션 전환 시 샘플링을 도입하라고 안내하세요. Cost Explorer로 CloudWatch 비용을, 예산 경보로 초과를 감시합니다. "모든 원격 측정이 같은 가치를 갖지 않는다 — 예산을 가장 중요한 신호에 집중하라"가 원칙입니다.

### 3.3 구현 요건 및 절차

**A. 통합 접근 선택**
1. AWS 스택 표준화 → **내장 CloudWatch**(추가 구성 없음).
2. AI 전문 플랫폼 병행 → **서드파티 계측 라이브러리**(이중 관찰성).
3. 다중 관찰성 도구 → **OTel Collector**(여러 내보내기 대상 동시).

**B. 경보 구성**
1. **사전 예방 가드레일** 먼저: 수명 주기 구성(유휴·최대 수명)으로 루프·폭주를 원천 차단.
2. **루프 탐지 경보**: 세션 지속·호출 급증·반복 도구 패턴에 CloudWatch 경보 설정.
3. **비용 보호 경보**: 토큰 임계값·오류율에 경보 + 자동 세션 종료·회로 차단기 연결.
4. **에스컬레이션 라우팅**: 자동 응답(계층 1) → 기술 팀(계층 2) → 비즈니스(계층 3).

**C. 비용 최적화 적용**
1. 프로덕션에 **샘플링**(10~20%) 도입, 오류는 테일 기반으로 전량 유지.
2. **계층형 보존**으로 규정 준수(요약 1년)와 디버깅(상세 7일)을 동시 충족.
3. **엣지 집계**로 전송 전 전처리, **계층형 스토리지**로 과거 데이터 이동.

### 3.4 구현 예시

#### (1) CloudWatch 루프 탐지 경보

세션 지속 시간이 30분을 초과하면(루프 의심) SNS로 알림을 보내는 경보입니다.

```python
# 세션 지속 시간이 30분을 초과하면 알림 → 루프/폭주 조기 탐지
cloudwatch.put_metric_alarm(
    AlarmName='AgentLoopDetection',
    MetricName='Duration',
    Namespace='bedrock-agentcore',          # Runtime이 자동 발행하는 세션 지표 네임스페이스
    Statistic='Maximum',                    # 최대값 기준(가장 긴 세션 포착)
    Period=300,                             # 5분마다 평가 → 빠른 탐지
    EvaluationPeriods=1,                    # 1회 위반 시 즉시 경보
    Threshold=1800000,                      # 30분(밀리초). 일반 상호작용(수 분)을 크게 초과
    ComparisonOperator='GreaterThanThreshold',
    AlarmActions=['arn:aws:sns:region:account:alert-topic'],  # SNS→Slack/이메일/PagerDuty 라우팅
)
# 이 경보는 세션 지표(자동 수집)에 기반하므로 추가 계측이 필요 없다.
# 응답 조치(자동 세션 종료·회로 차단기)와 결합하면 사전 예방적 관찰성(성숙도 4단계)이 된다.
```

#### (2) 확장성 고려 — 선형 비용 증가 방지

파일럿에서 전사 배포로 확장할 때 비용이 선형으로 늘지 않게 합니다. **지능형 샘플링**(오류 전량·성공 저비율), **엣지 집계**(전송 전 전처리), **수평 스케일링**(컨테이너·Auto Scaling), **계층형 스토리지**(운영 데이터는 즉시 접근, 과거 데이터는 저비용 계층)를 조합합니다.

> **💡 팁**: 통합 접근 선택은 "정답"이 없고 **기존 인프라·배포 모델에 따라 달라진다**는 점을 강조하세요. Runtime 호스팅은 CloudWatch로 항상 전송(비활성화 불가)되므로, 서드파티는 "추가"이지 "대체"가 아닙니다(비-Runtime은 완전 제어 가능). 이 차이를 명확히 해야 학습자가 아키텍처를 올바르게 설계합니다.

## 파트 4. 에이전트 평가 — 확률적 품질의 체계적 측정

### 4.1 해결할 문제

관찰성이 "에이전트가 *무엇을 했는가*"를 보여준다면, 평가는 "에이전트가 *잘했는가*"를 판정합니다. 문제는 에이전트가 **확률적**이라는 데 있습니다. 기존 소프트웨어 테스트는 "같은 입력 → 같은 출력 → 정확 일치 → 통과/실패"를 전제하지만, 에이전트는 같은 입력에도 다르지만 모두 유효한 응답을 낼 수 있습니다.

| 기존 소프트웨어 테스트 | 에이전트 평가 |
| --- | --- |
| 결정적 동작 | 확률적 응답 |
| 정확한 출력 일치 | 여러 차원의 품질 평가 |
| 이진 통과/실패 | 다차원 점수 |
| 고정된 로직·규칙 | 컨텍스트 의존 추론 경로 |

따라서 정확 일치가 아니라 **여러 차원에 걸쳐 품질을 평가하는 프레임워크**가 필요하고, 그 판정자로 **LLM-as-judge(평가형 LLM)** 를 씁니다. 게다가 이 평가는 일회성이 아니라 **지속적**이어야 합니다 — 모델 업데이트·새 버전·프롬프트 수정·도구 변경 때마다 품질이 회귀할 수 있기 때문입니다.

**에이전트 실패는 파급됩니다.** 품질 실패(할루시네이션·잘못된 도구 선택)가 신뢰성 문제(컨텍스트 손실·보안 격차)로, 다시 비효율(높은 비용·지연)로 번지고, 종국에는 고객 신뢰를 잃습니다.

```ascii
1. 품질 실패 (할루시네이션 / 잘못된 추론과 도구 선택)
  │
  │  파급
  v
2. 신뢰성 문제 (컨텍스트 손실 / 보안 격차)
  │
  │  파급
  v
3. 비효율성 (높은 비용 / 지연)
  │
  │  파급
  v
고객 신뢰 상실
```

> **💡 팁 — "고객이 알려주면 이미 늦다"**: 최악의 시나리오는 에이전트가 오작동해 고객 불만이 쏟아진 *후에야* 개발자가 아는 것입니다. 실시간·지속 평가로 고객이 실패를 경험하기 전에 잡아야 합니다. "결정적 테스트로 충분하지 않은 이유"를 확률적 응답 예시로 체감시키세요.

### 4.2 고려해야 할 기술·서비스

#### (1) AgentCore Evaluations 개요

에이전트 성능 평가를 위한 완전관리형 서비스로, AgentCore Observability와 통합됩니다. 자체 평가 인프라를 구축할 필요가 없습니다.
- **13개 내장 평가기**: 정확성·유용성·관련성·안전성 등 일반 품질 차원을 즉시 사용(최적화된 프롬프트·모델로 사전 구성, 수정 불가).
- **사용자 지정 평가기**: 도메인별 품질 지표를 직접 정의(예: HIPAA 준수, 금융 고지 사항).
- **통합 대시보드**: CloudWatch에서 점수·추세·개별 상호작용을 관찰성 인사이트와 함께 확인.
- **프레임워크 무관**: LangGraph·Strands·LlamaIndex 등 OTel 트레이스를 생성하는 어떤 프레임워크와도 작동.

```ascii
사용자
  │
  v
에이전트 (Runtime / Gateway / Memory)
  │
  │  OTel 트레이스
  v
┌─ AgentCore Observability
│
└──> AgentCore Evaluations (지표별 LLM 심판 호출)
       결과 + 심판 설명을 Observability 로 되돌려 준다

┌─ 에이전트 소유자
│
├──> AgentCore Evaluations 에 평가기 구성
└──> AgentCore Observability 에서 모니터링과 평가
```

핵심은 **에이전트 코드를 변경하지 않는다**는 것입니다. 이미 관찰성을 위해 수집하는 트레이스에 품질 점수를 얹을 뿐이며, 평가는 서비스 측(AWS 관리)에서 수행됩니다.

#### (2) 3가지 세분성 수준과 13개 지표

평가도 관찰성처럼 세션·트레이스·스팬 세분성에서 작동합니다.

```ascii
세션 -- 목표 성공률 (1)
  │
  v
트레이스 -- 정확성 / 충실도 / 유용성 / 관련성 / 간결함 / 일관성 /
            지침 준수 / 거절 / 유해성 / 고정관념 (10)
  │
  v
스팬 -- 도구 선택 / 파라미터 선택 정확성 (2)
```

| 수준 | 답하는 질문 | 지표 |
| --- | --- | --- |
| **세션** | 에이전트가 전체 목표를 달성했는가? | 목표 성공률 |
| **트레이스** | 응답이 유용·정확·안전한가? | 정확성·충실도·유용성·관련성·간결함·일관성·지침 준수 + (안전) 거절·유해성·고정관념 |
| **스팬** | 도구를 제대로 썼는가? | 도구 선택 정확성·파라미터 선택 정확성 |

#### (3) 두 가지 평가 모드 — 온디맨드 vs 온라인

| 항목 | 온디맨드 평가 | 온라인 평가 |
| --- | --- | --- |
| 실행 | 동기식, 개발자 시작 | 비동기식, 자동 |
| 사용 사례 | 배포 전 테스트, CI/CD 게이트 | 프로덕션 모니터링 |
| 범위 | 특정 트레이스·스팬 | 샘플링된 라이브 트래픽(10~20%) |
| 피드백 | 즉각적 | 대시보드 기반 |
| 언제 | 개발·테스트·디버깅 | 프로덕션·추세 분석 |

실제로는 **둘 다** 씁니다 — 개발·CI/CD에서 온디맨드, 배포 후 온라인.

#### (4) 보강 — 평가를 넘어선 "테스트" 계층

> **🏛️ 심화 보강 — 다층 테스트 프레임워크 (AGENTOPS06-BP01)**: AgentCore Evaluations는 *품질 평가*에 강하지만, Well-Architected는 그 앞단에 **테스트 피라미드**를 둘 것을 권합니다 — 단위(unit) → 통합(integration) → 엔드투엔드(end-to-end) → **섀도(shadow)** 테스트. 특히 섀도 테스트는 새 버전을 프로덕션 트래픽에 *영향 없이 병렬 실행*해 실제 트래픽으로 검증합니다. 온디맨드 평가를 CI/CD 게이트로 쓰고, 섀도 테스트로 배포 전 실트래픽 검증을 더하면 회귀를 사용자 도달 전에 막습니다. (AgentCore Evaluations는 벤치마크 데이터세트를 직접 지원하지 않으므로, 데이터세트 기반 평가가 필요하면 [Strands Evaluations](https://strandsagents.com/latest/documentation/docs/user-guide/evals-sdk/quickstart/)를 병행 고려)

### 4.3 구현 요건 및 절차

**A. 평가기 선택**
1. **내장 평가기 우선**: `Builtin.Correctness`·`Builtin.Helpfulness` 등으로 시작한다(일관·신뢰, 수정 불가).
2. **사용자 지정 평가기는 갭이 있을 때만**: 내장으로 못 다루는 도메인 요구(규정 준수·범위 준수)에 한해 생성한다.

**B. 사용자 지정 평가기 생성 — 4요소**
1. **평가 지침**(프롬프트): `{context}`·`{agent_response}`·`{available_tools}` 자리 표시자로 평가 방법을 기술(수준별로 접근 가능한 자리 표시자가 다름).
2. **평가자 모델**: Bedrock 모델 선택(복잡 추론=Claude, 간단=소형). 일관성 위해 낮은 온도.
3. **채점 스키마**: 최대 20개 레벨의 개별 척도(숫자·문자열) + 각 레벨 레이블·설명.
4. **평가 수준**: 세션/트레이스/스팬 중 지정.

**C. 모드별 운영**
1. **온디맨드**: 테스트 쿼리로 에이전트 호출 → 트레이스 ID를 평가 서비스에 전달 → 몇 초 내 점수·설명. CI/CD에서 점수가 임계값 미만이면 배포 차단.
2. **온라인**: 에이전트 엔드포인트·평가기(최대 10개)·샘플링 비율을 구성 → 프로덕션 트래픽을 백그라운드 자동 평가 → 대시보드에서 회귀·저점수 세션 조사.

### 4.4 구현 예시

#### (1) 사용자 지정 평가기 생성 — 구매 의도 탐지

```python
from agentcore_evaluation import EvaluationClient  # AgentCore 스타터 도구 키트

client = EvaluationClient()                          # 평가 서비스와 통신하는 클라이언트

evaluator = client.create_evaluator(
    name="purchase-intent-detector",
    # ① 평가 지침: {context}·{agent_response} 자리 표시자는 평가 시 실제 트레이스로 채워짐
    evaluation_instructions=(
        "Analyze {context} and {agent_response} to determine purchase intent "
        "based on pricing questions, availability, shipping inquiries, or buying signals."
    ),
    evaluator_model="amazon.nova-pro-v1:0",          # ② 평가자(심판) 모델
    inference_config={"temperature": 0.1, "top_p": 0.9},  # 낮은 온도 → 일관된 채점
    # ③ 채점 스키마: 각 레벨에 레이블·설명을 줘 심판이 일관되게 점수 부여
    scoring_schema={
        "0.0": {"label": "No purchase intent", "description": "No indication of purchase interest"},
        "0.5": {"label": "Browsing", "description": "Some interest but not ready to purchase"},
        "1.0": {"label": "Clear purchase intent", "description": "Strong readiness to purchase"},
    },
    evaluation_level="Session",                      # ④ 평가 수준(세션 전체 대화 기준)
)
# 활용 예 — 'Scope Adherence'(범위 준수) 평가기: 날씨·계산 전용 에이전트가 지리 질문에 답하면
#           사실이 맞더라도 '범위 위반'으로 낮은 점수를 줘 경고 → 비즈니스 규칙을 평가에 인코딩.
```

#### (2) 온라인 평가 구성 — 프로덕션 지속 모니터링

```python
from agentcore_evaluation import EvaluationClient

client = EvaluationClient()

# 내장 + 사용자 지정 평가기를 함께 사용해 프로덕션 트래픽을 자동 평가
online_config = client.create_online_evaluation(
    agent_endpoint="arn:aws:bedrock:us-east-1:123456789012:agent/my-agent",  # Runtime 엔드포인트
    evaluators=["Builtin.Helpfulness", "purchase-intent-detector"],  # 내장+사용자지정 혼용 가능
    sampling_rate=0.1,                               # 트래픽의 10%만 평가 → 비용 관리
)
# 동작: 사용자 상호작용 → 트레이스 생성 → 서비스가 10% 샘플링해 비동기 평가(UX 영향 없음)
#       → CloudWatch 대시보드에 집계 점수·시계열·저점수 세션 표시.
# 피드백 루프: 배포 → 모니터링 → 저점수로 문제 식별 → 근본 원인 조사(트레이스) → 개선 → 재배포.
```

#### (3) 내장 평가기로 회귀 진단

`Builtin.ToolSelectionAccuracy`(스팬 수준)가 도구 선택 정확도를 측정합니다. 기준선 **0.91**(91% 정확)에서 배포·모델 업데이트 후 **0.30**으로 급락하면, 대시보드가 즉시 중대 문제로 표시합니다 — 에이전트가 전문 도구 대신 일반 검색을 고르고 있다는 신호입니다. 기준선이 있어야 이 회귀를 "무엇이 잘못됐는지"까지 진단할 수 있습니다.

> **💡 팁 — 내장 먼저, 사용자 지정은 갭에만**: 학습자가 처음부터 사용자 지정 평가기를 만들려 하면 말리세요. 내장 13개로 대부분 커버되고, 사용자 지정은 "규정 준수·범위 준수"처럼 도메인 특수 요구에만 씁니다. 온디맨드(개발·CI/CD)와 온라인(프로덕션)을 *둘 다* 쓴다는 점, 온라인은 반드시 샘플링(10~20%)한다는 점을 강조하세요.

### 4.5 모범 사례 (Well-Architected Agentic AI Lens)

- 🏛️ **AGENTOPS06-BP02 지속적 에이전트 성능 평가·추적**: 온라인 평가가 이 BP의 직접 실천이다. 프로덕션 트래픽을 지속 평가해 회귀를 사용자 도달 전에 잡는다.
- 🏛️ **AGENTOPS06-BP01 다층 테스트 프레임워크**: 온디맨드 평가를 CI/CD 게이트로, 섀도 테스트로 실트래픽 검증을 더한다(위 심화 보강). LLM-as-judge가 비결정적 출력의 시맨틱 평가를 가능하게 한다.
- 🏛️ **AGENTOPS06-BP03 SME 주도 검증·비즈니스 승인 워크플로**: 사용자 지정 평가기(규정 준수·도메인 품질)가 SME 지식을 평가 기준으로 인코딩한다. 고위험 변경은 SME·비즈니스 오너 검토로 라우팅한다.
- 🏛️ **AGENTOPS02-BP04 지속적 개선 피드백 제어 루프**: 온라인 평가 → 저점수 진단 → 프롬프트·도구·데이터셋 갱신 → 재배포의 피드백 루프가 이 BP다.
- 🏛️ **AGENTREL05-BP02 평가 기반 개선 주기 / AGENTREL05-BP03 실제 정보에 인지 근거**: 신뢰성 기둥과 교차 — 충실도·정확성 평가가 할루시네이션을 잡아 근거를 실제 정보에 고정한다.

## 파트 5. 프로덕션 구현 종합 체크리스트

파트 1~4를 프로덕션에 올릴 때 관찰성 성숙도 순서로 점검합니다.

- **성숙도 진단 우선**: 조직이 4단계 중 어디인지 판정하고, 다음 단계로 갈 격차를 로드맵으로 만든다. 목표는 즉시 4단계가 아니라 다음 단계로의 이동이다. (파트 1)
- **3핵심 요소·3계층 확보**: 지표·로그·트레이스를 모두 수집하고, 답하려는 질문에 맞는 세분성(세션/트레이스/스팬)을 쓴다. (파트 1)
- **관찰성 우선 설계**: 시스템이 단순할 때 OTel/ADOT 계측을 심는다(나중 추가보다 쉽다). Runtime 호스팅은 세션 지표 자동, 트레이스·스팬은 ADOT 계측. (파트 2)
- **서비스 관찰성 구성**: Memory·Gateway·Code Interpreter·Browser·Identity는 로그 대상 구성, Policy는 추적 활성화, Evaluations는 평가 작업 구성. (파트 2)
- **엔터프라이즈 통합**: 배포 모델·기존 인프라에 맞는 접근(내장 CloudWatch / 서드파티 계측 / OTel Collector)을 고른다. OTLP 표준이라 나중 전환이 자유롭다. (파트 3)
- **경보·비용 가드레일**: 수명 주기 구성으로 루프를 원천 차단하고, 루프 탐지·비용 보호 경보 + 자동 세션 종료·회로 차단기를 건다. 프로덕션은 샘플링(10~20%)·계층형 보존으로 비용을 관리한다. (파트 3)
- **지속 평가**: 내장 평가기로 시작하고 도메인 갭에만 사용자 지정 평가기를 만든다. 온디맨드(CI/CD 게이트·섀도 테스트)와 온라인(프로덕션 샘플링)을 함께 쓴다. (파트 4)
- **피드백 루프**: 평가 저점수 → 트레이스로 근본 원인 조사 → 프롬프트·도구·데이터셋 개선 → 재배포를 지속한다. (파트 4)
