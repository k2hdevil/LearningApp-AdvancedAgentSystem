## 슬라이드 3. 에이전틱 시스템에서는 각 상호 작용에 따라 컨텍스트가 누적됩니다. 효과적인 컨텍스트 관리는 에이전트의 지식 및 성과를 결정하는 중요한 요소가 됩니다.

> **강사용 노트**
>
> 컨텍스트 엔지니어링을 프롬프트 엔지니어링보다 광범위한 분야로 정립하여 적절한 범위를 설정합니다.
>
> 예시 질문: "LLM이 컨텍스트를 파악해야 한다고 생각하는 몇 가지 상황은 무엇입니까?"

> **수강생용 노트**
>
> 컨텍스트 엔지니어링은 기존의 프롬프트 엔지니어링에서의 근본적인 전환을 의미합니다. 개별 프롬프트를 작성하는 것이 아니라 에이전트가 작동하는 전체 정보 환경을 설계하는 것입니다. 프로덕션 시스템에서는 에이전트가 여러 번 대화를 주고받는 상호 작용을 통해 컨텍스트가 빠르게 누적되므로 컨텍스트 관리가 에이전트 인텔리전스의 제한 요소가 됩니다.

## 슬라이드 4. 프롬프트부터 프로덕션까지

- AI 엔지니어링의 진화
- 프롬프트 엔지니어링
- 지식 추가
- RAG
- 도구 및 자율성 추가
- 에이전트
- 대규모 프로덕션
- 컨텍스트 엔지니어링

> **강사용 노트**
>
> 수강생이 진화 과정을 구체적으로 이해할 수 있도록 각 진화 단계의 예시를 사용합니다.
>
> 각 단계는 이전 기능을 대체하는 것이 아니라 이를 기반으로 구축된다는 점을 강조합니다.
>
> 컨텍스트 엔지니어링을 프로덕션 ROI에 연결하여 조기에 비즈니스 관련성을 확립합니다.
>
> 컨텍스트 엔지니어링을 프로토타입과 프로덕션 시스템 간의 중요한 차별화 요소로 규정합니다.

> **수강생용 노트**
>
> AI 엔지니어링은 여러 단계를 거쳐 발전해 왔으며, 각 단계마다 새로운 기능 및 복잡성이 추가되었습니다. 먼저, 모델로부터 양질의 응답을 얻을 수 있도록 최적의 프롬프트를 작성하기 위한 프롬프트 엔지니어링에서 시작했습니다. 다음에는 훈련 데이터의 한계를 넘어 확장할 수 있도록 지식 기반 접근 기능을 추가한 검색 증강 생성(RAG)이 발표되었습니다. 그런 다음, 에이전트가 등장하여 단순히 응답을 생성하는 데 그치지 않고 조치를 취할 수 있는 도구 및 자율성을 확보하게 되었습니다. 하지만 프로토타입에서 대규모 프로덕션 시스템으로 전환하려면 이러한 기능 이상이 필요합니다. 컨텍스트 엔지니어링은 에이전트가 작동하는 전체 정보 환경을 관리하는 데 초점을 맞춘 현재의 최첨단 분야입니다. 단순히 도구 또는 지식을 갖추는 것만 중요한 것이 아니라 모든 상황 정보를 조율하여 측정 가능한 ROI를 창출하는 안정적이고 비용 효율적인 프로덕션 시스템을 구축하는 것이 중요합니다. 진화 단계를 거칠 때마다 기능도 개선되었지만 복잡성 또한 증가했는데, 이러한 복잡성을 엔터프라이즈 규모에서 관리하는 방법이 바로 컨텍스트 엔지니어링입니다.

## 슬라이드 5. 컨텍스트 이해

- 메시지 배열에서
- 가장 중요한 것은 컨텍스트

> **강사용 노트**
>
> 복잡한 자율 루프를 보여주기 전에 간단한 메시지 배열 예제로 시작합니다.
>
> 메시지가 배열에 누적될 때 실시간으로 발생하는 토큰 계산을 시연합니다.
>
> 어떻게 각 상호 작용에 따라 여러 메시지(사용자, 어시스턴트, 도구 호출, 도구 결과)가 추가되는지 설명합니다.
>
> 장시간 대화 중에 컨텍스트 윈도우가 채워지는 실제 사례를 소개합니다.
>
> 자율 에이전트가 확장된 워크플로를 실행하는 실제 시나리오와 연결합니다.

> **수강생용 노트**
>
> 에이전틱 시스템에서 컨텍스트는 각 요청과 함께 언어 모델로 전송되는 메시지 배열에 포함된 모든 것을 의미합니다. 상호 작용이 발생할 때마다 사용자 입력, 어시스턴트 응답, 도구 호출, 도구 결과 등 여러 메시지가 추가됩니다. 시스템이 장기간 독립적으로 작동하는 자율 에이전트 루프에서는 에이전트가 문제를 파악하고 도구를 간접적으로 호출하고 결과를 처리함에 따라 메시지 배열이 빠르게 증가합니다. 컨텍스트 윈도우는 크기 제한이 있고 API 직접 호출 시마다 토큰을 소비하므로 이러한 누적 패턴을 이해하는 것이 중요합니다. 이는 기술적 제약과 비용 문제를 야기하므로 전략적인 최적화 접근 방식이 필요합니다.

## 슬라이드 6. 컨텍스트 범주

- 시스템
- 검색됨
- 도구
- 메모리
- 사용자

> **강사용 노트**
>
> 시스템 컨텍스트 문제: 일관되지 않은 행동, 제약 조건 무시
>
> AgentCore 서비스와 연결할 기회
>
> 검색된 컨텍스트 문제: 잘못된 정보, 오래된 데이터, 관련 없는 결과
>
> 도구 컨텍스트 문제: 잘못된 도구 선택, 잘못된 파라미터, 옵션 혼동
>
> 메모리 문제: 중요한 정보를 망각하거나 관련 없는 데이터를 유지
>
> 사용자 컨텍스트 문제: 프로필 문제, 멀티 테넌트 시스템에서 자격 증명 혼동

> **수강생용 노트**
>
> 일반적으로 에이전틱 시스템의 컨텍스트는 5가지 범주로 구분되는데, 각 범주는 특정 용도로 사용되며 서로 다른 최적화 접근 방식을 필요로 합니다. 시스템 컨텍스트는 에이전트 행동을 안내하는 시스템 프롬프트를 통해 역할 정의 및 행동 지침을 제공합니다. 검색된 컨텍스트는 RAG 구현 및 Amazon Bedrock Knowledge Bases와 같은 지식 기반을 통해 외부 지식을 제공합니다. 도구 컨텍스트는 에이전트 기능을 확장하는 API 연결 및 MCP 도구를 통해 사용 가능한 기능을 정의합니다. 메모리는 AgentCore Memory에서 관리하는 단기 세션 스토리지 및 장기 세션 간 지속성을 통해 연속성을 유지합니다. 사용자 컨텍스트는 즉각적인 프롬프트, 사용자 프로필 정보, 자격 증명 데이터 등 현재 상호 작용 세부 정보를 캡처합니다. 이러한 범주는 에이전트 실패 문제 해결을 위한 진단 프레임워크를 구성합니다. 시스템 컨텍스트 문제는 일관되지 않은 행동으로 드러나고, 검색된 컨텍스트 문제는 잘못된 정보를 표시하고, 도구 컨텍스트 문제는 잘못된 도구 선택으로 나타나고, 메모리 문제는 연속성 문제를 야기합니다. 또한 사용자 컨텍스트 문제는 일반적으로 멀티 테넌트 환경에서의 프로필 또는 자격 증명 혼동과 관련이 있습니다.

## 슬라이드 8. 컨텍스트 윈도우 관리

**다이어그램 (D2)**

```d2
direction: right
sources: "컨텍스트 소스" {
  sys: 시스템
  ret: 검색됨
  tool: 도구
  mem: 메모리
  usr: 사용자
}
mgmt: 컨텍스트 관리
llm: "LLM 컨텍스트 윈도우"
sources -> mgmt -> llm
```

- 시스템
- 검색됨
- 도구
- 메모리
- 사용자
- 컨텍스트 관리
- LLM
- 컨텍스트 윈도우
- 시스템
- 메모리
- 사용자

> **강사용 노트**
>
> 인간의 작업 기억 한계에 대한 비유로 시작하여 개념적 토대를 마련합니다.
>
> 컨텍스트 제한을 실제 프로덕션 시스템 제약 조건과 연결합니다.

> **수강생용 노트**
>
> 컨텍스트 윈도우는 AI 에이전트가 단일 상호 작용에서 처리할 수 있는 최대 정보량을 정의합니다. 메모리를 추가할 수 있는 기존 애플리케이션과 달리 AI 에이전트는 현재 질문, 이전 메시지, 코드 조각, 시스템 정보를 포함하는 고정된 토큰 제한 내에서 작동합니다. 이러한 제한은 에이전트 성능, 응답 품질, 운영 비용에 직접적인 영향을 미치는 엄격한 경계를 형성합니다. 컨텍스트를 유한한 리소스로 이해하면 실제 제약 조건에서도 신뢰할 수 있게 작동하는 보다 효율적인 에이전트 시스템을 설계하는 데 도움이 됩니다.

## 슬라이드 9. 예시: 고객 서비스 AI 에이전트

- 시나리오: 한 고객 서비스 AI 에이전트는 200,000개 토큰 컨텍스트 윈도우가 있는 LLM을 사용하여 복잡한 기술 문의를 해결합니다.
- LLM
- 컨텍스트 윈도우
- 시스템
- 메모리
- 사용자
- 검색됨
- 고객의 상세한 아키텍처 설명
- 3가지 서비스의 오류 로그
- 관련 구성 파일
- 3가지 서비스의 오류 로그
- 세션별 메모리
- 사용자의 현재 프롬프트
- 상세한 시스템 지침
- 토큰 75,000개
- 토큰 85,000개
- 토큰 10,000개
- 토큰 25,000개
- 총 토큰 195,000개

> **강사용 노트**
>
> 각 컨텍스트 구성 요소를 분석하고 각각 어떤 전략을 나타내는지 설명합니다.
>
> 절충점에 대해 논의: 검색된 정보가 증가하면 어떻게 됩니까? 우선순위는 어떻게 지정합니까?
>
> 실제 제약 조건과 연결: 대부분의 프로덕션 시스템은 컨텍스트 제한에 가깝게 작동합니다.

> **수강생용 노트**
>
> 이 고객 서비스 시나리오는 컨텍스트 엔지니어링 전략이 실제에서 어떻게 함께 작동하는지 보여줍니다. 이 에이전트는 200,000개 토큰 컨텍스트 윈도우 내에서 작동하면서 복잡한 기술 문의를 해결해야 합니다. 컨텍스트는 검색된 정보용 토큰 75,000개, 세션별 메모리용 토큰 85,000개, 현재 사용자 프롬프트용 토큰 10,000개, 시스템 지침용 토큰 25,000개 등 전략적으로 구성됩니다. 토큰이 총 195,000개 할당되고 나머지 5,000개는 에이전트의 응답 생성을 위한 토큰 버퍼로 남겨둡니다. 이 예시는 프로덕션 시스템에 필요한 중요한 균형, 즉 응답 용량을 유지하면서 컨텍스트 활용도를 극대화해야 하는 것을 잘 보여줍니다. 자체 에이전트 시스템을 설계할 때는 각 컨텍스트 구성 요소가 전체 토큰 예산에 어떻게 기여하는지 고려해야 합니다.

## 슬라이드 10. 계산상 한계 및 성능 영향

- 예시에서 대화가 이어지면서 로그, 스크린샷, 문제 해결 시도가 추가되어 컨텍스트 윈도우가 한계에 다다르면 어떻게 됩니까?
- 잠재적 영향은 다음과 같습니다.
- 성능 저하: 에이전트가 고객의 아키텍처에 대한 이전 세부 정보를 '망각'합니다.
- 우선순위 지정 문제: 응답 품질이 떨어집니다.
- 계산 속도 저하: 응답 시간이 증가합니다.

> **강사용 노트**
>
> 이 슬라이드를 이전 고객 서비스 에이전트의 시나리오와 직접 연결합니다(32,000개 토큰 제한에 육박하는 31,500개).
>
> 숨겨진 정보 검색 테스트로 로스트 인 더 미들(Lost in the Middle) 현상의 사례를 소개합니다.

> **수강생용 노트**
>
> 토큰 31,500개를 신중하게 할당한 고객 서비스 에이전트의 시나리오를 바탕으로, 추가적인 오류 로그, 스크린샷, 문제 해결 시도 등으로 대화가 이어진다고 상상해 보십시오. 컨텍스트 윈도우가 200,000개 토큰 제한에 가까워지면 3가지 중요한 효과가 나타납니다. 1번째, 새로운 정보가 이전의 중요한 세부 정보를 대체할 때 성능 저하가 발생합니다. 에이전트는 문제를 이해하는 데 필수적인 고객의 아키텍처 설명을 '망각'할 수 있습니다. 2번째, 에이전트가 경합하는 컨텍스트 요소(예: 원래 오류 로그 또는 새로운 문제 해결 시도) 중 하나를 선택해야 하기 때문에 우선순위 지정 문제가 발생합니다. 이러한 강제 선택 때문에 에이전트가 전체 컨텍스트를 사용할 수 없어 응답 품질이 저하됩니다. 3번째, 모델이 기술적으로 더 큰 컨텍스트 크기를 지원하더라도 컨텍스트가 커짐에 따라 처리 오버헤드가 증가하면서 계산 속도 저하가 발생합니다. 사용률이 최대 용량에 가까워질수록 성능이 저하됩니다. 일부 모델은 컨텍스트 크기가 증가하면 성능이 저하될 수 있습니다. 즉, 컨텍스트 윈도우를 늘린다고 성능 문제가 자동으로 해결되지 않습니다. 관련 정보를 세심하게 큐레이팅한 토큰 5,000개는 포괄적이지만 집중적이지 않은 설명서의 토큰보다 성능이 더 좋은 경우가 많습니다.
>
> 컨텍스트 최적화는 성능 외에도 경제성 측면에서 매우 중요합니다. 컨텍스트 파일은 실제 사용량과 관계없이 모든 요청에서 토큰을 소비하며, 토큰 요금은 입력 토큰과 출력 토큰 모두에 대해 부과됩니다. 매일 수천 개의 요청을 처리하는 엔터프라이즈 애플리케이션의 경우 비효율적인 컨텍스트 관리는 상당한 규모의 불필요한 비용을 초래합니다.

## 슬라이드 16. 입력 형식 최적화 전략

- 컨텍스트
- 데이터 구조
- 스키마 설계
- 콘텐츠 프루닝
- 형식 선택

> **강사용 노트**
>
> 개념 소개: '입력 형식 최적화'는 컨텍스트 최적화 프레임워크의 5번째 전략입니다.
>
> 중앙 컨텍스트 요소를 설명: 이 요소는 데이터가 소비되는 컨텍스트 윈도우를 나타냅니다. 목표는 입력되는 항목을 최적화하는 것입니다.
>
> 4가지 최적화 접근 방식을 각각 살펴봅니다.
>
> 형식 선택: 효율적인 데이터 형식(JSON, CSV, YAML 또는 최적화된 형식)을 선택합니다.
>
> 데이터 구조: 불필요한 필드를 제거하고, 중첩 구조를 평면화하고, 중복을 제거합니다.
>
> 스키마 설계: 짧은 필드 이름을 사용하고, 메타데이터를 최소화하고, 장황한 이름 지정을 방지합니다.
>
> 콘텐츠 프루닝: 컨텍스트로 전송하기 전에 관련 없는 데이터를 제거하고 불필요한 정보를 필터링합니다.
>
> TOON을 옵션으로 설정하는 데 사용합니다.

> **수강생용 노트**
>
> '입력 형식 최적화' 전략은 데이터가 컨텍스트 윈도우에 들어오기 전에 데이터를 최적화하여 토큰 소비를 줄이는 데 초점을 맞춥니다. 이 기초적인 최적화 전략은 다른 전략의 효과를 증폭합니다.
> 핵심 개념:
>
> 입력 최적화는 동일한 데이터가 형식 지정, 구조화 및 표시 방식에 따라 토큰 소비량이 다를 수 있다는 사실을 해결합니다. 데이터 파이프라인 초기에 입력을 최적화하면 기본 토큰 소비가 감소하여 모든 후속 최적화 전략(기록, 선택, 압축, 분리)의 효과가 증가합니다.
>
> 4가지 입력 최적화 접근 방식:
>
> 1. 형식 선택: 데이터 형식에 따라 동일한 정보라도 토큰 비용이 다릅니다. JSON, CSV, YAML, 그리고 TOON과 같은 특수 형식은 각각 다른 특징을 가지고 있습니다.
> - JSON: 구조화되었지만 장황함(따옴표, 대괄호, 쉼표로 인해 오버헤드 추가)
> - CSV: 테이블 형식 데이터에 적합한 간결한 구분 기호 기반 형식
> - YAML: 들여쓰기를 사용하여 사람이 읽을 수 있지만 토큰을 많이 소비할 수 있음
> - 최적화된 형식: 최상의 속성을 결합하는 하이브리드 접근 방식
>
> 2. 데이터 구조 최적화: 데이터 구성 방식은 토큰 소비에 영향을 미칩니다.
> - 현재 태스크에 필요하지 않은 불필요한 필드를 제거
> - 계층 구조가 필요하지 않은 경우 중첩 구조를 평면화
> - 레코드 전체에서 반복되는 중복 정보를 제거
> - 단순한 구조로도 충분할 때 복잡한 중첩된 객체를 단순화
>
> 3. 스키마 설계: 필드 이름 및 메타데이터는 토큰 수에 영향을 미칩니다.
> - 장황한 서술형 이름 대신 짧고 간결한 필드 이름을 사용
> - 태스크에 가치를 부가하지 않는 메타데이터를 최소화
> - 필드 이름에 중복되는 접두사 또는 접미사를 사용하지 않음
> - 토큰 효율성을 염두에 두고 스키마를 설계
>
> 4. 콘텐츠 프루닝: 모든 데이터가 모든 컨텍스트와 관련이 있는 것은 아닙니다.
> - 컨텍스트로 전송하기 전에 관련 없는 필드를 제거
> - 현재 태스크를 기반으로 불필요한 정보를 필터링
> - 에이전트의 목표에 기여하는 필수 데이터만 유지
> - 모든 데이터를 전송하는 대신 선택적 포함을 적용
>
> 다른 전략과의 통합:
>
> 입력 최적화는 다른 4가지 전략과 함께 작동하며 그 효과를 증폭합니다.
> - 기록 전략과 함께 사용: 외부 스토리지에 저장하기 전에 형식 및 구조를 최적화
> - 선택 전략과 함께 사용: 컨텍스트 요소를 선택할 때 효율적인 형식을 사용
> - 압축 전략과 함께 사용: 형식 최적화가 압축 효과 향상 가능
> - 분리 전략과 함께 사용: 에이전트마다 요구 사항에 따라 서로 다른 최적화된 형식 사용 가능
>
> 적용 시기:
> 컨텍스트 어셈블리 전의 데이터 파이프라인 초기에 입력 최적화를 적용합니다. 특히 다음과 같은 경우에 유용합니다.
> - 형식 선택이 토큰 소비에 상당한 영향을 미치는 구조화된 대규모 데이터세트
> - 스키마 최적화의 이점을 얻을 수 있는 반복적인 데이터 구조를 가진 시스템
> - 동일한 데이터가 여러 번 처리되는 애플리케이션(1번의 최적화로 여러 번 효과를 얻을 수 있음)
> - 토큰 효율성이 중요하고 모든 토큰이 중요한 시나리오

## 슬라이드 17. 예: TOON(Token-Oriented Object Notation: 토큰 지향 객체 표기법)

- Pretty JSON: 토큰 149개, 문자 461자
- {
- "context": {
- "task": "customer_support_session",
- "session_id": "sess_20250315_abc123",
- "timestamp": "2025-03-15T14:30:00Z"
- },
- "agents": [
- "billing_agent",
- "technical_agent",
- "shipping_agent"
- ],
- "conversations": [
- {
- "id": 1,
- "role": "user",
- "content": "I need help with my   order 45678",
- "agent": "billing_agent",
- "timestamp": "2025-03-15T14:31:00Z",
- "requiresResponse": true
- }
- ]
- }
- TOON: 토크 104개, 문자 319자(-30.2%)
- context:
- task: customer_support_session
- session_id: sess_20250315_abc123
- timestamp: "2025-03-15T14:30:00Z"
- agents[3]: billing_agent,technical_agent,shipping_agent
- conversations[1]{id,role,content,agent,timestamp,requiresResponse}:
- 1,user,I need help with my order 45678, billing_agent,"2025-03-15T14:31:00Z",true
- ©2026, Amazon Web Services, Inc. or its affiliates. All rights reserved.

> **강사용 노트**
>
> TOON을 형식 최적화를 위한 새로운 오픈 소스 옵션으로 제시합니다.
>
> 이는 1가지 기법을 강조하기 위한 것이지 규범적 권장 의도는 아닙니다.
>
> https://github.com/toon-format/toon - 수강생과 링크를 공유하십시오. https://toonformat.dev/
>
> 형식 최적화 옵션을 시각화하는 데 사용할 수 있는 훌륭한 데모 도구: https://www.curiouslychase.com/playground/format-tokenization-exploration?mode=preset&size=small-simple&structure=uniform-flat

> **수강생용 노트**
>
> TOON(Token-Oriented Object Notation: 토큰 지향 객체 표기법)은 새로운 오픈 소스 형식 최적화 기법으로, 형식 선택이 토큰 소비에 얼마나 큰 영향을 미칠 수 있는지 잘 보여줍니다. 여기서는 규범적 솔루션이 아니라 형식 최적화의 한 예로 제시됩니다. 형식 최적화에는 여러 가지 접근 방식이 있으며 TOON은 하나의 구체적인 구현일 뿐입니다.
> TOON의 역할:
> TOON은 기존 형식에서 최상의 특성을 결합하여 토큰 소비를 줄입니다.
> JSON: 구조화된 객체 인코딩 및 중첩된 데이터 표현을 유지합니다.
> CSV: 간결한 표현을 위해 구분 기호 기반 구분(배열에는 쉼표, 객체 속성에는 파이프)을 사용합니다.
> YAML: 가독성 및 논리적 그룹화를 위해 들여쓰기 기반 계층 구조를 사용합니다.
>
> 토큰 소비 감소 시연:
> 이 슬라이드 예제는 동일한 에이전트 세션 컨텍스트 데이터를 2가지 형식으로 보여 줍니다.
> JSON: 토큰 149개, 문자 461자
> TOON: 토큰 104개, 문자 319자
> 감소: 토큰 30.2% 감소, 문자 30.8% 감소
>
> 이러한 감소는 키 및 문자열 값 주위의 따옴표, 대괄호 및 중괄호, 속성 사이의 쉼표 등 JSON의 장황한 구문 오버헤드를 제거했기 때문입니다.
>
> TOON 형식 특징:
> 슬라이드의 예제를 보면 TOON은 몇 가지 기법을 사용합니다.
> 1. 계층 들여쓰기: YAML과 마찬가지로 중첩된 객체도 중괄호 대신 들여쓰기를 사용합니다.
> ```
> context:
> task: customer_support_session
> session_id: sess_20250315_abc123
> ```
> 2. 쉼표로 구분된 배열: 단순 배열은 CSV 스타일의 쉼표 구분을 사용합니다.
> ```
> agents[3]: billing_agent,technical_agent,shipping_agent
> ```
> 3. 간결한 객체 표기법: 객체 배열은 헤더 표기법을 사용하여 키를 나열한 다음 쉼표로 구분된 값을 나열합니다.
> ```
> conversations[1]{id,role,content,agent,timestamp,requiresResponse}:
> 1,user,I need help with my order 45678,billing_agent,"2025-03-15T14:31:00Z",true
> ```
>
> 4. 최소 인용: 모든 문자열이 아닌 인용이 필요한 값(예: 특수 문자가 포함된 타임스탬프)만 인용합니다.
>
> 형식 최적화가 중요한 경우:
>
> TOON과 같은 형식 최적화는 다음과 같은 경우에 가장 유용합니다.
> - LLM에 자주 전달되는 구조화된 대규모 데이터세트로 작업하는 경우
> - 동일한 데이터 구조가 여러 번 처리되는 경우(1번의 최적화로 여러 번 효과를 얻을 수 있음)
> - 토큰 효율성이 매우 중요하며 모든 토큰 소비 감소가 중요한 경우
> - 파이프라인의 데이터 직렬화를 제어할 수 있는 경우
>
> 중요한 고려 사항:
>
> TOON은 규범적 솔루션이 아니라 형식 최적화의 한 예로 제시됩니다. 형식 최적화는 다양한 구현이 가능한 전략입니다.
> - 테이블 형식 데이터에는 CSV를 사용할 수 있습니다.
> - 특정 사용 사례에 맞게 간결한 사용자 지정 형식을 사용할 수 있습니다.
> - 불필요한 공백을 제거하여 JSON을 최적화할 수 있습니다.
> - 스키마 설계를 사용하여 필드 이름을 단축할 수 있습니다.
>
> 핵심은 형식 선택이 토큰 소비에 영향을 미친다는 것이고, TOON은 이러한 최적화를 달성하기 위한 1가지 접근 방식을 보여줍니다. 특정 사용 사례, 데이터 특성, 시스템 요구 사항을 기반으로 형식 최적화 기술을 평가해야 합니다.
> 다른 전략과의 통합:
> 형식 최적화는 다른 컨텍스트 최적화 전략과 함께 작동합니다.
> 기록 전략과 함께 사용: 외부 스토리지에 저장하기 전에 형식을 최적화합니다.
> 선택 전략과 함께 사용: 컨텍스트 요소를 선택할 때 효율적인 형식을 사용합니다.
> 압축 전략과 함께 사용: 형식 최적화가 압축 효과를 향상할 수 있습니다.
> 분리 전략과 함께 사용: 에이전트마다 서로 다른 최적화된 형식을 사용할 수 있습니다.
>
> 목표는 데이터의 기본 토큰 소비를 줄여 모든 후속 최적화 전략의 효과를 증폭하는 것입니다.

- 런타임 상태 지속성

> **강사용 노트**
>

>
> 대화 상태 및 사용자 선호 사항에 대한 스키마 설계 패턴을 소개합니다.
>
> 외부 스토리지와 컨텍스트 토큰 간의 비용 절충을 계산하는 연습을 합니다.
>
> 검색 최적화 기법 및 인덱싱 전략을 살펴봅니다.

> **수강생용 노트**
>
> 컨텍스트 기록 전략은 외부 스토리지 시스템을 통해 접근성을 유지하면서 정보를 컨텍스트 윈도우 외부로 이동합니다. 이 접근 방식은 모든 콘텐츠를 활성 컨텍스트에 보관하는 대신 대화 기록, 사용자 선호 사항, 축적된 지식을 영구 스토리지에 저장합니다. AgentCore Memory는 단기 세션 스토리지 및 장기 세션 간 지속성을 위한 내장 기능을 제공합니다. 이 전략에서는 정보가 필요할 때 효율적으로 검색할 수 있도록 신중한 스키마 설계 및 인덱싱이 필요합니다. 성공 여부는 외부 스토리지 액세스 비용과 컨텍스트 윈도우 효율성 향상 간의 균형을 맞추는 데 달려 있습니다.

## 슬라이드 19. Amazon Bedrock을 사용한 프롬프트 캐싱

**다이어그램 (D2)**

```d2
direction: right
p1: "캐시 체크포인트가 포함된 프롬프트"
bedrock: "Amazon Bedrock (Amazon Nova 등)"
p2: "프롬프트 캐시를 사용하는 후속 프롬프트"
p1 -> bedrock: "1. 캐시 체크포인트 지정"
p2 -> bedrock: "2. 캐시 참조 (TTL 내)"
```

- 프롬프트 캐싱 사용 단계
- 지원되는모델 프롬프트에서캐시 체크포인트를지정합니다.
- TTL(Time To Live:유지 시간) 내에서추가 프롬프트 입력 시해당 캐시 체크포인트를참조합니다.
- Amazon Bedrock
- Amazon Nova
- 캐시 체크포인트가 포함된 프롬프트
- 프롬프트 캐시를 사용하는 후속 프롬프트

> **강사용 노트**
>
> 종종 동일하고 캐시 가능한 콘텐츠
>
> 시스템 프롬프트
>
> 사용자에 관계없이 동일한 HR 정책

> **수강생용 노트**
>
> 프롬프트 캐싱은 Amazon Bedrock의 지원되는 모델에서 모델 추론을 가져올 때 응답 지연 시간 단축을 위해 사용 가능한 선택적 기능입니다. 프롬프트 캐싱 사용 시에는 대화 중 일부분을 캐시에 추가할 수 있습니다. 그러면 모델이 매번 전체 입력을 처리하고 응답을 계산하는 대신 캐시의 컨텍스트를 재사용할 수 있습니다.
>
> 프롬프트 캐싱은 컨텍스트 윈도우를 계층형 스토리지 시스템으로 취급합니다. Amazon Bedrock은 정적 섹션(시스템 프롬프트, 도구, 문서)에 체크포인트를 표시함으로써 5분 TTL 윈도우 이내의 후속 요청을 위한 정적 섹션 재처리를 생략합니다. 모델 응답의 `CacheReadInputTokens` 및 `CacheWriteInputTokens` 필드를 사용하여 이 동작을 확인할 수 있습니다. `CacheReadInputTokens`는 캐시된 콘텐츠를 추적(상당히 낮은 요금을 청구)하는 반면, `CacheWriteInputTokens`는 캐시에 추가되는 새 콘텐츠를 추적합니다. 이 기능은 성능 향상과 비용 절감을 모두 측정할 수 있는 투명한 메커니즘을 제공합니다.
>
> 프롬프트 캐싱 사용 시에는 할인된 추론 요금이 청구되며, 토큰을 캐시에서 읽고 캐시에 쓰는 횟수에도 다른 요금이 적용됩니다.
>
> 자세한 내용은 다음 리소스를 참조하십시오.
> Amazon Bedrock 요금 페이지: https://aws.amazon.com/bedrock/pricing
> Amazon Bedrock Prompt Caching(Amazon Bedrock 프롬프트 캐싱): https://aws.amazon.com/bedrock/prompt-caching
> Prompt Caching for Faster Model Inference(더욱 빠른 모델 추론을 위한 프롬프트 캐싱): https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html

## 슬라이드 20. 캐시 최적화를 위한 컨텍스트 구조화

**다이어그램 (D2)**

```d2
prompt: "프롬프트 구조 (정적 요소 우선)" {
  sys: "시스템 지침 (정적·캐시됨)"
  tools: "도구 정의 (정적·캐시됨)"
  ref: "참조 문서 (정적·캐시됨)"
  cp: "캐시 체크포인트"
  user: "사용자 입력 (동적·처리됨)"
  sys -> tools -> ref -> cp -> user
}
```

- 정적 요소 우선 프롬프트 전략
- 시스템 지침
- (역할, 어조, 제약 조건)
- 도구 정의
- (JSON 스키마)
- 참조 문서
- (지식 기반)
- 사용자 입력
- (질문, 변수)
- 캐시 체크포인트
- 동적 콘텐츠
- 정적 접두사
- (캐시됨)
- 동적
- (처리됨)

> **강사용 노트**
>
> '정적 요소 우선' 조직에 대해 논의: 시스템 -> 도구 -> 참조 -> 사용자 입력
>
> 공통 시스템 프롬프트를 공유하는 다중 에이전트 아키텍처를 위한 전략에 대해 논의합니다.

> **수강생용 노트**
>
> 캐싱을 효과적으로 사용하려면 '정적 요소 우선' 컨텍스트 엔지니어링 전략을 채택해야 합니다. 모델이 처음부터 프롬프트 접두사를 일치하도록 하기 때문에 변경하면 이후의 모든 토큰에 대한 캐시가 무효화됩니다. 프롬프트는 핵심 시스템 지침 및 도구 사양과 같은 영구 자산을 맨 위에 배치하고 그 아래에 참조 문서, 마지막으로 사용자 입력을 배치하여 구성해야 합니다. 다중 에이전트 시스템에서 여러 에이전트가 동일한 시스템 지침 및 도구 정의를 사용하는 경우, 텍스트가 모든 클라이언트에서 동일하게 직렬화된다면 동일한 캐시 항목을 공유하여 전체 오버헤드를 줄일 수 있습니다.

## 슬라이드 21. 예제: Strands를 사용하여 시스템 지침 캐시

- # STATIC-FIRST: 시스템 지침(캐시됨)
- system_content = [
- SystemContentBlock(
- text="""You are a professional customer service agent.
- Role: Provide helpful, accurate responses
- Tone: Friendly and professional
- Constraints: Always verify information before responding"""
- ),
- SystemContentBlock(cachePoint={"type": "default"}) # ← CACHE END(명시적 체크포인트)
- ]
- # 캐시된 시스템 프롬프트로 에이전트 생성
- agent = Agent(system_prompt=system_content)
- 캐시된 값

> **강사용 노트**
>
> Strands에서 캐싱과 관련된 설명서를 참조하십시오. https://strandsagents.com/latest/documentation/docs/user-guide/concepts/model-providers/amazon-bedrock/#caching
>
> 정적 요소 우선 패턴을 시연: 시스템 지침(정적)을 먼저 캐시하고, 사용자 질문(동적)을 나중에 캐시합니다.
>
> Strands가 SystemContentBlock 배열을 사용하는 방식을 설명: 1번째 블록에는 텍스트가 포함되고 2번째 블록에는 cachePoint가 포함됩니다.
>
> 시스템 지침이 캐싱에 이상적인 이유를 설명: 시스템 지침은 대화 간에 거의 변경되지 않습니다.
>
> 코드 구조 살펴보기: SystemContentBlock 배열 → cachePoint → 에이전트 생성 → 에이전트 호출
>
> 캐시되는 항목을 식별하는 연습: 1번째 SystemContentBlock 텍스트에서 cachePoint 앞에 있는 모든 항목
>
> 캐시 지표 해석을 설명: response.metrics.accumulated_usage 사전을 통해 액세스합니다.
>
> 다중 요청을 시연: 1번째 요청을 캐시에 쓰고, 후속 요청을 캐시에서 읽는 방법을 보여줍니다.
>
> 토큰 최소 요구 사항에 대해 논의: 시스템 지침은 Claude Sonnet 4.5의 토큰 최소 요구 사항 1,024개를 충족해야 합니다.
>
> 다른 예와 비교: 이것이 도구 정의(cache_tools) 또는 참조 문서와 어떻게 다릅니까?
>
> 캐시 확인을 연습: Strands 지표를 사용하여 캐싱이 효과적으로 작동하는지 확인하는 방법
>
> Stands 장점을 설명: 공급자에 구애받지 않는 인터페이스, 자동 지표, 간소화된 API

> **수강생용 노트**
>
> 이 예제는 Strands Agents SDK를 사용하여 시스템 지침을 캐시하는 방법을 보여줍니다. 시스템 지침은 일반적으로 여러 대화에서 일정하게 유지되는 에이전트의 역할, 어조, 제약 조건을 정의합니다. Strands에서는 배열에서 `SystemContentBlock` 객체를 사용합니다. 1번째 블록에는 시스템 지침 텍스트가 포함되고, 2번째 블록에는 캐시된 콘텐츠의 끝을 나타내는 `cachePoint: {"type": "default"}` 마커가 포함됩니다. 이 시스템 프롬프트로 에이전트를 생성하면 Strands가 자동으로 캐싱 구성을 처리합니다. 사용자 질문은 에이전트의 invoke 메서드로 직접 전달되므로 캐시되지 않고 동적으로 처리됩니다. 이 정적 요소 우선 구조를 사용하면 정적 시스템 지침은 캐시 및 재사용되고 동적 사용자 질문은 매번 새로 처리됩니다. 캐시 지표는 Strands에 의해 자동으로 캡처되고 `response.metrics.accumulated_usage`를 통해 사용할 수 있습니다. 1번째 요청에서 시스템 지침이 캐시에 기록될 때 `cacheWriteInputTokens`가 0보다 커집니다. 동일한 시스템 지침을 사용하는 후속 요청에서도 `cacheReadInputTokens`가 0보다 커집니다. 이는 캐시된 콘텐츠가 더 저렴한 비용으로 재사용되었음을 의미합니다. 이 패턴은 시스템 지침은 일관되지만 사용자 질문이 다양한 애플리케이션에서 캐시 재사용 및 비용 절감을 극대화하는 경우 적합합니다. Strands는 특정 플랫폼 공급자에 종속되지 않아 Amazon Bedrock 모델에서도 원활하게 작동하는 인터페이스를 제공하므로 프롬프트 캐싱을 수월하게 처리할 수 있습니다.

## 슬라이드 22. 예제: Strands를 사용하여 도구 정의 캐시

- from strands import Agent, tool
- from strands.models import BedrockModel
- from strands_tools import calculator, current_time
- # cache_tools 구성으로 Strands 사용
- bedrock_model = BedrockModel(
- model_id="anthropic.claude-sonnet-4-5-20250929-v1:0",
- cache_tools="default" # ← 도구에 대해 CACHE ENABLED
- )
- # 캐시된 도구로 에이전트 생성
- agent = Agent(
- model=bedrock_model,
- tools=[calculator, current_time]
- )
- 도구 정의가 캐시됩니다.

> **강사용 노트**
>
> 정적 요소 우선 패턴을 설명: 도구 정의(정적)를 먼저 캐시하고 사용자 요청(동적)을 나중에 캐시합니다.
>
> Strands가 도구 캐싱을 간소화하는 방식을 설명: BedrockModel 구성에서 cache_tools="default"를 설정하기만 하면 됩니다.
>
> 도구 정의가 캐싱에 이상적인 이유를 설명: 도구 정의는 도구를 업데이트하지 않는 한 일반적으로 일정하게 유지됩니다.
>
> 코드 구조 살펴보기: cache_tools를 사용한 BedrockModel → 도구를 사용한 에이전트 → 에이전트 호출
>
> 캐시되는 항목을 식별하는 연습: cache_tools가 활성화되면 모든 도구 정의가 에이전트에게 제공됩니다.
>
> 여러 도구가 함께 캐시되는 방식을 설명: 도구 목록의 모든 도구가 한 단위로 캐시됩니다.
>
> 캐시 지표 해석을 시연: 도구 정의 캐싱이 토큰 비용에 미치는 영향
>
> 시스템 지침과 비교: 시스템은 SystemContentBlock을 사용하고 도구는 cache_tools 구성을 사용합니다.
>
> 도구가 언제 변경될 수 있는지 논의: 도구 정의 캐시를 언제 무효화해야 합니까?
>
> 캐시 확인을 연습: Strands 지표를 사용하여 도구 정의 캐싱이 작동하는지 확인하는 방법
>
> Strands 장점을 설명: 원시 API보다 간단한 구성, 자동 캐시 관리

> **수강생용 노트**
>
> 이 예제에서는 Strands Agents SDK를 사용하여 도구 정의를 캐시하는 방법을 보여줍니다. 도구 정의는 이름, 설명, 입력 스키마 등 모델이 사용할 수 있는 도구(함수)를 설명합니다. 이러한 정의는 일반적으로 정적이며 도구를 추가, 제거 또는 수정하지 않는 한 변경되지 않습니다. Strands에서는 도구 캐싱이 매우 간단합니다. `BedrockModel` 구성에서 `cache_tools="default"`를 설정하기만 하면 됩니다. 이 캐싱을 활성화한 상태에서 도구를 사용하여 에이전트를 생성하면 Strands는 자동으로 모든 도구 정의를 함께 캐시합니다. 사용자 요청은 에이전트의 invoke 메서드로 직접 전달되므로 캐시되지 않고 동적으로 처리됩니다. 이 패턴을 사용하면 도구 정의를 캐시하여 여러 요청에서 재사용할 수 있으므로 동일한 도구를 반복해서 사용할 때 비용이 절감됩니다. 캐시 지표는 Strands에 의해 자동으로 캡처되고 `response.metrics.accumulated_usage`를 통해 사용할 수 있습니다. 1번째 요청은 도구 정의를 캐시에 기록하고(`cacheWriteInputTokens > 0`), 후속 요청은 더 저렴한 비용으로 캐시에서 읽습니다(`cacheReadInputTokens > 0`). 이 패턴은 도구 정의는 일정하지만 사용자 요청이 다양하여 정적 도구 구성에 캐시 재사용을 극대화할 수 있는 프로덕션 시스템에서 특히 유용합니다. Strands를 사용하면 원시 Bedrock API보다 도구 캐싱이 훨씬 간단해집니다.

## 슬라이드 23. 예제: Strands를 사용하여 참조 문서 캐시

- messages = [
- {
- "role": "user",
- "content": [
- {
- "document": {
- "format": "txt",
- "name": "knowledge_base",
- "source": {
- "bytes": b"Company Policies document, 2000+ tokens"
- }
- }
- },
- {
- "text": "Use this document to answer questions."
- },
- {
- "cachePoint": {"type": "default"}
- }
- ]
- }
- ]

> **강사용 노트**
>
> 정적 요소 우선 패턴을 설명: 참조 문서(정적)를 먼저 캐시하고, 사용자 쿼리(동적)를 나중에 캐시합니다.
>
> 메시지 콘텐츠 배열의 문서 블록 및 지침 텍스트 뒤에 cachePoint 마커가 어떻게 배치되는지 설명합니다.
>
> 참조 문서가 캐싱에 적합한 이유를 설명: 참조 문서는 용량이 크고 정적이며 자주 재사용됩니다.
>
> 코드 구조 살펴보기: 메시지 배열 → 문서 블록(형식, 이름, 소스 바이트) → 지침 텍스트 → cachePoint → 에이전트 생성 → 에이전트 호출
>
> 캐시되는 항목을 식별하는 연습: 문서 콘텐츠 블록 + 지침 텍스트(cachePoint 이전의 모든 항목)
>
> 비용 영향을 설명: 대용량 문서를 1번 캐시하면 더 저렴한 비용으로 여러 질문에 대한 답을 찾을 수 있습니다.
>
> 다중 쿼리 패턴을 설명: 동일한 문서, 다양한 질문은 캐시 재사용을 보여줍니다.
>
> 토큰 최소 요구 사항에 대해 논의: 대용량 문서(토큰 1,000개 이상)는 일반적으로 자동으로 임계값을 충족합니다.
>
> 다른 예와 비교: 문서는 메시지에서 cachePoint를 사용하고, 도구는 cache_tools 구성을 사용하고, 시스템은 SystemContentBlock을 사용합니다.
>
> 캐시 확인을 연습: Strands 지표를 사용하여 대용량 문서 캐싱이 작동하는지 확인하는 방법
>
> 실제 영향을 설명: 캐시된 문서 하나로 여러 가지 질문에 답하는 문서 분석 사용 사례
>
> Strands 장점을 설명: 더 깔끔한 메시지 구조, 자동 지표, 더 용이한 유지 관리

> **수강생용 노트**
>
> 이 예제는 Strands Agents SDK를 사용하여 참조 문서 또는 지식 기반 콘텐츠를 캐시하는 방법을 보여줍니다. 참조 문서는 회사 정책, 제품 사양, 지식 기반과 같은 대용량 정적 콘텐츠로, 토큰을 수천 개 포함할 수 있습니다. 이러한 문서는 사용자가 다양한 질문을 하는 동안에도 일정하게 유지되므로 캐싱에 적합합니다. Strants에서는 문서 콘텐츠 블록을 사용하여 에이전트 생성자에 전달된 메시지 배열에 참조 문서를 배치합니다. 문서 블록 구조에는 형식(예: 'txt'), 이름, 소스 바이트가 포함됩니다. 메시지 내용에는 문서 블록, 명령 텍스트(필요한 경우), 캐시된 콘텐츠의 끝을 나타내는 명시적인 `cachePoint: {"type": "default"}` 마커가 포함됩니다. 사용자 쿼리는 에이전트의 invoke 메서드로 전달되어 동적으로 처리됩니다. 이 정적 요소 우선 구조는 캐시된 문서 하나로 여러 가지 질문에 답할 수 있는 강력한 패턴을 제공합니다. 1번째 요청은 문서를 캐시에 기록하고(`cacheWriteInputTokens > 0`), 동일한 문서를 포함하는 후속 요청은 상당히 더 저렴한 비용으로 캐시에서 읽습니다(`cacheReadInputTokens > 0`). 이는 동일한 문서에 대해 사용자 질문이 수십 가지 나올 수 있는 문서 Q&A 시스템에서 특히 유용합니다. 캐시 지표는 Strands에 의해 자동으로 캡처되고 `response.metrics.accumulated_usage`를 통해 사용할 수 있으므로 효과를 쉽게 확인할 수 있습니다. 이 패턴은 상당한 비용 절감을 달성할 수 있습니다. 프로덕션 시스템은 대용량 문서를 캐시하고 질문만 변경하면서 비용을 86% 절감했습니다. Stands는 기본 API 세부 정보를 자동으로 처리하여 이러한 구현을 간소화합니다.

## 슬라이드 24. 프롬프트 캐싱을 사용할 경우 모델 고려 사항

| 기능 | Anthropic Claude | Amazon Nova |
| --- | --- | --- |
| 모드 | Simplified(단일 포인트), Explicit(다중 포인트) | Automatic(지연 시간), Explicit(비용+지연 시간) |
| 비용 절감 | 2가지 모드 모두 | Explicit 모드만 |
| 체크포인트 수 | 최대 4개 | 최대 4개 |
| 최소 토큰 수 | 1,024 - 대부분의 모델  2,048 - Claude 3.5 Haiku 4,096 - Opus 4.5, Haiku 4.5 | 1,000 |
| 체크포인트를 지원하는 필드 | 시스템, 메시지, 도구 | 시스템, 메시지 |

> **강사용 노트**
>
> 중요한 차이점을 강조: Nova Automatic 모드는 지연 시간 이점을 제공하지만 비용 절감 효과는 제공하지 않습니다. 이것이 핵심 차별화 요소입니다.
>
> 실제 사례를 통해 Claude Simplified 모드를 사용해야 하는 경우와 Claude Explicit 모드를 사용해야 하는 경우를 설명합니다.
>
> 비용에 미치는 영향을 설명: Claude는 2가지 모드 모두에서 비용 절감 효과를 얻지만 Nova는 Explicit 모드에서만 가능합니다.
>
> 어떤 모드를 사용할지 식별하는 연습: Nova Automatic 모드와 Nova Explicit 모드 중 어떤 것을 선택하겠습니까?
>
> 체크포인트 전략을 비교: 단일 체크포인트(Claude Simplified)와 다중 체크포인트(Claude Explicit, Nova Explicit).
>
> 토큰 최소 요구 사항에 대해 논의: 모델마다 최소 토큰 요구 사항이 다른 이유는 무엇입니까?
>
> 의사결정 트리 살펴보기: 다양한 시나리오에 어떤 캐싱 모드를 사용해야 합니까?
>
> 코드 예제 보기: Simplified 구현과 Explicit 구현의 차이점을 시연합니다.
>
> 캐시 효율성 계산을 연습: 사용 사례에 필요한 체크포인트는 몇 개입니까?
>
> 프로덕션 고려 사항을 비교: 비용에 민감한 워크로드와 지연 시간에 민감한 워크로드
>
> Nova의 자동 캐싱을 시연: 명시적 구성 없이 어떻게 캐싱이 작동하는지 설명합니다.
>
> Nova Explicit가 프로덕션 환경에 권장되는 이유를 설명: 비용 절감 + 일관된 성능

> **수강생용 노트**
>
> 이 슬라이드는 프롬프트 캐싱 구현에서 중요한 모델별 차이점을 강조합니다. Anthropic Claude는 Simplified(자동 접두사 일치 기능이 있는 단일 체크포인트) 및 Explicit(정밀한 제어가 가능한 최대 4개의 체크포인트)의 2가지 모드를 제공합니다.
>
> 2가지 Claude 모드 모두 동일한 기본 캐싱 메커니즘을 사용하기 때문에 비용을 절감할 수 있습니다. 차이점은 비용 이점이 아니라 체크포인트 배치 전략에 있습니다. Amazon Nova도 2가지 모드를 제공하지만 중요한 차이점이 있습니다. Explicit 모드는 지연 시간 이점(비용 절감 이점 없음)만 제공하는 반면, Explicit 모드는 비용 절감 이점과 지연 시간 이점을 모두 제공합니다.
>
> Nova에서 비용을 최적화하려면 Explicit 모드에서 명시적 cachePoint 마커를 함께 사용해야 합니다.
>
> Explicit 모드는 기본적으로 활성화되며 구성이 필요하지 않으므로 비용이 주요 문제가 아닌 빠른 프로토타입 생성 또는 지연 시간에 민감한 애플리케이션에 유용합니다. 그러나 프로덕션 워크로드의 경우 비용 절감 이점과 일관된 성능 이점을 모두 제공하는 Nova Explicit 모드를 사용하는 것이 좋습니다.
>
> 2가지 모델군 모두 요청당 캐시 체크포인트를 최대 4개 지원하지만 최소 토큰 요구 사항이 다릅니다. Claude 모델에는 일반적으로 체크포인트당 토큰이 1,024개 필요합니다(Claude 3.5 Haiku에는 2,048개, Claude Opus 4.5 및 Claude Haiku 4.5에는 4,096개 필요). 반면 Nova 모델은 체크포인트당 토큰이 1,000개 필요합니다.
>
> 캐싱 전략을 선택할 때는 우선순위를 고려하십시오. Nova에서 비용을 절감해야 하는 경우 Explicit 모드를 사용해야 합니다. Claude를 사용하는 경우 2가지 모드 모두 비용 절감 이점을 제공하므로 간단한 단일 체크포인트 캐싱이 필요한지 아니면 세분화된 다중 체크포인트 제어가 필요한지에 따라 모드를 선택합니다. 이 슬라이드는 프로덕션 시스템의 성능과 비용을 모두 최적화하려면 모델별 캐싱 기능을 이해하는 것이 필수적이라는 점을 강조합니다.

## 슬라이드 25. AgentCore Memory에 컨텍스트 기록

- 목적: 데이터 접근성을 유지하면서 정보를 외부에 저장하여 컨텍스트 윈도우 사용을 줄입니다.
- AgentCore 구현: 장기 메모리
- Amazon Bedrock AgentCore Memory는 세션별 지속성과 세션 간 지속성을 모두 제공
- 대화 기록, 사용자 선호 사항, 축적된 지식을 외부에 저장
- 대화가 많은 애플리케이션에서 컨텍스트 축소를 지원

> **강사용 노트**
>
> 기록 전략이 정보를 외부화하여 컨텍스트 윈도우 제한을 해결하는 방법을 설명합니다.
>
> 단기 및 장기 메모리에 대한 시맨틱 전략을 사용하여 AgentCore Memory 구성을 시연합니다.
>
> 단기 메모리가 세션 내에서 대화 컨텍스트를 유지하는 방식을 설명합니다.
>
> 장기 메모리 추출 프로세스를 설명: 원시 이벤트의 비동기식 백그라운드 처리
>
> 메모리 검색 살펴보기: 단기의 경우 ListEvents, 장기의 경우 시맨틱 검색을 위한 RetrieveMemoryRecords
>
> 사용 사례에 대해 논의: 대화가 많은 애플리케이션, 다중 세션 사용자 상호 작용, 개인화된 경험
>
> 컨텍스트 축소 계산을 연습: AgentCore Memory를 사용하는 경우와 사용하지 않는 경우 토큰 사용량을 비교합니다.
>
> 에이전트가 어떻게 전체 대화 기록을 컨텍스트에 로드하지 않고도 메모리를 사용하여 과거 상호 작용을 회상할 수 있는지 설명합니다.

> **수강생용 노트**
>
> 컨텍스트 기록 전략은 AgentCore Memory를 통해 데이터 접근성을 유지하면서 정보를 외부에 저장하여 컨텍스트 윈도우 사용을 줄입니다. 이 접근 방식은 프로덕션 에이전틱 시스템에서 컨텍스트 윈도우가 유한하고 비용이 많이 드는 리소스라는 근본적인 문제점을 해결합니다.
>
> AgentCore Memory는 세션별 지속성과 세션 간 지속성을 모두 제공합니다. 단기 메모리는 단일 세션 내에서 순차적으로 발생하는 상호 작용을 캡처하여 각각 별도의 이벤트로 저장합니다. 이를 통해 에이전트는 사용자가 정보를 반복하지 않아도 즉각적인 대화 컨텍스트를 유지할 수 있으므로 보다 자연스럽고 사람과 같은 대화가 가능합니다. 단기 메모리는 ListSessions, ListEvents 및 GetEvent 작업을 사용하여 액세스할 수 있습니다.
>
> 장기 메모리는 원시 에이전트 상호 작용에서 구조화된 정보를 자동으로 추출 및 저장하여 여러 세션에 걸쳐 주요 인사이트를 유지합니다. 추출 프로세스는 백그라운드에서 비동기적으로 실행되어 대화를 분석하여 요약, 사실, 지식, 사용자 선호 사항을 추출합니다. 장기 메모리 레코드는 영구적으로 저장되며 GetMemoryRecord, ListMemoryRecords 또는 RetrieveMemoryRecords 작업을 사용하여 검색할 수 있습니다. RetrieveMemoryRecords 작업은 시맨틱 검색을 수행하여 현재 쿼리와 가장 관련이 있는 메모리 레코드를 찾으므로 컨텍스트를 인식하는 개인화된 에이전트 응답이 가능해집니다.
>
> 대화 기록, 사용자 선호 사항, 축적된 지식을 AgentCore Memory를 통해 외부에 저장함으로써 에이전트는 전체 대화 기록을 활성 컨텍스트 윈도우에 로드하지 않고도 관련 과거 정보에 액세스할 수 있습니다. 이를 통해 컨텍스트를 인식하는 개인화된 경험을 제공하는 기능을 유지하면서 대화가 많은 애플리케이션에서 상당한 컨텍스트 축소(일반적으로 40~60%)를 달성할 수 있습니다. 이 전략은 에이전트가 다양한 대화 세션에서 사용자 선호 사항 및 과거 상호 작용을 기억해야 하는 다중 세션 상호 작용이 필요한 애플리케이션에 특히 유용합니다.

## 슬라이드 26. 예제: 장기 메모리에 기록

- # AgentCore Memory에 정보 저장
- from agentcore_memory import MemoryClient
- memory_client = MemoryClient()
- # 사용자 선호 사항을 장기 메모리에 기록
- memory_client.put_memory_record(
- memory_id="user-preferences",
- actor_id="user-123",
- content={
- "preferred_language": "Python",
- "notification_settings": "email",
- "last_interaction": "2025-12-17"
- },
- memory_type="user_preference"
- )
- # 컨텍스트 대신 메모리에서 검색
- preferences = memory_client.get_memory_record(
- memory_id="user-preferences",
- actor_id="user-123"
- )
- 메모리에 기록

> **강사용 노트**
>
> 코드 예제를 1줄씩 살펴보고 각 파라미터를 설명합니다.
>
> MemoryClient 초기화 및 AgentCore Memory 리소스 연결을 시연합니다.
>
> memory_id를 논리적 그룹화로 설명합니다(예: 'user-preferences', 'conversation-history').
>
> actor_id를 다중 사용자 메모리 격리를 가능하게 하는 사용자 식별자로 설명합니다.
>
> 콘텐츠 사전이 구조화된 데이터(선호 사항, 설정, 사실)를 저장하는 방식을 설명합니다.
>
> 모든 필수 파라미터를 사용하여 put_memory_record() 호출을 시연합니다.
>
> get_memory_record() 검색 패턴을 설명합니다(컨텍스트에 유지하지 않고 필요할 때 가져옴).
>
> 토큰 사용량을 비교: 선호 사항을 컨텍스트에 저장하는 방법과 메모리에서 검색하는 방법
>
> 확장 예제를 연습: 선호 사항 필드 추가, 다양한 메모리 유형 추가
>
> put_memory_record를 사용하는 경우와 이벤트에서 자동 추출을 사용하는 경우에 대해 논의합니다.
>
> 오류 처리에 대해 설명: memory_id 또는 actor_id가 존재하지 않으면 어떻게 됩니까?

> **수강생용 노트**
>
> 이 코드 예제는 사용자 선호 사항을 활성 컨텍스트 윈도우에 유지할 필요가 없도록 명시적으로 AgentCore Memory의 장기 스토리지에 저장 및 검색하는 방식으로 컨텍스트 기록 전략을 구현하는 방법을 보여줍니다.
>
> 예제는 먼저 `agentcore_memory` 모듈(AgentCore 스타터 도구 키트의 일부)에서 `MemoryClient`를 가져오고 클라이언트 인스턴스를 초기화하는 것으로 시작합니다. `MemoryClient`는 AgentCore Memory 리소스와 상호 작용하기 위한 Python 인터페이스를 제공합니다.
>
> put_memory_record()를 사용하여 데이터 저장:
> `put_memory_record()` 메서드는 구조화된 정보를 장기 메모리에 직접 저장합니다. 주요 파라미터는 다음과 같습니다.
> `memory_id`: 관련 레코드를 그룹화하는 메모리 유형(예: 'user-preferences')의 논리적 식별자
> `actor_id`: 다중 사용자 메모리 격리를 가능하게 하는 사용자 또는 엔티티의 고유 식별자(예: 'user-123')
> `content`: 사용자 선호 사항, 설정, 사실과 같은 저장할 실제 데이터를 포함하는 사전
> `memory_type`: 다양한 유형의 메모리를 구성하는 데 도움이 되는 범주화 문자열(예: 'user_preference')
>
> 이 예제에서는 선호 언어, 알림 설정, 마지막 상호 작용 날짜 등의 사용자 선호 사항이 구조화된 사전으로 저장됩니다. 이 데이터는 여러 세션에 걸쳐 지속되며 나중에 컨텍스트 윈도우 토큰을 사용하지 않고 검색할 수 있습니다.
>
> get_memory_record()를 사용하여 데이터 검색:
> 코드는 모든 상호 작용에 대해 사용자 선호 사항을 컨텍스트 윈도우로 로드하는 대신, `get_memory_record()`를 사용하여 필요할 때만 메모리에서 해당 정보를 검색합니다. 이 메서드를 사용하려면 특정 레코드를 찾기 위한 `memory_id` 및 `actor_id`가 필요합니다. 그러면 검색된 데이터를 모든 컨텍스트 윈도우에 포함하여 발생하는 오버헤드 없이 사용하여 에이전트의 응답 또는 행동을 개인화할 수 있습니다.
> 이 패턴은 사용자 선호 사항, 설정, 역사적 사실, 자주 변경되지 않지만 여러 세션에서 액세스할 수 있어야 하는 기타 정보를 저장하는 데 특히 효과적입니다. 이러한 데이터를 컨텍스트 윈도우에 유지하는 대신 장기 메모리에 기록함으로써 에이전트는 컨텍스트를 인식하는 개인화된 경험을 유지하면서 상당한 컨텍스트 축소를 달성할 수 있습니다.

> **수강생용 노트**
>
> 컨텍스트 전략 선택은 현재 목표와 가장 관련이 있는 정보를 선택하여 지능적으로 컨텍스트를 어셈블합니다. 관련성 알고리즘은 의미적 유사성, 최신성 가중치, 목표 기반 점수를 사용하여 사용 가능한 컨텍스트 요소의 순위를 매깁니다. 동적 컨텍스트 로딩이란 시스템이 현재 태스크, 사용자 프로필, 대화 상태를 기반으로 실시간으로 컨텍스트를 구축하는 것을 의미합니다. 우선순위 기반 선택을 통해 토큰 제약이 있는 경우에도 중요한 정보가 항상 컨텍스트 윈도우에 도달할 수 있습니다. 다중 에이전트 환경에서는 전문가 에이전트 간에 가용성을 유지하면서 중복 없이 컨텍스트를 효율적으로 공유할 수 있는 조정 프로토콜이 필요합니다.

## 슬라이드 28. 목적: 의미적 유사성과 우선순위 기반 선택을 사용하여 현재 목표와 가장 관련이 있는 정보를 선택합니다.

- AgentCore 구현: 시맨틱 검색을 사용한 메모리 검색
- Amazon Bedrock AgentCore Memory의 RetrieveMemoryRecords를 사용
- 시맨틱 검색을 수행하여 가장 관련이 있는 메모리 레코드를 검색
- 가중치 기반 채점을 사용한 우선순위 기반 선택을 구현
- 컨텍스트 팽창을 줄이면서 응답 관련성을 개선
- AgentCore를 사용하여 지능적으로 관련 컨텍스트를 선택

> **강사용 노트**
>
> 컨텍스트를 인식하여 관련 정보를 검색하는 데 시맨틱 검색과 키워드 기반 검색이 어떻게 다른지 설명합니다.
>
> 다양한 쿼리 예제 및 파라미터 구성을 사용하여 RetrieveMemoryRecords 작업을 시연합니다.
>
> 가중치 기반 채점을 사용한 우선순위 기반 선택이 중요한 정보가 항상 포함되도록 할 수 있음을 설명합니다.
>
> 컨텍스트를 어셈블할 때 max_results와 컨텍스트 윈도우 크기 간의 절충에 대해 논의합니다.
>
> min_relevance_score 임계값을 기반으로 관련성 점수를 계산하고 결과를 필터링하는 연습을 합니다.
>
> 지능형 선택이 있는 경우와 없는 경우의 컨텍스트 어셈블리를 비교하여 팽창 감소 효과를 설명합니다.

> **수강생용 노트**
>
> 컨텍스트 선택 전략은 AgentCore Memory의 RetrieveMemoryRecords 작업을 사용하여 현재 목표와 가장 관련이 있는 정보를 지능적으로 선택합니다. 사용 가능한 컨텍스트를 모두 로드하는 것과 달리, 이 접근 방식은 시맨틱 검색을 수행하여 현재 쿼리 또는 태스크와 컨텍스트상 유사한 메모리 레코드를 찾습니다. 이 전략은 벡터 임베딩 및 유사성 알고리즘을 사용하여 사용 가능한 메모리 레코드의 순위를 매겨 컨텍스트 윈도우에는 가장 관련이 있는 정보만 표시되도록 합니다.
>
> 가중치 기반 채점을 사용한 우선순위 기반 선택을 통해 시스템은 컨텍스트 관련성 순위를 매길 때 여러 요소를 결합할 수 있습니다. 이러한 요소에는 의미적 유사성(메모리 내용이 쿼리 의도와 일치하는 정도), 최신성(정보가 최근에 생성 또는 액세스된 정도), 다양한 정보 유형에 할당된 명시적 우선순위 가중치가 포함됩니다. 이러한 다중 요소 접근 방식에서는 의미상 가장 유사한 일치 항목이 아니더라도 중요한 정보가 항상 포함됩니다.
>
> 이 전략은 사용 가능한 컨텍스트를 모두 로드하는 대신 최상위 관련 레코드만 선택함으로써 컨텍스트 팽창을 상당히 줄이고 응답 관련성을 개선합니다. RetrieveMemoryRecords 작업은 max_results와 같은 파라미터를 사용하여 반환되는 레코드 수를 제한하고 min_relevance_score와 같은 파라미터를 사용하여 관련성이 낮은 일치 항목을 필터링합니다. 개발자는 이 세밀한 제어를 통해 컨텍스트 완전성과 토큰 효율성 간의 균형을 맞출 수 있어 응답 관련성이 35~50% 향상되는 동시에 불필요한 컨텍스트 소비가 줄어듭니다.

## 슬라이드 29. 예제: 관련 메모리 검색

- from bedrock_agentcore.memory import MemoryClient
- client = MemoryClient(region_name="us-east-1")
- 시맨틱 검색을 사용하여 메모리 레코드를 검색
- response = client.retrieve_memory_records(
- memoryId="conversation-history",
- namespace="/users/{actorId}/preferences", # 필수 파라미터
- searchCriteria={
- "searchQuery": "What are the user's preferences for data visualization?",
- "topK": 5 # 시맨틱 검색 순위 지정에 사용(최소: 1, 최대: 100)
- }
- )
- # 결과 처리
- relevant_memories = response.get('memoryRecordSummaries', [])
- # 필요한 경우 관련 점수별 필터링
- selected_context = [
- memory['content']['text'] # MemoryContent 객체에서 텍스트 액세스
- for memory in relevant_memories
- if memory.get('score', 0) > 0.8 # 관련 점수가 0.8을 초과하는 메모리만 포함
- ]
- # 에이전트 프롬프트에서 선택한 프롬프트 사용
- agent_context = "\n".join(selected_context)

> **강사용 노트**
>
> 각 코드 섹션을 살펴봅니다.

> **수강생용 노트**
>
> 이 예제는 AgentCore Memory를 사용하여 지능형 컨텍스트 선택을 실제로 구현하는 방법을 보여줍니다. 코드는 먼저 bedrock_agentcore.memory에서 MemoryClient를 가져오고 region 파라미터를 사용하여 MemoryClient 인스턴스를 초기화하는 것으로 시작합니다.
>
> RetrieveMemoryRecords 작업은 3가지 주요 파라미터를 사용하여 시맨틱 검색을 수행합니다.
> memoryId: 검색할 AgentCore Memory 리소스를 식별합니다(예: 'conversation-history').
> namespace: 메모리 레코드가 저장되는 위치를 지정하는 필수 파라미터로, 파일 경로와 같이 계층적으로 구성됩니다(예: '/users/{actorId}/preferences'). 이 값은 메모리 전략에 구성된 네임스페이스와 일치해야 합니다.
> searchCriteria: 다음을 포함하는 사전입니다.
> searchQuery: 필요한 정보를 설명하는 시맨틱 쿼리 문자열(예: "데이터 시각화에 대한 사용자의 선호 사항은 무엇입니까?")
> topK: 반환할 최대 결과 수(최소: 1, 최대: 100)
>
> 시맨틱 검색 쿼리는 질문과 컨텍스트상 유사한 메모리 레코드를 찾기 위해 벡터 임베딩을 사용하여 처리됩니다. topK 파라미터는 반환되는 레코드 수를 가장 관련이 있는 일치 항목으로 제한합니다. API는 'memoryRecordSummaries' 배열이 포함된 응답 사전에 결과를 반환합니다. 각 요약에는 콘텐츠(MemoryContent 객체), 점수(관련성 점수), memoryRecordId, memoryStrategyId, 네임스페이스와 같은 필드가 포함됩니다.
>
> 코드는 관련 메모리를 검색한 후 점수가 0.8 이상인 레코드만 선택하는 필터링을 수행합니다. API가 min_relevance_score 파라미터를 제공하지 않기 때문에 이 필터링 단계는 코드에서 검색 후에 발생합니다. 점수 필드는 쿼리 임베딩과 메모리 임베딩 간의 코사인 유사성을 나타냅니다. 즉, 값이 높을수록 관련성이 더 높습니다.
>
> 콘텐츠를 추출할 때는 memory['content']['text']에 액세스하는 것이 중요합니다. API는 콘텐츠를 직접 문자열이 아닌 텍스트 필드가 있는 MemoryContent 객체(유니온 유형)로 반환하기 때문입니다. 그런 다음 list comprehension을 사용하여 선택된 메모리 텍스트를 단일 문자열로 어셈블하고 줄바꿈으로 결합하여 에이전트의 프롬프트에 포함할 수 있는 agent_context를 생성합니다.
>
> 이 패턴은 전체 대화 기록을 컨텍스트 윈도우에 로드하는 대신 현재 상호 작용에 필요한 특정 과거 정보만 검색하므로 동적 온디맨드 컨텍스트 로드가 용이해집니다. namespace 파라미터는 메모리를 적절하게 구성하고 필요에 따라 특정 액터, 세션 또는 전략으로 범위를 지정할 수 있도록 합니다.

## 슬라이드 30. 컨텍스트 압축 전략 - 고충실도 요약

- 필수 정보를 유지하면서 토큰 팽창을 줄입니다.
- 요약
- 궤적을 압축
- 트리밍 또는 프루닝
- 선택적으로 토큰 제거
- 압축된 컨텍스트
- 컨텍스트

> **강사용 노트**
>
> 대화 압축을 위한 Strands SDK 통합을 시연합니다.
>
> 토큰 수 및 시맨틱 보존 지표를 사용하여 전, 후 예제를 소개합니다.
>
> 압축된 컨텍스트 평가를 위한 품질 평가 기법을 연습합니다.
>
> 토큰 소비 감소와 정보 손실 간의 압축 절충점에 대해 논의합니다.

> **수강생용 노트**
>
> 컨텍스트 압축은 토큰 사용량 관리를 위한 프롬프트 캐싱 보완 전략입니다. 프롬프트 캐싱은 여러 요청에서 프롬프트의 정적 부분을 재사용하는 데 초점을 맞추는 반면, 컨텍스트 압축은 동적 또는 증가하는 컨텍스트에서 토큰 수를 줄이는 과제를 해결합니다.
>
> 요약은 의미를 보존하면서 정보를 요약하는 데 중점을 둡니다. 이 접근 방식은 장황한 내용을 모델이 태스크를 효과적으로 수행하는 데 필요한 필수 정보를 포함하는 보다 간결한 표현으로 변환합니다.
>
> 트리밍 및 프루닝에는 필수 정보를 제공하지 않는 토큰의 전략적 제거가 포함됩니다. 내용을 압축하는 요약과 달리, 이 방법은 중복 또는 덜 중요한 토큰을 선택적으로 제거하여 전체 컨텍스트 크기를 줄입니다.
>
> 2가지 방법 모두 고충실도 요약을 달성하여 정보 품질을 유지하면서 토큰 팽창을 줄이는 것이 목표입니다. 이러한 압축 기법은 프롬프트 캐싱 전략과 결합될 때 프로덕션 AI 애플리케이션에서 토큰 사용량을 최적화하고 컨텍스트 크기를 관리하는 포괄적인 접근 방식을 제공합니다.
>
> 압축은 지능형 요약을 통해 필수 정보를 보존하면서 토큰 소비를 줄일 수 있습니다. Strands 대화 관리를 사용한 고충실도 요약은 중요한 세부 정보를 누락하지 않으면서 긴 대화와 복잡한 컨텍스트를 필수 정보로 압축합니다. 토큰 최적화는 중복 정보를 제거하고, 유사한 개념을 통합하고, 보다 효율적인 언어 패턴을 사용합니다. 시맨틱 보존은 에이전트가 효과적인 의사결정을 내리는 데 필요한 의미 및 관계를 유지합니다. 압축 품질 지표는 토큰 감소 비율과 정보 보존 비율을 모두 추적하여 효과를 측정합니다.

## 슬라이드 31. 3가지 대화 관리자 유형:

- NullConversationManager: 수정이 필요 없음, 짧은 대화 및 디버깅용
- SlidingWindowConversationManager: 기본 유형, 고정된 창을 유지
- SummarizingConversationManager: 지능형 요약
- Strands Agents SDK를 사용한 대화 관리

> **강사용 노트**
>
> 기본 SlidingWindow 동작을 다른 2가지 옵션과 비교합니다.
>
> NullConversationManager를 안전하게 사용할 수 있는 구체적인 사용 사례에 대해 논의합니다(예: REPL, 테스트).
>
> SummarizingConversationManager의 메커니즘 및 장기 실행 태스크에서의 이점을 설명합니다.
>
> 기본 대화 관리자 이외의 대화 관리자를 사용하여 에이전트를 인스턴스화하는 방법을 시연합니다.

> **수강생용 노트**
>
> Strands Agents SDK의 대화 관리자는 활성 컨텍스트 윈도우 내에서 대화 기록을 관리하는 체계적인 접근 방식을 제공합니다. SDK는 3가지 유형의 내장 대화 관리자를 제공하며, 각 유형은 서로 다른 시나리오에 최적화되어 있습니다.
> NullConversationManager는 가장 간단한 옵션으로, 대화 기록을 전혀 수정하지 않습니다. 따라서 컨텍스트 제한을 초과하지 않는 짧은 대화, 전체 대화 기록을 확인하려는 디버깅 시나리오 또는 수동 컨텍스트 관리를 선호하는 경우에 적합합니다. 압축 또는 윈도잉 작업을 수행하지 않기 때문에 가장 투명한 옵션이지만 긴 대화에는 효율성이 떨어집니다.
>
> SlidingWindowConversationManager는 에이전트 클래스에서 사용하는 기본 대화 관리자입니다. 고정된 수의 최근 메시지를 유지하고 윈도우 크기가 초과되면 오래된 메시지를 자동으로 제거합니다. 이 접근 방식은 간단하고 예측 가능하므로 보존되는 메시지 수를 항상 정확히 알 수 있습니다. 그러므로 최근 컨텍스트가 가장 중요하고 오래된 메시지를 삭제해도 무방한 대화에 효과적입니다. 그러나 오래된 메시지의 정보가 보존되지 않으므로 과거 컨텍스트가 중요한 긴 대화에 사용하기에는 제한적일 수 있습니다.
>
> SummarizingConversationManager는 제한된 토큰 내에서 컨텍스트를 보존하기 위해 오래된 메세지를 지능적으로 요약합니다. 오래된 메시지를 삭제하는 대신 주요 정보, 논의된 주제, 사용된 도구, 기술 세부 정보를 캡처하는 구조화된 글머리 기호 요약을 생성합니다. 이 접근 방식은 정보 밀도를 유지하면서 토큰 소비를 줄입니다. 과거 컨텍스트가 중요하지만 전체 메시지 기록이 토큰 제한을 초과하는 장기 실행 대화, 연구 세션, 지식 집약적 애플리케이션에 특히 유용합니다.
>
> AgentCore Memory 통합: 대화 관리자는 세션 관리자와 연동하여 완전한 대화 수명 주기 관리를 제공합니다. 대화 관리자는 활성 세션 동안 인메모리 컨텍스트를 처리하고, `AgentCoreMemorySessionManager`와 같은 세션 관리자는 세션 간 연속성을 위해 AgentCore Memory로 지속성을 관리합니다. 이 통합에서 에이전트는 대화 관리자를 통해 활성 컨텍스트를 압축하고 AgentCore Memory를 통해 과거 정보에 대한 액세스를 유지할 수 있습니다. SummarizingConversationManager는 AgentCore Memory와 결합될 때 특히 강력합니다. 대화 관리자는 활성 컨텍스트를 지능적으로 압축하고 세션 관리자는 중요한 정보가 세션 간에 유지되도록 합니다.

## 슬라이드 32. SummarizingConversationManager 개요

- 컨텍스트 윈도우 관리: 토큰 제한이 초과되면 자동으로 컨텍스트를 축소
- 지능형 요약: 구조화된 글머리 기호 요약을 사용하여 주요 정보를 캡처
- 도구 페어 보존: 요약 중에 도구 사용 및 결과 메시지 페어가 손상되지 않도록 함
- 유연한 구성: 다양한 파라미터를 통해 요약 동작을 사용자 지정
- 폴백 안전성: 요약 실패를 정상적으로 처리

> **강사용 노트**
>
> 자동 컨텍스트 윈도우 관리가 긴 대화 중에 어떻게 토큰 제한 오류를 방지하는지 설명합니다.
>
> 구조화된 글머리 기호 요약 형식과 주요 정보를 효율적으로 캡처하는 방법을 시연합니다.
>
> 도구 페어 보존이 중요한 이유를 설명: 컨텍스트 무결성을 위해 도구 호출 및 해당 결과가 함께 유지되어야 합니다.
>
> 요약 적극성(summary_ratio)과 정보 보존 간의 균형에 대해 논의합니다.
>
> 대체 안전 메커니즘 살펴보기: 요약이 실패하거나 시간이 초과되면 어떻게 됩니까?
>
> 다양한 사용 사례에서 SummarizingConversationManager를 SlidingWindow 및 Null 관리자와 비교합니다.

> **수강생용 노트**
>
> SummarizingConversationManager는 토큰 제한을 초과할 경우 컨텍스트를 자동으로 줄이는 지능적인 컨텍스트 윈도우 관리 기능을 제공합니다. 이 관리자는 슬라이딩 윈도우 접근 방식처럼 오래된 메시지를 삭제하는 대신, 최근 메시지의 전체 내용을 보존하면서 오래된 대화 기록을 구조화된 요약으로 압축합니다. 이 접근 방식은 토큰 제약 조건 이내로 유지하면서 과거 컨텍스트에 대한 액세스를 유지합니다.
>
> 지능형 요약은 구조화된 글머리 기호 요약을 사용하여 오래된 메시지의 주요 정보를 캡처합니다. 이러한 요약에는 논의된 주제, 결정 사항, 사용된 도구, 기술 정보 등 중요한 세부 정보가 보존되므로 압축 중에 중요한 컨텍스트가 손실되지 않습니다. 구조화된 형식을 사용하여 요약을 쉽게 구문 분석 및 이해할 수 있어 정보 밀도를 유지하면서 토큰 소비를 줄일 수 있습니다.
>
> 도구 페어 보존은 도구 사용 메시지 및 해당 결과 메시지가 요약 중에 원자 단위로 함께 유지되도록 하는 중요한 기능입니다. 이러한 페어를 깨뜨리면 도구 호출 및 해당 결과의 논리적 흐름이 파괴되어 대화 컨텍스트가 유효하지 않게 됩니다. 관리자는 이러한 페어를 인식하고 분리 불가능한 단위로 취급하여 2개 메시지를 함께 보관 또는 요약합니다.
>
> 유연한 구성을 통해 summary_ratio(요약할 대화의 양을 제어), preserve_recent_messages(항상 최근 컨텍스트가 유지되도록 함)와 같은 파라미터, 사용자 지정 요약 에이전트 또는 프롬프트(선택 사항)를 통해 사용자 지정할 수 있습니다. 요약 작업이 실패할 수 있는 시나리오를 처리하는 대체 안전 메커니즘은 요약 프로세스에서 오류가 발생하더라도 대화가 계속되도록 하여 시스템 장애로 인해 사용자 상호 작용이 중단되는 것을 방지합니다.

## 슬라이드 33. SummarizingConversationManager 구성

- summary_ratio(float, 기본값: 0.3): 컨텍스트를 축소할 때 요약할 메시지의 백분율입니다(0.1~0.8 사이로 고정).
- preserve_recent_messages(int, 기본값: 10): 항상 유지할 최근 메시지의 최소 수입니다.
- summarization_agent(에이전트, 선택 사항): 요약 생성을 위한 사용자 지정 에이전트입니다. 제공하지 않을 경우 기본 에이전트 인스턴스가 사용됩니다.
- summarization_system_prompt(str, 선택 사항): 요약을 위한 사용자 지정 시스템 프롬프트입니다. 제공하지 않을 경우 기본 프롬프트가 사용됩니다.

> **강사용 노트**
>
> summary_ratio=0.3이 컨텍스트 축소가 필요할 때 메시지의 30%가 요약된다는 의미임을 설명합니다.
>
> 클램핑 동작을 시연: 0.1보다 작은 값은 0.1이 되고, 0.8보다 큰 값은 0.8이 됩니다.
>
> preserve_recent_messages=10이 최근 10개 메시지의 요약을 금지하여 즉각적인 컨텍스트를 유지함을 설명합니다.
>
> 사용자 지정 summarization_agent를 사용해야 하는 경우에 대해 논의: 전문 모델, 다양한 온도 설정 또는 도메인별 요약
>
> 사용자 지정 summarization_system_promp 사용 사례를 설명: 도메인별 용어, 구조화된 출력 요구 사항 또는 특정 요약 형식
>
> 다양한 파라미터 조합을 구성하는 연습을 하고 해당 조합이 컨텍스트 보존 및 토큰 사용량에 미치는 영향을 설명합니다.

> **수강생용 노트**
>
> SummarizingConversationManager는 동작을 제어하는 4가지 주요 파라미터를 통해 유연한 구성이 가능합니다. summary_ratio 파라미터(기본값 0.3)는 컨텍스트 축소가 필요할 때 요약할 메시지의 비율을 결정합니다. 값 0.3은 대화의 30%가 요약으로 압축된다는 의미입니다. 이 값은 적절한 동작을 확보하기 위해 자동으로 0.1에서 0.8 사이로 고정됩니다. 값이 너무 낮으면 의미 있는 압축을 제공하지 못하고, 값이 너무 높으면 중요한 정보가 손실될 수 있습니다. 기본값 0.3은 균형 잡힌 접근 방식을 제공하여 대부분의 정보를 보존하면서 컨텍스트를 크게 줄입니다.
> preserve_recent_messages 파라미터(기본값 10)를 사용하면 최소 개수의 최근 메시지가 요약되지 않고 항상 전체 내용이 유지됩니다. 그러면 즉각적인 대화 컨텍스트가 그대로 유지되며, 이는 자연스러운 대화 흐름을 유지하는 데 매우 중요합니다. 최근 메시지에는 현재 상호 작용과 가장 관련이 있는 컨텍스트가 포함되는 경우가 자주 있으므로, 메시지를 보존하면 에이전트가 최근 교환의 전체 내용에 액세스할 수 있습니다.
>
> summarization_agent 파라미터(선택 사항)를 사용하면 특별히 요약 생성을 위한 사용자 지정 에이전트 인스턴스를 제공할 수 있습니다. 이 파라미터를 제공하지 않으면 관리자가 기본 에이전트 인스턴스를 사용합니다. 이는 요약과 기본 대화에 서로 다른 모델 설정(예: 온도)을 원하거나 요약 태스크에 최적화된 전문 모델을 사용하려는 경우에 유용합니다.
>
> 마찬가지로, summarization_system_prompt 파라미터(선택 사항)를 사용하면 요약 생성 방법에 대한 사용자 지정 지침을 사용할 수 있습니다. 이 파라미터를 생략하면 기본 프롬프트가 사용됩니다. 사용자 지정 프롬프트는 기술 용어를 보존하거나, 특정 구조화된 형식을 유지하거나, 요약에서 특정 유형의 정보를 강조하는 등 도메인별 요약 요구 사항에 유용합니다. 이러한 유연성 덕분에 SummarizingConversationManager는 핵심적인 지능형 요약 기능을 유지하면서 다양한 애플리케이션 요구 사항에 맞게 조정이 가능합니다.

## 슬라이드 34. 컨텍스트 분리 전략 - 다중 에이전트 경계

**다이어그램 (D2)**

```d2
ctx: 컨텍스트
mas: 다중 에이전트 시스템
sandbox: "샌드박스 환경 (분리된 실행 컨텍스트)"
ctx -> mas: "상태 버킷에서 선택적 필드 전송"
mas -> sandbox
```

- 컨텍스트를 서로 다른 경계로 분할합니다.
- 다중 에이전트 시스템
- 다중 에이전트 시스템
- 컨텍스트
- 샌드박스 환경
- 분리된 실행 컨텍스트
- 상태 버킷 LLM에
- 선택적 필드를 전송

> **강사용 노트**
>
> 병렬 처리의 이점 및 조정 문제에 대해 논의합니다.
>
> 예를 들어 CodeAct 에이전트(https://arxiv.org/html/2402.01030v4)가 있습니다. AgentCore Code Interpreter에 대해서도 논의할 수 있습니다.

> **수강생용 노트**
>
> 컨텍스트 분리 전략은 컨텍스트를 여러 전문가 에이전트에 분산하여 집중형 처리 환경을 조성합니다. 다중 에이전트 컨텍스트 경계를 사용하면 특정 전문 분야를 가진 에이전트를 생성할 수 있으며, 각 에이전트는 해당 도메인과 관련된 컨텍스트만 유지합니다. 전문가 에이전트 설계는 단일 에이전트로 모든 시나리오를 처리하려 하지 않고 특정 태스크에 맞게 에이전트를 최적화합니다. 컨텍스트 핸드오프 프로토콜은 대화 연속성을 유지하면서 분리된 컨텍스트 간의 정보 전송을 관리합니다. 이 접근 방식은 병렬 처리를 촉진하고 에이전트당 컨텍스트 복잡성을 낮춰 여러 도메인을 아우르는 복잡한 애플리케이션에 효과적입니다.

## 슬라이드 35. 컨텍스트를 전문가 에이전트로 분산

**다이어그램 (D2)**

```d2
direction: right
orch: "오케스트레이터 (최소 컨텍스트 · 태스크 라우팅 · 품질 가이드라인)"
research: "연구 에이전트 (연구 논문)"
analysis: "분석 에이전트 (데이터/통계)"
report: 보고서 에이전트
orch -> research
research -> analysis: 종합 결과
analysis -> report: 분석 결과
research -> report: 연구 인사이트
```

- 연구 에이전트
- 분석 에이전트
- 보고서 에이전트
- 연구 논문
- 오케스트레이터 에이전트
- 데이터 및 통계
- 연구 및 분석의 출력
- 최소 컨텍스트
- 태스크 라우팅
- 품질 가이드라인
- 컨텍스트

> **수강생용 노트**
>
> 구체적인 연구 워크플로 예제를 통해 이 오케스트레이터-전문가 패턴이 실제로 어떻게 작동하는지 살펴보겠습니다. 이 아키텍처 다이어그램은 오케스트레이터가 조정하는 3개의 에이전트 파이프라인을 보여줍니다.
>
> 오케스트레이터는 최상위에 위치하여 의도적으로 컨텍스트를 최소화하고 태스크 라우팅 로직 및 품질 지침만 사용합니다. 이러한 경량 설계는 확장성에 매우 중요합니다. 오케스트레이터는 도메인 콘텐츠를 처리하지 않고 워크플로 전반에 걸쳐 라우팅을 결정하고 품질 표준을 적용합니다.
>
> 워크플로는 3개의 전문가 에이전트를 통해 순차적으로 진행됩니다. 먼저, 연구 에이전트는 연구 논문 및 과학 문헌에 국한된 컨텍스트에서 활성화됩니다. 관련 출처를 검색하고, 주요 결과를 추출하고, 인용 및 인사이트를 포함한 구조화된 출력을 생성합니다. 결정적으로 이 출력은 전체 논문이 아니라 축약된 그러나 종합된 결과입니다.
>
> 이 축약된 출력은 분석 에이전트의 입력이 되며, 분석 에이전트는 이를 데이터 및 통계 방법론이라는 자체 컨텍스트와 결합합니다. 여기서 컨텍스트가 분리되어 있다는 점에 주목하십시오. 분석 에이전트는 절대로 원본 연구 논문을 볼 수 없습니다. 오로지 종합된 결과만 사용하므로 불필요한 컨텍스트로 인한 토큰을 수천 개 절약합니다. 이 에이전트는 정량 분석을 수행하고 추세를 식별하며 연구 컨텍스트와 비교하여 결과를 검증합니다.
>
> 마지막으로, 보고서 에이전트는 두 업스트림 에이전트로부터 출력을 수신합니다. 이 에이전트의 컨텍스트에는 이러한 처리된 결과, 연구 인사이트, 분석 결과가 포함되며, 이는 핵심 요약 및 권장 사항이 포함된 포괄적인 보고서로 통합됩니다.
>
> 에이전트 간의 핸드오프 프로토콜은 AgentCore Memory를 스테이징 영역으로 사용합니다. 각 에이전트는 출력을 처리 단계 및 신뢰도 점수를 나타내는 메타데이터와 함께 공유 메모리에 기록합니다. 다음 에이전트는 엄격한 컨텍스트 경계를 유지하면서 필요한 항목만 검색합니다.
>
> 점진적으로 컨텍스트가 구체화되는 이 순차적 파이프라인을 통해 개별 에이전트의 컨텍스트 요구 사항을 줄일 수 있습니다. 각 에이전트는 전체 워크플로 컨텍스트를 동시에 유지하려고 하지 않고 자신의 전문 지식에 최적화된 집중형 환경을 유지합니다.

## 슬라이드 36. 예제: 전문가 에이전트를 사용하여 컨텍스트 분리

- from strands_agents import Agent
- from specialized_agents import research, analyze, write_report
- # 라우팅 로직을 갖춘 오케스트레이터
- orchestrator = Agent(
- name="orchestrator",
- model="anthropic.claude-opus-4-5",
- instructions="""Coordinate research workflows. Route to: researcher for
- literature review, analyst for data analysis, writer for synthesis.
- Ensure quality at each stage.""",
- tools=[research, analyze, write_report] # 도구 함수 전달
- )
- result = orchestrator.run("Create market analysis on renewable energy")

> **강사용 노트**
>
> @tool 데코레이터 요구 사항을 언급: 에이전트는 도구로 사용하려면 먼저 래핑해야 합니다.
>
> 문제 격리를 강조: 전문가 에이전트가 별도의 모듈에 배치되고 오케스트레이터가 도구 함수를 가져옵니다.
>
> 컨텍스트 분리 이점과 연결: 각 에이전트는 도메인 관련 컨텍스트만 유지 관리합니다.
>
> 자주 묻는 질문을 해결: "왜 @tool 데코레이터를 사용해야 합니까?" - 이 데코레이터는 에이전트 호출 함수를 적절한 스키마 생성을 통해 LLM에서 호출 가능한 도구로 변환합니다.

> **수강생용 노트**
>
> 이 간결한 코드는 Strands의 도구로서의 에이전트 패턴의 우아함을 잘 보여줍니다. 기존의 오케스트레이션 접근 방식보다 훨씬 적은 코드로 동일한 오케스트레이터-전문가 아키텍처를 구현하고 있습니다.
>
> 이 패턴에는 2가지 주요 구성 요소가 필요합니다. 하나는 @tool 데코레이터로 래핑된 전문가 에이전트와 해당 도구 함수를 가져와서 사용하는 오케스트레이터입니다. specialized_agents.py 모듈에서는 최소한의 구문, 즉 이름 및 모델만으로 3개의 전문가 에이전트를 정의합니다. 연구 에이전트, 분석 에이전트, 보고서 에이전트는 각각 Claude Sonnet 4.5를 사용하여 인스턴스화됩니다. 명확성을 위해 지침 문자열을 포함할 수 있지만, 에이전트의 동작은 에이전트의 이름, 에이전트가 유지 관리하는 컨텍스트, 오케스트레이터가 에이전트에게 위임하는 방식에 따라서도 결정됩니다.
>
> 중요한 단계는 각 에이전트를 @tool 데코레이터로 래핑하는 것입니다. 이렇게 하면 에이전트를 호출하는 함수가 다른 에이전트에서 사용할 수 있는 도구로 변환됩니다. @tool 데코레이터는 함수 docstring 및 타입 힌트에서 메타데이터를 자동으로 추출하여 LLM이 보는 도구 스키마를 생성합니다. 각 도구 함수는 적절한 파라미터(예: 연구 쿼리 또는 데이터 설명)를 사용하고 에이전트의 응답과 함께 구조화된 사전을 반환합니다.
>
> 오케스트레이터는 Claude Opus 4.5를 사용하고 tools 파라미터를 통해 3가지 도구 데코레이션 함수를 수신합니다. 이는 도구로서의 에이전트 패턴의 핵심입니다. 전문가 에이전트가 @tool 데코레이터를 통해 호출 가능한 도구가 됩니다. 오케스트레이터는 연구가 필요한 태스크를 발견하면 자동으로 연구 도구를 간접적으로 호출합니다(내부적으로 연구 에이전트를 호출함). 분석이 필요한 경우 분석 도구를 호출합니다. 종합이 필요한 경우 보고서 도구에 위임합니다.
> 실행은 매우 간단합니다. 한 줄에 상위 수준의 태스크 설명이 있습니다. 백그라운드에서는 오케스트레이터의 추론이 최적의 위임 순서를 결정합니다. 연구 에이전트, 분석 에이전트, 보고서 에이전트를 순서대로 호출할 수도 있습니다. 또는 연구 에이전트 및 분석 에이전트를 동시에 호출한 후 보고서 에이전트와 종합할 수도 있습니다. 모델 기반 접근 방식이란 오케스트레이터가 사전 정의된 워크플로 로직 없이도 특정 태스크를 기반으로 전략을 조정한다는 의미입니다.
> 이 패턴은 실제 컨텍스트 분리를 보여줍니다. 각 전문가 에이전트는 도메인 관련 컨텍스트, 연구 논문, 통계 데이터 또는 보고서 출력만 관리합니다. 오케스트레이터는 각 도메인의 세부 정보를 이해할 필요 없이 조정합니다. 그 결과, 코드 복잡성을 최소화하면서 앞서 논의한 개별 에이전트 컨텍스트 요구 사항을 동일하게 50~70%까지 낮출 수 있습니다.
>
> 도구로서의 에이전트 패턴은 사전 정의된 엄격한 워크플로보다 모델 기반 위임의 유연성을 원하는 경우에 이상적입니다. 이는 프로덕션에 바로 사용할 수 있는 다중 에이전트 오케스트레이션을 간단하게 구현한 것으로, @tool 데코레이터가 에이전트를 도구처럼 호출할 수 있도록 하는 복잡한 과정을 처리합니다.

## 슬라이드 37. 활동

- 대규모 전자상거래 플랫폼을 위한 고객 지원 챗봇을 구축하는 AI 엔지니어
- 전략 선택 시나리오:
- 챗봇은 여러 제품 카테고리에서 고객 서비스 문의를 처리합니다.
- 주요 요구 사항:
- 며칠 또는 몇 주 동안 여러 번 재방문하는 고객을 지원
- 이전 대화, 주문 내역 및 고객 선호 사항을 기억
- 개별 채팅 세션에서 연속성을 유지
- 수천 개의 동시 대화를 처리
- 이전 메시지를 자주 참조하여 대화당 20~30회의 교환을 지원
- 이 시나리오에서 권장하는 메모리 최적화 전략은 무엇입니까? 그 이유는 무엇입니까?

> **강사용 노트**
>
> 시나리오를 다시 살펴봅니다.
>
> 일반적인 오해를 해결: 압축 전략 사고방식은 인정하되 세션 간 요구 사항과 세션 내 요구 사항을 명확히 구분합니다.
>
> 주요 의사결정 기준을 강조: 대화가 많은 애플리케이션, 상태 관리, 세션 간 지속성
>
> 현실 세계와 연결: 고객 지원을 위해 기록 전략을 사용하는 전자상거래 플랫폼 사례를 공유합니다.
>
> 학습 강화: 시나리오 특성이 기록 전략의 이점과 어떻게 매핑되는지 강조합니다.

> **수강생용 노트**
>
> 이 시나리오는 수천 개의 동시 대화를 처리하는 전자상거래 플랫폼을 위한 고객 지원 챗봇입니다. 고객은 며칠 또는 몇 주에 걸쳐 여러 번 재방문하며 "지난주에 배송에 대해 문의했을 때를 기억합니까?"와 같은 연속성을 기대합니다. 각 대화는 20~30회의 교환에 걸쳐 진행되며 자주 이전 메시지를 참조합니다. 문제는 대화가 길어질수록 컨텍스트 윈도우에 이전 주문 세부 정보, 배송 주소, 제품 선호 사항, 과거 불만 해결, 고객 서비스 기록이 가득 차 에이전트가 토큰 제한에 도달하여 중요한 컨텍스트를 잃게 된다는 것입니다. 권장 전력은 기록 전략입니다. 세션 간 지속성이 필요한 중요한 상태 관리 요구 사항이 있는 대화가 많은 애플리케이션이기 때문입니다. 기록 전략은 정보를 영구 스토리지(AgentCore Memory, DynamoDB, RDS)로 외부화하여 컨텍스트를 줄이는 동시에 챗봇이 여러 세션에서 고객 정보를 검색할 수 있도록 합니다. 세션 내 최적화뿐만 아니라 세션 간 상태 지속성이 핵심 요구 사항이기 때문에 이 접근 방식이 압축 전략보다 우수합니다. 기록 전략은 외부 스토리지 시스템을 통해 과거 정보에 대한 액세스를 유지하면서 컨텍스트 윈도우를 현재 대화 스레드에 집중합니다.
>
> 전략을 선택할 때는 중요한 상태 관리 요구 사항이 있는 대화가 많은 애플리케이션에는 기록 전략이 가장 적합하고, 지식 집약적 시나리오에는 선택 전략이 탁월하고, 광범위한 컨텍스트 축적이 필요한 장기 실행 세션에는 압축 전략이 적합하고, 복잡한 다중 도메인 애플리케이션에는 분리 전략이 유용하다는 점을 고려해야 합니다. 프로덕션 시스템에서는 여러 전략을 결합하는 경우가 많지만, 이 특정 시나리오에서는 기록 전략이 세션 간 상태 지속성이라는 주요 문제를 해결합니다.

> 4. 영향: "이러한 백분율은 프로덕션 시스템에서 흔히 볼 수 있는 패턴을 여실히 보여줍니다. 특정 연구 논문에서 나온 것이 아니라 실제 세계의 비효율성을 나타냅니다. 핵심 인사이트: 컨텍스트 중 35%가 중복 데이터인 경우 가치를 부가하지 않는 토큰에 비용을 지불하게 됩니다."
>
> 해당 백분율은 특정 연구에서 나온 것이 아니라 예시 및 대표적인 패턴임을 명확히 하십시오.

> **수강생용 노트**
>
> 도구 설계에서는 제한된 컨텍스트 윈도우 공간을 두고 경합하는 3가지 주요 소비 벡터로 인해 컨텍스트 효율성 문제가 대두됩니다. 도구 응답(일반적인 시스템의 경우 약 40%)은 API 직접 호출, 데이터베이스 쿼리, 파일 작업에서 반환된 실제 데이터를 나타냅니다. 모든 응답 페이로드는 토큰을 소비합니다. 작업 실패 시 스택 추적, 검증 오류, 디버깅 정보 등 오류 메시지(약 25%)가 오버헤드를 가중합니다. 중복 데이터(약 35%)는 숨겨진 비효율성을 나타냅니다. 즉, 도구의 기능이 중복되어 유사한 정보를 서로 다른 형식으로 반환하면, 호출을 여러 번 해야만 모든 정보를 수집할 수 있게 됩니다. 예를 들어 고객 데이터를 서로 다른 5개의 도구를 통해 따로따로 호출(기본 프로필, 구매 내역, 선호 사항, 연락처 정보, 로열티 상태)하는 경우, 통합된 1개의 도구를 사용할 때보다 훨씬 많은 컨텍스트를 소비하게 됩니다. 장황한 메타데이터, 응답 간 필드 중복, 불필요한 서식, 도구 간에 책임이 서로 겹치는 경우도 중복 데이터에 해당합니다. 이러한 백분율은 특정 연구 논문이 아닌 일반적인 프로덕션 패턴을 나타낸 것이지만, 비용과 성능 모두에 영향을 미치는 실제 비효율성을 나타냅니다. 목표는 시스템 기능은 유지하면서도, 소비한 토큰당 정보 가치를 극대화하는 것입니다.

## 슬라이드 42. 정보 집약형 응답 구현

- 구현 방식
- 계층적 JSON: 데이터 관계와 신선도를 설명하는 논리적 그룹화 및 메타데이터를 사용하여 응답을 구조화합니다. 그러면 에이전트가 정보를 효율적으로 분석할 수 있습니다.
- 스마트한 오류 처리: 상세한 스택 추적 없이 실행 가능한 정보를 제공합니다. 데이터를 사용할 수 없는 경우 긴 오류 메시지 대신 구조화된 'null' 응답을 반환합니다.
- 컨텍스트 인식 필터링: 에이전트의 현재 컨텍스트 또는 태스크를 기반으로 데이터 섹션의 우선순위를 지정하고 가장 관련이 있는 섹션만 반환합니다.

> **강사용 노트**
>
> 이 슬라이드를 슬라이드 35의 `getCompleteCustomerProfile()` 예제와 직접 연결합니다. 이들은 통합 도구의 응답을 구현하기 위한 원칙입니다.
>
> 구체적인 예제를 보여주기 전에 3가지 주요 구현 방법을 소개합니다.
>
> 각 접근 방식이 정보 밀도와 컨텍스트 효율성에 어떻게 기여하는지 설명합니다.
>
> 다음 슬라이드에서 이러한 원칙을 설명하는 구체적인 JSON 예제를 제시합니다.
>
> 다양한 응답 설계 시나리오에 어떤 접근 방식이 적용되는지 파악하는 연습을 합니다.

> **수강생용 노트**
>
> 이 슬라이드에서는 슬라이드 35의 통합 도구 아키텍처를 지원하는 정보 집약적 응답을 구현하기 위한 3가지 주요 접근 방식을 소개합니다. 계층적 JSON은 데이터 관계와 신선도를 설명하는 논리적 그룹화 및 메타데이터를 사용하여 응답을 구조화하므로 에이전트가 정보를 효율적으로 구문 분석할 수 있습니다. 스마트한 오류 처리는 데이터를 사용할 수 없을 때 긴 오류 메시지 대신 구조화된 null 응답을 사용하여 상세한 스택 추적 없이 실행 가능한 정보를 제공합니다. 컨텍스트 인식 필터링은 에이전트의 현재 컨텍스트 또는 태스크를 기반으로 가장 관련이 있는 데이터 섹션만 우선 반환합니다. 이러한 접근 방식은 함께 작동하여 명확성 및 실행 가능성을 유지하면서 소비된 토큰당 정보 가치를 극대화합니다.

>

> 단일 Gateway에서 API, Lambda, MCP 서버 대상을 혼합한 예제를 사용하여 도구 구성 가능성을 설명합니다.
>
> 자연어 쿼리로 시맨틱 검색 기능을 실행하여 지능적인 도구 검색을 제시합니다.
>
> 에이전트 코드 변경 없는 백엔드 진화의 유지 관리 이점을 강조합니다.
>
> 이 추상화 개념을 친숙한 API 게이트웨이와 서비스 메시 패턴에 연결합니다.

> **수강생용 노트**
>
> Gateway는 포괄적인 MCP 서버 구현 기능을 통해 표준화된 도구 검색과 호출 작업을 제공합니다. 에이전트는 도구 및 목록을 사용하여 이름, 설명, 파라미터 스키마와 함께 사용 가능한 도구를 검색하고, 도구 및 호출을 사용하여 제공된 인수로 특정 도구를 간접적으로 호출합니다. 이때 표준화는 기본 도구가 Lambda 함수든, REST API 또는 기타 MCP 서버든 상관없이 에이전트가 일정하게 상호 작용한다는 뜻입니다. Gateway는 모든 프로토콜 변환, 인증, 라우팅을 투명하게 처리합니다. 이러한 추상화 덕분에 하나의 Gateway 내에서 다양한 대상 유형을 조합할 수 있는 진정한 도구 구성이 가능하며, 에이전트는 이를 모두 동일한 MCP 도구로 인식합니다. 기업 배포의 경우 에이전트 코드를 변경하지 않고도 백엔드 구현을 발전시켜 시스템 진화 및 유지 관리를 위한 유연성을 제공할 수 있습니다. 또한 Gateway는 시맨틱 검색 기능을 지원하므로(활성화된 경우) 에이전트가 자연어 쿼리로 도구를 검색하여 대규모 카탈로그에서 지능적으로 도구를 선택할 수 있습니다.

>

>
> 컨텍스트 인식 필터링 원칙과 연결: 에이전트는 검색을 통해 현재 태스크를 기반으로 관련 도구의 우선순위를 지정할 수 있습니다.
>

> **수강생용 노트**
>
> AgentCore Gateway를 사용한 시맨틱 검색은 자연어 쿼리를 통해 지능적인 도구 검색을 지원하여 에이전트가 처리해야 하는 도구 수를 대폭 줄이고 컨텍스트 효율성을 개선합니다. Gateway 생성 시 시맨틱 검색을 활성화하면, Gateway가 전체 대상에서 모든 도구에 대한 벡터 임베딩을 자동으로 사전 계산하며 이를 통해 자연어 쿼리와 도구 설명이 의미를 기반으로 매칭될 수 있습니다. 그러면 에이전트는 x_amz_bedrock_agentcore_search 도구(검색이 활성화되면 도구 및 목록 응답에서 가장 먼저 표시됨)를 사용하여 '고객 지원 티켓 생성' 또는 '결제 트랜잭션 처리'와 같은 자연어 쿼리를 사용하여 도구를 검색할 수 있습니다. 에이전트는 전체 도구 카탈로그(여러 대상에 걸쳐 300개 이상의 도구가 포함될 수 있음)를 받는 대신, 쿼리 의도와 일치하는 가장 관련이 있는 도구(일반적으로 10개 이하)만 받습니다. 이 접근 방식은 에이전트가 현재 태스크 또는 사용 사례와 관련된 도구만 검색할 수 있도록 함으로써 컨텍스트 인식 필터링을 직접 지원하여 컨텍스트 소비를 크게 줄입니다.
>
> 예를 들어 3가지 대상(대상 1: 175개 도구, 대상 2: 150개 도구, 대상 3: 10개 도구)에서 300개 이상의 도구를 관리하는 Gateway는 검색이 없는 경우 300개 이상의 도구를 모두 반환하지만 '소셜 미디어 게시물 작성'과 같은 검색 쿼리를 사용하면 가장 관련이 있는 상위 10개 도구만 반환합니다. 이처럼 도구 카탈로그 크기가 감소하면 에이전트가 도구 정의에 사용하는 토큰이 훨씬 적어지므로 실제 도구 실행 및 응답 처리에 더 많은 컨텍스트를 사용할 수 있습니다. 시맨틱 검색은 Gateway가 여러 서비스, API, 함수에 걸친 방대하고 다양한 도구 카탈로그를 관리하는 엔터프라이즈 환경에서 특히 유용합니다. 검색 기능은 자연어 처리를 사용하여 쿼리 의도를 파악하고 이를 도구 설명, 이름 및 기능과 일치하도록 하므로 에이전트가 수동 도구 선택 또는 철저한 카탈로그 검색 없이 용이하게 적절한 도구를 찾을 수 있습니다. 이 기능은 Gateway 생성 중에 명시적으로 활성화해야 하며 생성 후에는 활성화할 수 없습니다. 따라서 대규모 도구 관리를 위한 Gateway 아키텍처를 설계할 때는 시맨틱 검색을 계획하는 것이 중요합니다.

### 2. 누락된 모범 사례 (본 모듈에 미수록 · 보완 권장)

- **AGENTPERF03-BP03 RAG 검색 파이프라인 최적화**: 시맨틱 청킹, 하이브리드 검색, 쿼리 변환, re-ranking, per-passage 관련성 임계값으로 첫 검색에서 1초 미만 지연으로 정밀한 컨텍스트를 확보합니다. 본 모듈은 "검색된 컨텍스트(RAG)"를 컨텍스트 범주로만 언급하고 파이프라인 최적화는 다루지 않습니다.

### 3. 충돌 및 업데이트

- Agentic AI Lens와의 **직접적 기술 충돌은 발견되지 않았습니다.** 본 모듈의 5대 컨텍스트 전략과 프롬프트 캐싱·컨텍스트 축소(40~60%) 서술은 Lens 성능/비용 기둥과 일관됩니다.
- 참고(내부 정합성, Lens 무관): 슬라이드 10 강사용 노트는 "32,000개 토큰 제한에 육박하는 31,500개"로 서술하나 슬라이드 9·10의 시나리오는 200,000개 토큰 윈도우를 사용합니다. Lens 기준과는 무관하나 강의 내 수치 정합성 점검을 권장합니다.
- 참고: 슬라이드 11의 "컨텍스트 파일 75% 제한·자동 삭제"는 특정 제품 동작에 대한 서술로, Agentic AI Lens는 이에 대한 보편 규칙을 규정하지 않습니다(상충 아님).
