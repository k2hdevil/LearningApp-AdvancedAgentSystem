## 슬라이드 3. 에이전틱 AI 보안의 기초

- 에이전틱 AI 애플리케이션에는 생성형 AI의 모든 보안 위험이 여전히 존재합니다.
- 에이전틱 AI는 LLM에서 수행하는 자동화된 작업으로 인해 추가 보안 위험을 초래합니다.
- 기존 애플리케이션에 사용되는 보안 제어는 에이전틱 AI 워크로드에도 적용됩니다.
- 에이전틱 AI의 보안은 엔터프라이즈 애플리케이션과 로컬에 배포된 애플리케이션에 모두 적용됩니다.
- 에이전틱 AI는 여전히 진화하고 있으므로 새로운 위협 및 트렌드에 대한 최신 정보를 지속적으로 파악해야 합니다.

> **수강생용 노트**
>
> 이전에 우리는 생성형 AI 보안에 대해 논의했습니다. AWS는 AWS Generative AI Security Scoping Matrix와 같은 리소스를 개발했습니다. OWASP, MITRE, NIST는 생성형 AI의 보안을 고려하는 방법에 대한 리소스를 작성했습니다. 이 모든 것을 종합해 볼 때, 생성형 AI 애플리케이션에 적용되는 모든 보안 및 안전 위험은 에이전틱 AI 애플리케이션에도 여전히 적용됩니다. 아키텍처 내에서 LLM을 사용하는 데 초점이 맞춰졌기 때문입니다.
> 에이전트에서는 모든 생성형 AI 보안 위험 외에도 앞서 설명한 기능 및 에이전트가 수행할 수 있는 자동화(메모리 액세스, 도구 액세스, 추론 그리고 단순히 데이터 가져오기 또는 도구 및 애플리케이션 변경 또는 쓰기가 아닌 작업)로 인해 추가 보안 위험이 발생합니다.
> 보안 관점에서 보면 기존 워크로드에 사용하는 것과 동일한 유형의 보안 제어(자격 증명, 인프라 보호, 데이터 보호, 애플리케이션 보호, 위협 탐지 및 대응)가 에이전트 워크로드에도 계속 사용됩니다. 그러나 프롬프트 자체에 존재하는 안전성 문제 외에도 워크로드 내에서 이들을 올바르게 사용하는 방법을 고려해야 합니다.
> 또한 생성형 AI 애플리케이션에서 그다지 많이 등장하지 않은 영역 중 하나는 IDE와 같은 사용자 디바이스의 로컬 배포였습니다. 사용자 디바이스에서 Q Developer 또는 다른 로컬 모델 등을 사용할 수도 있지만, 이는 모델에 대한 쿼리 및 응답 방식이었습니다. 에이전트에서는 사용자가 GitHub에서 다운로드한 MCP 서버 및 도구를 로컬에 배포하고 로컬 stdio 구조를 통해 자격 증명 컨텍스트를 전달하게 되는데, 이는 사용자 및 조직에 더 많은 보안 문제를 제기할 수 있습니다.
> 마지막으로, 생성형 AI와 마찬가지로 에이전틱 AI도 빠르게 진화하는 분야로, 매일까지는 아니더라도 매주 변화가 일어나고 있습니다. 보안 조직으로서, 팀원들은 새로운 위협 및 트렌드를 파악하고, 기업이 배포하는 에이전트뿐 아니라 사용자가 자신의 디바이스에서 에이전트를 사용하는 방식까지 고려하여 적절한 보안 구조를 제공하는 방법을 숙지해야 합니다.
>
> 지금까지 에이전트와 관련된 새로운 위협에 대해 말씀드렸습니다. 이제 이것이 구체적으로 무엇을 의미하는지 자세히 살펴보겠습니다.

## 슬라이드 4. Agentic AI Security Scoping Matrix

**다이어그램 (D2)**

```d2
direction: right
s1: "범위 1 · 대리권 없음 (사람 시작, 변경 없음)"
s2: "범위 2 · 규정된 대리권 (사람 승인 필요)"
s3: "범위 3 · 감독되는 대리권 (사람 트리거, 자동 실행)"
s4: "범위 4 · 전체 대리권 (자체 개시, 완전 자율)"
s1 -> s2 -> s3 -> s4: 대리권 + 위험 증가
```

- 대리권 없음:
- 사람이 시작, 에이전틱 변경 금지
- 정의된 경로를 따르지만 시스템에서 변경을 실행할 수 없는 에이전트
- 예: 사용자가 에이전트에게 서로 시간이 맞는 일정을 찾아달라고 요청하고 사용자가 회의를 예약합니다.
- 범위 1
- 규정된 대리권:
- 사람이 시작, 사람이 승인한 에이전트 작업
- 변경 사항을 실행할 수 있지만 휴먼 인 더 루프(HITL) 개시, 검토 및 승인이 필요한 에이전트
- 예: 사용자가 에이전트에게 서로 시간이 맞는 일정을 찾아달라고 요청하고 사람이 검토한 후 에이전트가 회의를 예약합니다.
- 범위 2
- 감독되는 대리권:
- 사람이 시작, 자동화된 에이전트 작업
- 자율 에이전트 작업이 포함된 사람이 트리거하는 AI 워크플로
- 예: 사용자가 에이전트에게 서로 시간이 맞는 일정을 찾아달라고 요청하고 에이전트가 자동으로 회의를 예약합니다.
- 범위 3
- 전체 대리권:
- 자동 개시, 자동화된 에이전트 작업
- 자율 에이전트 작업이 가능한 자체 개시 AI
- 예: 환경이 에이전트를 트리거하고 자동으로 서로 시간이 맞는 일정을 예약합니다.
- 범위 4
- 대리권 + 위험
- 더 적음
- 더 많음
- 중요 보안 차원
- 자격 증명 컨텍스트(AuthN + AuthZ)
- 데이터, 메모리 및 상태 보호
- 감사 및 로깅
- 에이전트 및 FM 제어
- 대리권 경계 및 정책
- 오케스트레이션

> **강사용 노트**
>
> 보안 차원 요구 사항이 범위 전반에 걸쳐 어떻게 증가하는지 설명합니다.
>
> 각 범위 수준별로 수강생 조직의 실제 에이전트를 보여줍니다.
>
> 다양한 에이전트 시나리오에 어떤 범위가 적용되는지 식별하는 연습을 합니다.
>
> 대리권 + 위험 원칙 및 규정 준수에 미치는 영향에 대해 논의합니다.
>
> 방문: https://aws.amazon.com/blogs/security/the-agentic-ai-security-scoping-matrix-a-framework-for-securing-autonomous-ai-systems/

> **수강생용 노트**
>
> Agentic AI Security Scoping Matrix는 에이전트마다 다른 규정 준수 접근 방식이 필요한 이유를 이해할 수 있는 프레임워크를 제공합니다. 에이전트는 다음과 같은 4가지 고유한 자율성 범위로 운영됩니다.
>
> 범위 1은 에이전트가 사전 정의된 경로를 따르고 시스템 변경을 실행할 수 없는 대리권 없음을 나타냅니다. 예를 들어, 사용자가 에이전트에게 서로 시간이 맞는 일정을 찾아달라고 요청하면 에이전트는 명시적 승인을 받은 후에만 회의를 예약합니다.
> 범위 2는 에이전트가 변경을 시작할 수 있지만 각 단계에서 휴먼 인 더 루프 승인이 필요한 규정된 대리권입니다. 예를 들어, 사용자가 서로 시간이 맞는 일정을 찾아달라고 요청하면 에이전트가 옵션을 제안하고 예약 전에 사람의 검토를 기다립니다.
> 범위 3은 사람이 워크플로를 트리거하지만 에이전트가 해당 워크플로 내에서 자율적인 작업을 실행하는 감독되는 대리권입니다. 예를 들어, 사용자가 서로 시간이 맞는 일정을 찾아달라고 요청하면 에이전트가 사전 정의된 제약 조건 내에서 자동으로 예약합니다.
> 범위 4는 에이전트가 스스로 작업을 시작 및 실행하는 전체 대리권입니다. 예를 들어, 사람의 개입 없이 환경이 에이전트를 트리거하고, 에이전트가 서로 시간이 맞는 일정을 찾아 예약합니다.
>
> 모든 범위에 걸쳐 AuthN 및 AuthZ를 사용하는 자격 증명 컨텍스트, 데이터 메모리 및 상태 보호, 감사 및 로깅 기능, 에이전트 행동을 제어하는 Agency FM 제어, 경계를 정의하는 파라미터 및 정책, 다중 에이전트 상호 작용을 관리하는 오케스트레이션이라는 6가지 핵심 보안 차원을 다뤄야 합니다. 범위 1에서 범위 4로 이동함에 따라 대리권 + 위험 원칙에 따라 각 차원에 요구되는 정교성이 상향됩니다. 이 매트릭스는 규정 준수를 일률적으로 적용할 수 없는 이유를 설명합니다. 범위 1 읽기 전용 연구 에이전트는 프로덕션 데이터베이스를 수정하는 범위 4 자율 에이전트와는 다른 제어 기능이 필요합니다.

## 슬라이드 5. OWASP Agentic AI: 위협 및 방어

**다이어그램 (D2)**

```d2
direction: right
input: "입력" {
  prompt: 사용자 프롬프트
  api: API
  ext: 외부 에이전트
}
proc: "통합 및 처리" {
  gov: 정책 및 거버넌스
  hitl: 휴먼 인 더 루프
  mem: 메모리
  rag: "연결된 데이터 및 RAG"
  a1: 에이전트 1
  a2: 에이전트 2
}
output: "출력" {
  tools: 도구
  res: "API 및 리소스"
  ext2: 외부 에이전트
}
input -> proc -> output
```

- 입력
- 통합 및 처리
- 출력
- 사용자 프롬프트
- API
- 외부 에이전트
- 정책 및 거버넌스
- 휴먼 인 더 루프
- 메모리
- 연결된 데이터 및 RAG
- 에이전트 1
- 에이전트 2
- 도구
- API 및 리소스
- 외부 에이전트

> **강사용 노트**
>
> OWASP 생성형 AI 보안 프로젝트는 에이전틱 AI를 사용하는 시스템이 직면한 10대 보안 취약점을 식별했습니다.
>
> 에이전트 목표 하이재킹 - 공격자가 프롬프트 인젝션 또는 오염된 데이터를 통해 에이전트의 목표를 조작하여 에이전트를 유해한 결과로 유도합니다.
> 자격 증명 및 권한 남용 - 에이전트가 신뢰 메커니즘을 악용하여 위임 체인 및 역할 상속을 통해 액세스 권한을 의도된 범위 이상으로 에스컬레이션합니다.
> 인간-에이전트 신뢰 악용 - 공격자가 AI 에이전트에 대한 인간의 신뢰를 악용하여 의사결정에 영향을 미치거나, 정보를 추출하거나, 사용자를 조종하여 유해한 행동으로 유도합니다.
> 메모리 및 컨텍스트 포이즈닝 - 공격자가 악성 데이터로 저장된 에이전트 정보를 손상하여 편향된 추론 및 안전하지 않은 미래 작업을 유발합니다.
> 안전하지 않은 에이전트 간 통신 - 에이전트 간 인증이 취약하면 공격자가 다중 에이전트 시스템에서 메시지를 가로채거나 조작하거나 도용할 수 있습니다.
> 악성 에이전트 - 손상된 에이전트가 의도된 기능에서 벗어나 목표 이탈, 워크플로 하이재킹 또는 다른 악성 에이전트과의 조정을 통해 악의적으로 행동합니다.
> 도구 오용 및 악용 - 에이전트가 프롬프트 인젝션 또는 안전하지 않은 위임으로 인해 합법적인 도구를 오용하고, 이는 데이터 도난 또는 워크플로 손상으로 이어집니다.
> 에이전트 공급망 취약성 - 서드 파티 에이전트 구성 요소에는 악성 코드, 숨겨진 지침 또는 에이전트 시스템으로 침투하는 손상된 기능이 포함되어 있을 수 있습니다.
> 예기치 않은 코드 실행 - 공격자가 에이전트 코드 생성 기능을 악용하여 프롬프트 인젝션을 통해 원격 코드 실행 또는 시스템 손상을 달성합니다.
> 연쇄 장애 - 단일 장애가 자율 에이전트 네트워크 전반으로 전파되어 인적 감독 체크포인트 없이 시스템 전체 장애로 확대됩니다.

## 슬라이드 6. 심층 방어 보안 접근 방식

**다이어그램 (D2)**

```d2
direction: up
l1: "1. 정책, 절차 및 인식"
l2: "2. Identity & Access 관리"
l3: "3. 인프라 보호"
l4: "4. 네트워크 및 엣지 보호"
l5: "5. 애플리케이션 보호"
l6: "6. 데이터 보호"
l7: "7. 위협 탐지 및 사고 대응"
l1 -> l2 -> l3 -> l4 -> l5 -> l6 -> l7
```

- 위협 탐지 및 사고 대응
- 데이터 보호
- 애플리케이션 보호

**다이어그램 (D2)**

```d2
direction: right

```

- 사용자
- 에이전트
- AgentCore Runtime
- AgentCore Gateway
- AgentCore Identity
- AgentCore Policy
- 도구

> **강사용 노트**
>
> 복습용으로 사용 - 이 강의에서 이러한 단계에 대해 자세히 설명합니다.
>
> 수강생용 노트에이전틱 AI 시스템에서 자격 증명 및 액세스를 관리하려면 사용자가 에이전트에 액세스하는 방법과 에이전트가 외부 리소스에 액세스하는 방법을 모두 보호하는 포괄적인 접근 방식이 필요합니다. 자격 증명 및 액세스 관리 프로세스의 개괄적인 흐름은 다음과 같습니다.
> 1. 사용자 인증: 사용자는 OAuth 2.0 또는 OpenID Connect 프로토콜을 사용하여 IdP(Identity Provider: 자격 증명 공급자)를 통해 인증합니다. 이 초기 인증은 사용자의 자격 증명을 확인하고 상호 작용 전반에 걸쳐 사용될 자격 증명을 생성합니다.
> 2. AgentCore Gateway와 함께 에이전트 도구 사용: 사용자의 요청에 따라 에이전트가 AgentCore Gateway를 통해 도구를 호출할 수 있습니다.
> 3. AgentCore Identity를 사용한 인바운드 인증: AgentCore Identity는 OAuth 2.0 프로토콜을 사용하여 인바운드 요청을 검증합니다. 이 인바운드 인증 단계는 에이전트를 간접적으로 호출하려는 사용자 또는 서비스에 적절한 권한이 부여되었는지 확인합니다.
> 4. 아웃바운드 권한 부여 및 JWT 토큰 생성: 인바운드 요청을 검증한 후 AgentCore Identity는 아웃바운드 인증을 수행합니다. 서비스는 보안 토큰 저장소에서 필요한 자격 증명을 검색하고 에이전트가 다운스트림 리소스에 액세스하는 데 사용하는 JWT 토큰을 발급합니다. 이 토큰에는 도구 호출에 필요한 권한 부여 컨텍스트가 포함되어 있습니다.
> 5. AgentCore Policy를 통한 정책 평가: 도구 호출이 진행되기 전에 AgentCore Gateway는 요청을 JWT 토큰과 함께 AgentCore Policy로 보냅니다. 정책 엔진은 요청을 보내는 에이전트, 액세스 중인 리소스, 수행 중인 작업과 같은 요소를 검토하여 정의된 Cedar 정책에 따라 요청을 평가합니다.
> 6. 정책 결정: 허용 또는 거부: AgentCore Policy는 권한 부여 결정을 'allow' 또는 'deny'로 응답합니다. 이 결정은 에이전트가 사용자 대신 수행할 수 있는 작업을 정의하는 구성된 정책을 기반으로 하여 조직의 보안 요구 사항을 준수하도록 합니다.
> 7. 도구 호출 실행: 정책 평가가 'allow' 결정을 반환하면 도구 호출이 대상 서비스로 진행됩니다.

## 슬라이드 11. AWS IAM을 사용하여 AgentCore Runtime에서 에이전트에 액세스

- AgentCore Runtime이 AWS 리소스에 대한 액세스를 정의하는 IAM 실행 역할을 수임합니다.
- 사용자
- 에이전트 또는 MCP 서버
- AWS IAM(Sigv4)
- Sigv4 자격 증명
- IAM 실행 역할
- AWS 리소스
- AgentCore Identity
- AgentCore Runtime

> **강사용 노트**
>
> 사용자 동의 흐름 및 토큰 관리 프로세스를 살펴봅니다.

> **수강생용 노트**
>
> 인바운드 인증: 사용자 자격 증명 권한 부여

> 사용자가 AgentCore Runtime에서 에이전트를 간접적으로 호출하는 경우:
> AWS IAM 자격 증명을 사용하여 사용자를 인증(SigV4 서명 프로세스)
> 각 요청은 호출자의 자격 증명을 확인하기 위해 암호화 방식으로 서명됩니다.
> 런타임은 요청을 처리하기 전에 자격 증명을 검증합니다.
> 감사 및 액세스 제어를 위해 세션 내내 사용자 자격 증명이 보존됩니다.
>
> 아웃바운드 인증: IAM 역할을 통한 리소스 액세스
> 방법: 런타임이 수임하는 AWS IAM 실행 역할
> 에이전트가 AWS 리소스에 액세스해야 하는 경우:
> AgentCore Runtime이 에이전트를 대신하여 IAM 실행 역할을 수임합니다. 이 역할에는 에이전트가 액세스할 수 있는 AWS 서비스 및 리소스를 정의하는 권한 정책이 포함되어 있습니다.
> 역할 기반 권한으로 표준 AWS SDK 호출을 사용하여 리소스에 액세스할 수 있습니다.

## 슬라이드 12. OAuth - 2-Legged 인증(2LO)

**다이어그램 (D2)**

- 클라이언트 자격 증명
- 앱
- 클라이언트 애플리케이션
- 권한 부여 서버
- 보호되는 리소스
- 액세스할 서비스 또는 도구

>
> 흐름 설명
> OAuth 2.0 클라이언트 자격 증명 흐름은 애플리케이션이 사용자 상호 작용 없이 자신이 소유한 리소스 또는 서비스 계정 리소스에 액세스하는 M2M(Machine-to-Machine: 사물 지능 통신) 인증 방법입니다.

> 클라이언트 인증: 애플리케이션이 client_id 및 client_secret을 권한 부여 서버의 토큰 엔드포인트로 보냅니다.
> 토큰 발급: 서버가 자격 증명을 검증하고 access_token을 반환합니다(이 흐름에서는 새로 고침 토큰이 발급되지 않음).
> 리소스 액세스: 애플리케이션이 액세스 토큰을 사용하여 보호되는 리소스에 액세스합니다.
> 사용 사례:
> 사용자 상호 작용이 필요 없는 시스템 간 인증
> 데이터 동기화, 이벤트 기반 워크플로, 마이크로서비스 통신과 같은 자동화된 프로세스
> 동일한 계정 내에서 API 또는 데이터베이스에 액세스하는 백엔드 서비스
> 보안 고려 사항:
> 인증에 클라이언트 암호가 필요합니다.
> 액세스 토큰은 임시적이고 사용 기한이 있습니다.
> 승인에 관련된 사용자 컨텍스트가 없습니다.
> 요청이 권한 부여 엔드포인트를 완전히 우회하고 토큰 엔드포인트로 직접 이동합니다.

> 인바운드 인증 방법:
> AgentCore Gateway는 인바운드 요청을 검증하기 위한 2가지 기본 방법을 지원합니다. IAM 기반 인증은 AWS Signature Version 4(SigV4)에서 AWS Identity and Access Management 자격 증명을 사용하여 게이트웨이를 호출하는 사용자 또는 서비스의 자격 증명을 확인합니다. 이 방법은 특정 게이트웨이 리소스에 액세스할 수 있는 AWS 보안 주체에 대한 세분화된 제어를 제공합니다. OAuth 토큰 인증은 Model Context Protocol(MCP) 권한 부여 사양을 따르며 자격 증명 공급자의 OAuth 2.0 보유자 토큰을 검증합니다. 이 접근 방식은 최종 사용자가 외부 자격 증명 공급자를 통해 인증하는 사용자 위임 액세스 시나리오에 특히 유용합니다.
> 아웃바운드 권한 부여 방법:
> 게이트웨이는 인증된 사용자를 대신하여 백엔드 서비스에 액세스해야 하는 경우 3가지 권한 부여 전략을 사용합니다. AWS IAM 권한 부여는 게이트웨이 서비스 역할의 자격 증명을 사용하여 SigV4 서명을 사용하는 백엔드 AWS 서비스에 인증합니다. API 키 권한 부여는 AgentCore Identity의 보안 토큰 저장소에서 API 키를 검색하여 서드 파티 서비스에 대한 요청에 포함합니다. 토큰 기반 권한 부여(OAuth)는 AgentCore Identity로부터 액세스 토큰을 획득하며, 시스템 간 인증을 위한 클라이언트 자격 증명 부여와 사용자 위임 액세스 시나리오를 위한 권한 부여 코드 부여를 모두 지원합니다.
> 이 양방향 보안 모델은 사용자와 대상 리소스 사이에 안전한 연결을 구축하여 게이트웨이 액세스 및 백엔드 서비스 호출을 적절히 인증하고 권한을 부여하는 동시에 요청 수명 주기 전반에 걸쳐 포괄적인 감사 추적을 유지합니다.

- 에이전트가 비즈니스 정책을 오해하여, 그럴듯해 보이지만 규정 준수 제약 조건을 위반하는 조치를 취할 가능성
- 데이터 노출
- 에이전트가 실수로 개인 정보를 유출하거나 승인된 범위를 벗어난 민감한 데이터에 액세스할 가능성

> **수강생용 노트**
>

>
> 자율적으로 추론하고 행동할 수 있기 때문에 그 성능은 강력하지만 기존 제어로는 억제하기 어려운 거버넌스 위험이 발생할 수 있습니다.
>
> 에이전트는 신중하게 설계되었더라도 동적인 특성 때문에 부적절하게 데이터에 액세스하거나, 승인된 범위를 벗어난 결정을 내리거나, 예상치 못한 방식으로 고객과 상호 작용하거나, 계획되지 않은 조치를 취하려고 할 수 있습니다.
>
> 이는 현실 세계에서 다양한 방식으로 나타날 수 있습니다.

## 슬라이드 21. AgentCore Policy 권한 부여 흐름(4/4)

- 정책 평가 프로세스
- Cedar는 다음을 평가합니다.
- 보안 주체 검사: 보안 주체가 OAuthUser인가? ✓ (일치)
- 작업 검사: 작업이 RefundTool__process_refund인가? ✓ (일치)
- 리소스 검사: 리소스가 환불 게이트웨이인가? ✓ (일치)
- 조건 검사:
- 보안 주체에게 username 태그가 있는가? ✓ (예, JWT)
- username = 'refund-agent'인가? ✓ (예)
- context.input.amount가 500보다 작은가? ✓ (450 < 500)
- 결과: 허용 - 모든 검사가 통과되면 환불이 승인됩니다.

> **수강생용 노트**
>
> Cedar의 정책 평가는 권한 부여 요청의 여러 측면을 확인하는 체계적인 프로세스를 따릅니다. 평가는 요청을 하는 엔터티가 정책에 정의된 예상 유형과 일치하는지 확인하는 보안 주체 검사로 시작됩니다. 이 경우 Cedar는 보안 주체가 실제로 OAuthUser 엔터티임을 확인하여 요청이 인증된 OAuth 사용자로부터 나온 것인지 확인합니다.
>
> 다음으로 작업 검사는 요청되는 특정 작업이 정책에서 제어하는 작업과 일치하는지 확인합니다. Cedar는 해당 작업이 RefundTool__process_refund 작업임을 확인하여 정책이 이 특정 도구 호출에 적용되는지 확인합니다. 그런 다음 리소스 검사는 요청이 올바른 Gateway 인스턴스를 대상으로 하고 있음을 확인하여 정책의 리소스 사양이 액세스 중인 실제 게이트웨이와 일치하는지 확인합니다.
>
> Cedar 평가의 가장 강력한 측면은 속성 기반 및 컨텍스트 인식 승인 결정을 가능하게 하는 조건 검사입니다. Cedar는 보안 주체 엔터티에 JWT 토큰의 필수 태그가 있는지 확인한 다음 사용자 이름과 같은 특정 속성값을 평가합니다. 또한 Cedar는 환급액이 지정된 임계값 이하인지 확인하는 등 도구 호출에서 전달되는 실제 파라미터를 평가할 수 있습니다.
>
> 모든 검사가 통과하고, 보안 주체 유형이 일치하고, 작업이 일치하고, 리소스가 일치하고, 모든 조건이 true로 평가되면 Cedar가 허용 결정을 반환하고 도구 호출이 대상 서비스로 진행됩니다. 검사가 실패할 경우 Cedar는 거부 결정을 반환하고 요청이 차단되어 에이전트 작업에 대한 보안 경계가 유지됩니다.

## 슬라이드 23. 조건부 허가 정책 예제

- 자연어 프롬프트:
- "취소 사유가 'fraud_detected'인 경우에는 회사에서 취소를 개시한 경우에만 계산 금액을 환불하십시오."
- permit (
- principal,
- action == MCP::Action::"refund_calculator",
- resource
- )
- when {
- context.input.initiated_by == MCP::refund_calculator::Input::initiated_by::"company" &&
- context.input.cancellation_reason == MCP::refund_calculator::Input::cancellation_reason::"fraud_detected"
- };

> **강사용 노트**
>
> 이 슬라이드는 모두 충족되어야 하는 여러 조건을 포함하는 허가 정책을 보여줍니다. 자연어 프롬프트가 어떻게 Cedar 정책 구문으로 직접 변환되는지 설명하십시오.
>
> 주요 교수 포인트:
>
> - 정책이 허가 효과를 사용하여 특정 조건이 충족되는 경우에만 작업을 허용하는 방법을 보여줍니다.
>
> - 허가를 적용하려면 2가지 조건이 모두 true(AND 로직)이어야 한다고 설명합니다.
>
> - 규정 준수를 위해 이러한 유형의 조건부 허가가 필요한 실제 시나리오에 대해 논의합니다.
>
> 정책 구조 살펴보기:
>
> 1. 효과: 허가 - 조건 충족 시 작업을 허용
>
> 2. 범위: 모든 리소스에 대한 refund_calculator 작업
>
> 3. 조건: 개시자가 '회사'여야 하고 그리고 취소 사유가 '사기 행위 탐지'여야 함
>
> 이는 보안 제어라는 점을 강조하십시오. 사기 행위로 인한 환불은 회사에서 환불을 시작할 때만 허용되므로 에이전트가 적절한 승인 없이 사기 관련 환불을 자동으로 처리하는 것을 방지합니다.

> **수강생용 노트**
>
> 이 슬라이드는 작업 수행 시기를 제한하는 조건부 논리가 포함된 허용 정책을 보여줍니다. 자연어 프롬프트에는 다음과 같이 명시되어 있습니다. "취소 사유가 '사기 행위 탐지'인 경우 회사에서 시작한 경우에만 계산 금액을 환불하십시오."
>
> Cedar 정책은 AND 논리 연산자(&&)로 연결된 2가지 조건을 포함하는 when 절과 함께 permit 스테이트먼트를 사용하여 이 요구 사항을 구현합니다. 정책 구조는 다음과 같이 구분됩니다.
>
> 효과: permit 키워드는 조건이 충족될 때 이 정책이 작업을 허용한다는 것을 나타냅니다. 조건이 충족되지 않으면 정책이 적용되지 않으며 다른 정책 또는 기본 동작에 따라 권한 부여가 결정됩니다.
>
> 범위: 이 정책은 모든 보안 주체 및 리소스의 refund_calculator 작업(MCP::Action::"refund_calculator")에 적용됩니다. 즉, 인증된 사용자 또는 에이전트는 조건이 충족된 경우에만 이 작업을 트리거할 수 있습니다.
> 조건: when 절에는 모두 true로 평가되어야 하는 2가지 조건이 포함됩니다.
> 1. context.input.initiated_by == MCP::refund_calculator::Input::initiated_by::"company" - 고객이나 자동화 시스템이 아닌 회사가 환불 계산을 개시했는지 확인합니다.
> 2. context.input.cancellation_reason == MCP::refund_calculator::Input::cancellation_reason::"fraud_detected" - 취소 사유가 정확히 'fraud_detected'인지 확인합니다.
>
> context.input 객체를 사용하면 정책이 도구 호출 요청에서 전달되는 실제 파라미터를 평가할 수 있습니다. 이를 통해 정적 자격 증명 속성뿐만 아니라 런타임 데이터를 기반으로 세분화된 권한 부여가 가능합니다.
>
> 실제 사용 사례: 이 정책은 명백히 회사가 환불 계산을 개시한 경우가 아니면 에이전트가 사기 관련 환불을 자동으로 처리하지 못하도록 합니다. 사기 관련 환불에는 추가 확인, 수동 검토 또는 자동화하면 안 되는 특별 처리가 필요할 수 있으므로 이는 중요한 보안 제어입니다. 이 정책은 회사가 개시해야 한다는 조건을 통해 사기 관련 환불이 적절한 승인 워크플로를 거치도록 합니다.
>
> AND 연산자(&&)는 2가지 조건이 동시에 true여야 함을 의미합니다. 2가지 조건 중 하나가 false이면 허가가 적용되지 않으며 다른 정책 또는 기본 작업으로 인해 작업이 거부될 수 있습니다.

## 슬라이드 24. 조건부 금지 정책 예제

- 자연어 프롬프트:
- "18세 미만 또는 85세 초과 고객에 대해서는 자동차 보험 견적을 생성하지 마십시오."
- forbid (
- principal,
- action == MCP::Action::"quote_generator",
- resource
- )
- when {
- context.input.coverage_type == MCP::quote_generator::Input::coverage_type::"auto" &&
- context.input.customer_info has age &&
- (context.input.customer_info.age < 18 || context.input.customer_info.age > 85)
- };

> **강사용 노트**
>
> 이 슬라이드는 OR 연산자 및 속성 존재 검사를 사용하는 복잡한 조건부 논리가 포함된 금지 정책을 보여줍니다. 이는 안전하지 않은 에이전트 작업을 방지하기 위한 중요한 패턴입니다.
>
> 주요 교수 포인트:
>
> - 금지 정책이 다른 방법으로 허용될 수 있는 활동을 차단하는 방식을 설명합니다.
>
> - 평가 전에 속성 존재를 확인하는 has 연산자를 설명합니다.
>
> - 적용 범위 유형 검사, 연령 속성 검사, 연령 범위 검사의 3개 부분으로 구성된 조건 구조를 살펴봅니다.
>
> 정책 구조 살펴보기:
>
> 1. 효과: 금지 - 조건이 충족되면 작업을 명시적으로 차단
>
> 2. 범위: 자동차 보험을 위한 quote_generator 작업
>
> 3. 조건: 3단계 검사 - 적용 범위 유형은 'auto'여야 하고, 고객 정보에는 연령 속성이 있어야 하고, 연령은 허용 범위(18세 미만 또는 85세 초과)가 아니어야 함
>
> 이 정책은 에이전트가 규제 요구 사항 또는 비즈니스 규칙을 위반할 수 있는 견적을 생성하는 것을 방지한다는 점을 강조합니다(에이전트가 자체 추론에 따라 계속 진행해야 한다고 제안하더라도 마찬가지).

> **수강생용 노트**
>
> 이 슬라이드는 에이전트가 비즈니스 규칙 또는 규정 요구 사항을 위반하는 작업을 수행하지 못하도록 하는 금지 정책을 보여줍니다. 자연어 프롬프트에는 다음과 같이 명시되어 있습니다. "18세 미만 또는 85세 초과 고객에 대해서는 자동차 보험 견적을 생성하지 마십시오."
> Cedar 정책은 여러 조건을 포함하는 when 절이 포함된 forbid 스테이트먼트를 사용하여 이 제한을 구현합니다. 정책 구조는 다음과 같이 구분됩니다.
> 효과: forbid 키워드는 조건이 충족될 때 작업을 명시적으로 차단합니다. 조건부로 작업을 허용하는 허용 정책과 달리, 금지 정책은 다른 정책으로 무시할 수 없는 엄격한 경계를 설정합니다.
> 범위: 이 정책은 모든 보안 주체 및 리소스의 quote_generator 작업(MCP::Action::"quote_generator")에 적용됩니다. 즉, 제한은 이 작업에 대한 모든 견적 생성 시도에 보편적으로 적용됩니다.
> 조건: when 절에는 3개 부분이 모두 AND 논리 연산자(&&)로 연결된 복합 조건이 포함됩니다.
> 1. context.input.coverage_type == MCP::quote_generator::Input::coverage_type::"auto" - 이 1번째 조건은 정책이 자동차 보험 견적에만 적용되며 주택 또는 생명 보험과 같은 다른 적용 범위 유형에는 적용되지 않도록 합니다.
>
> 2. context.input.customer_info has age - 이 조건은 has 연산자를 사용하여 평가 전에 customer_info 객체에 age 속성이 포함되어 있는지 확인합니다. 이는 입력에서 age 속성이 누락될 경우 오류를 방지하는 방어적인 프로그래밍 방식입니다.
> 3. (context.input.customer_info.age < 18
>
> context.input.customer_info.age > 85) - 이 3번째 조건은 OR 논리 연산자(
>
> )를 사용하여 고객의 연령이 18세 미만 또는 85세 초과인지 확인합니다. 1가지 조건이라도 true인 경우 전체 조건이 true로 평가되어 금지 정책이 적용됩니다.
> 연령 검사 주위의 괄호는 중요합니다. AND 연산자와 결합하기 전에 OR 연산을 단일 단위로 평가하기 때문입니다. 괄호가 없으면 연산자 우선순위로 인해 예상치 못한 평가 순서가 발생할 수 있습니다.
> 실제 사용 사례: 보험 규정 및 비즈니스 정책은 종종 특정 연령대에 대한 적용 범위를 제한합니다. 자동차 보험의 경우 18세 미만 고객은 표준 보험에 가입할 수 없으며(특별 적용 범위 또는 부모 동의가 필요할 수 있음), 85세 초과 고객은 다른 위험 평가 또는 적용 범위 한도가 적용될 수 있습니다. 이 정책은 에이전트가 이러한 제한을 위반하는 견적을 작성할 수 없도록 하며, 에이전트가 자체 추론에 따라 고객이 적격하다고 제안하더라도 마찬가지입니다.
>
> has 검사와 연령대 검사의 조합은 방어적 정책 설계를 보여줍니다. 먼저 데이터가 존재하는지 확인한 후에 평가합니다. 이렇게 하면 customer_info에서 age 속성이 완전히 누락된 경우 발생할 수 있는 정책 평가 오류를 방지할 수 있습니다.
>
> 금지 정책은 우회할 수 없는 엄격한 경계를 설정합니다. 다른 정책이 견적 생성을 허용하더라도 이 금지 정책이 우선 적용되어 조건이 충족되면 작업을 차단합니다.

## 슬라이드 27. 프라이빗 서브넷

**다이어그램 (D2)**

```d2
vpc: VPC {
  pub: "퍼블릭 서브넷" {
    igw: 인터넷 게이트웨이
    nat: NAT 게이트웨이
  }
  priv: "프라이빗 서브넷" {
    compute: 컴퓨팅
    sg: 보안 그룹
  }
  nacl: 네트워크 ACL
  routes: 라우팅 테이블
}
```

- 퍼블릭 서브넷
- VPC
- 라우팅 테이블
- 네트워크 ACL
- 컴퓨팅
- 보안 그룹
- 라우팅 테이블
- 네트워크 ACL
- NAT 게이트웨이
- 인터넷 게이트웨이
- 다중 방어 계층이 있는 인프라 설계

> **강사용 노트**
>
> 엄밀히 말하면 아키텍처 다이어그램은 아니고 흐름 및 특정 계층을 설명하기 위한 것입니다.
>
> 일부 조직에서는 퍼블릭 서브넷과 프라이빗 서브넷에 동일한 NACL을 사용할 수 있습니다. 또한 프라이빗 리소스만 외부 연결을 시작할 수도 있습니다.

> **수강생용 노트**
>
> 모범 사례는 다중 방어 계층으로 인프라를 보호하는 것입니다. NAT 게이트웨이 및 라우팅 테이블이 적절하게 구성된 VPC에서 인프라를 실행하여 인터넷에 액세스할 수 있는 리소스를 제어할 수 있습니다. 또한 보안 그룹과 네트워크 ACL을 정의하여 인터페이스 및 서브넷 수준에서 인프라를 더욱 안전하게 보호할 수도 있습니다.
>
> 보안 그룹을 네트워크 패킷 필터링 방법으로 사용할 수 있습니다. 상태 저장 패킷 필터링을 수행하고 다른 보안 그룹을 참조하는 규칙을 사용할 수 있기 때문에 네트워크 ACL보다 더 다양한 용도로 사용할 수 있습니다. 반면 네트워크 ACL은 특정 트래픽 하위 집합을 거부하거나 서브넷용으로 대략적인 가드레일을 제어하는 등의 보조 제어 기능으로 사용하면 효율적입니다.
>
> 네트워크 ACL과 보안 그룹을 모두 심층 방어 수단으로 구현하면 이러한 컨트롤 중 1가지를 잘못 구성하더라도 호스트가 예기치 못한 트래픽에 노출되지 않습니다.

## 슬라이드 28. AgentCore Runtime VPC 구성

```d2
region: "AWS 리전" {

region.vpc.vpce -> region.rt: AWS PrivateLink
```

- 프라이빗 서브넷
- 가용 영역
- 가용 영역
- 에이전트
- 보안 그룹
- VPC 엔드포인트
- AWS PrivateLink
- AWS 리전
- AgentCore Runtime
- AWS 서비스 계정
- ENI
- ENI

> **강사용 노트**
>
> 런타임 및 VPC 구성을 다루고 VPC 엔드포인트를 간략하게 언급합니다. 다음 슬라이드에서 VPC 엔드포인트를 더 자세히 설명합니다.

> **수강생용 노트**
>
> AgentCore Runtime 배포를 위해 관리하는 VPC를 지정하면 AgentCore Runtime은 ENI를 통해 VPC에 연결되는 AWS 서비스 계정에서 컴퓨팅을 관리합니다. VPC 환경에서 적절히 네트워크를 구성하면 퍼블릭 인터넷 트래픽으로부터 격리 상태를 유지하면서 안전하고 신뢰할 수 있는 에이전트 운영을 확보할 수 있습니다.
>
> VPC 및 서브넷 아키텍처 AgentCore Runtime용 VPC 및 서브넷을 지정할 때는 고가용성 및 내결함성을 제공하기 위해 서브넷이 여러 가용 영역에 분산된 VPC를 사용합니다. 이러한 다중 AZ 설계에서는 하나의 AZ에 문제가 발생하더라도 AgentCore Runtime이 계속 작동합니다.
>
> 보안 그룹 구성 에이전트의 특정 액세스 패턴을 지원하도록 보안 그룹을 구성합니다. 메모리, 게이트웨이와 같은 에이전트 구성 요소와 주고받는 트래픽을 허용하는 규칙을 생성합니다. 보안 그룹은 최소 권한의 원칙에 따라 에이전트 통신에 필요한 포트 및 프로토콜만 개방해야 합니다.
>
> IAM 서비스 연결 역할 IAM 권한에 서비스 연결 역할 AWSServiceRoleForBedrockAgentCoreNetwork를 생성할 수 있는 권한이 포함되어 있는지 확인합니다. 이 역할을 통해 Bedrock은 사용자를 대신하여 네트워크 리소스를 관리할 수 있으므로 VPC 내부에 ENI 생성 및 보안 그룹 관리를 포함할 수 있습니다.
>
> VPC 엔드포인트 인터넷 라우팅 없이 프라이빗 연결을 지원할 수 있도록 다른 AgentCore 서비스를 위한 VPC 엔드포인트를 설정합니다. 이러한 엔드포인트는 지연 시간을 줄이고 보안을 강화하며 에이전트 트래픽이 AWS 백본 네트워크 내에 유지되도록 하므로 규정 준수 요구 사항을 지원하는 동시에 에이전트 운영을 위한 최적의 성능을 유지할 수 있습니다.

## 슬라이드 29. 안전한 데이터 이동을 위한 AWS PrivateLink 사용

**다이어그램 (D2)**

```d2
direction: right
vpc: 소비자 VPC
pl: AWS PrivateLink
svc: Amazon Bedrock AgentCore Gateway
vpc -> pl: "프라이빗 IP (인터넷 미경유)"
pl -> svc: AWS 프라이빗 네트워크
```

- AWS PrivateLink를 사용하면 VPC를 인터넷 트래픽에 노출하지 않고도 Amazon VPC에서 Amazon Bedrock AgentCore Gateway로 프라이빗 연결을 설정할 수 있습니다.
- 프라이빗 IP를 사용하여 다른 VPC의 서비스에 액세스
- 트래픽이 Amazon의 프라이빗 네트워크에 유지됨
- 소비자가 통신 시작
- 제공업체와 소비자 간의 상호 핸드셰이크
- 2가지 중요한 클라우드 개념을 결합
- Amazon Virtual Private Cloud(VPC) - 인터넷 및 기타 VPC로부터 격리할 수 있는 프라이빗 네트워크
- 서비스로 제공되는 소프트웨어 - 제공업체가 소유 및 운영하고 소비자가 사용하는 소프트웨어

> **수강생용 노트**
>
> AWS PrivateLink VPC 엔드포인트를 사용하면 고객은 프라이빗 IP 주소를 사용하여 지원되는 AWS 서비스, 기업 서비스 및 서드 파티 서비스에 대한 프라이빗 연결을 설정함으로써 애플리케이션의 보안 상태를 더욱 강화할 수 있습니다.
>
> 그러므로 AWS PrivateLink에서는 데이터가 공개적으로 전송되지 않을까 걱정할 필요가 없습니다. PrivateLink가 애플리케이션과 AWS 서비스 간에 프라이빗 연결을 설정하여 네트워크 트래픽이 퍼블릭 인터넷과 격리된 상태로 Amazon 네트워크 내에서 유지되도록 하기 때문입니다.
>
> 이 프라이빗 연결을 통해 AgentCore Gateway에 안전하게 액세스하여 도구를 호출할 수 있습니다. 또한 이 아키텍처를 기반으로 솔루션을 구축하는 파트너는 데이터 소스에 대한 프라이빗 연결을 활용하여 데이터 프라이버시 및 보안을 침해하지 않으면서 쿼리를 보강하고 응답을 생성할 수 있습니다. 이것이 우리가 구축하고 있는 아이디어입니다.

```d2
vpce -> svc
```

- 프라이빗 서브넷
- 프라이빗 서브넷
- 보안 그룹
- VPC 엔드포인트
- ENI
- ENI
- AgentCore 서비스 및 기타 리소스
- AWS 서비스 계정의 AgentCore Runtime

> **강사용 노트**
>
> 프라이빗 DNS를 사용하도록 VPC 엔드포인트를 구성하면 기본 리전 이름을 사용하여 AWS 리소스를 대상으로 지정할 수 있다는 점을 강조하십시오.
>
> 이 이름은 해당 서브넷 ENI의 프라이빗 IP로 확인됩니다.

> **수강생용 노트**
>
> 프라이빗 VPC 내부의 AgentCore Runtime에서 실행되는 에이전트가 VPC 외부의 리소스(예: AgentCore Memory)에 액세스해야 하는 경우 연결은 VPC 인프라를 통한 보안 프라이빗 경로를 따릅니다. 에이전트는 런타임의 탄력적 네트워크 인터페이스(ENI)에 연결된 보안 그룹을 먼저 통과하는 API 직접 호출을 시작합니다. 이 보안 그룹은 AgentCore Memory 서비스 엔드포인트로 트래픽을 허용하도록 구성된 아웃바운드 규칙을 사용하여 가상 방화벽 역할을 합니다.
>
> 그런 다음 요청은 Amazon Bedrock이 서비스 연결 역할 AWSServiceRoleForBedrockAgentCoreNetwork를 사용하여 프라이빗 서브넷에서 자동으로 생성하는 ENI를 통해 전달됩니다. 이러한 ENI는 지정된 서브넷의 프라이빗 IP 주소가 할당되며 런타임과 AWS 서비스 간의 연결 지점 역할을 합니다. 프라이빗 DNS를 사용하도록 VPC 엔드포인트를 구성한 경우 API 직접 호출이 서비스의 퍼블릭 DNS 이름을 대상으로 할 수 있지만 이 이름은 ENI의 프라이빗 IP 주소로 확인됩니다.
>
> 다음으로, 트래픽은 AWS PrivateLink가 제공하는 VPC 인터페이스 엔드포인트로 라우팅됩니다. 이 VPC 엔드포인트는 의도된 리소스를 대상으로 합니다(예: com.amazonaws.region.bedrock-agentcore). VPC의 라우팅 테이블은 AgentCore 서비스로 향하는 트래픽을 퍼블릭 인터넷이 아니라 이 엔드포인트로 보냅니다.
>
> 마지막으로, VPC 엔드포인트는 AWS의 보안 내부 네트워크 백본을 통해 요청을 의도된 대상 AgentCore Memory 서비스로 직접 전달합니다. 전체 통신 경로가 AWS 인프라 내에서 유지되고 이 연결에는 인터넷 게이트웨이 또는 NAT 게이트웨이가 필요하지 않으므로 보안 강화, 지연 시간 감소, 기업 네트워크 격리 요구 사항 준수를 제공합니다.

>

> 런타임 - 에이전트 런타임 작업
> 내장 도구 - 코드 인터프리터 및 브라우저 도구 작업
> 메모리 - 메모리 스토어 작업
> 자격 증명 - 자격 증명 관리 작업
>
> AgentCore Gateway는 별도의 엔드포인트 com.amazonaws.region.bedrock-agentcore.gateway를 사용합니다.

> AWS Responsible AI Lens는 전체 기계 학습 수명 주기 동안 책임 있는 AI 관행을 내재화한 8개의 핵심 요소를 통해 책임성을 고려한 설계를 제공합니다. 핵심 요소 1에서는 명확한 시스템 목표 및 경계를 설정하는 사용 사례를 제시합니다. 핵심 요소 2에서는 정보에 입각하여 절충을 결정할 수 있도록 사용 사례의 예상되는 이점과 내재된 위험을 설명합니다. 핵심 요소 3에서는 측정 가능한 품질 및 안전 임계값을 통해 사용 사례를 해결하는 AI 시스템의 출시 기준을 정의합니다. 핵심 요소 4에서는 데이터 품질 및 대표성을 확보하는 AI 시스템의 평가, 훈련, 운영을 위한 데이터세트를 설계합니다. 핵심 요소 5에서는 적절한 아키텍처 및 제어를 구현하는 사용 사례를 해결하도록 AI 시스템을 설계합니다. 핵심 요소 6에서는 증거에 기반한 출시 결정의 실제 이점과 잔존 위험을 평가합니다. 핵심 요소 7에서는 적절한 시스템 사용 및 모니터링을 가능하게 하는 다운스트림 지침 및 투명성을 규정합니다. 핵심 요소 8에서는 출시 후 위험 및 폐기를 관리하여 운영 수명 주기 전반에 걸쳐 시스템 안전성을 유지합니다.
>
> 프레임워크에는 공정성, 설명 가능성, 개인 정보 보호, 보안, 안전성, 제어 가능성, 진실성, 견고성, 투명성, 거버넌스 등 10가지 차원에서 책임 있는 AI 원칙과의 조화를 개선하는 실행 가능한 지침과 함께 100개의 모범 사례가 포함되어 있습니다. Responsible AI Lens는 책임 있는 AI 시스템을 개발 및 배포하는 데 상호 보완적인 역할을 하는 3명의 주요 사용자에게 서비스를 제공합니다. AI 시스템을 개발 및 배포하는 엔지니어, 제품 관리자, 과학자 등의 AI 빌더는 AI 애플리케이션 고유의 이점-위험 절충을 식별하고 최적화하기 위한 구조화 작업에 대한 지침을 얻습니다. AI 시스템을 구축하고 전사적으로 책임 있는 AI 관행을 구현하는 팀을 감독하는 AI 기술 리더는 포트폴리오 위험의 균형을 맞추고 고객 신뢰를 얻기 위한 접근 방식을 표준화하는 프레임워크를 얻습니다. 조직의 규정 및 산업 표준 준수를 위한 구체적인 정책을 수립하는 책임 있는 AI 전문가는 AI 관련 정책을 설정 및 구현하는 데 도움이 되는 과학 기반 모범 사례 프레임워크의 이점을 얻습니다.

## 슬라이드 39. 에이전트 아키텍처 전반의 감사 추적

- 작업 로깅: 에이전트가 수행한 작업(도구 호출, 수정, 데이터 액세스)
- 추론 체인: 에이전트가 특정 결정을 내린 이유
- 자격 증명 컨텍스트: 작업 승인 주체(사람 또는 업스트림 시스템)
- 시간 데이터: 작업이 발생한 시점(정확한 타임스탬프를 사용)
- 세션 추적: 여러 상호 작용에 걸쳐 확장된 운영
- 낮은 자율성: 로컬 활동 로그 | 높은 자율성: 지속적인 행동 로깅
- 추천 그래픽 필요

> **강사용 노트**
>
> 실제 에이전트 사례를 통해 포괄적인 감사 추적 요소를 제시합니다.
>
> 다중 에이전트 워크플로 전반의 자격 증명 컨텍스트 전파를 살펴봅니다.
>
> 자율성 기반 요구 사항 및 플랫폼 기능에 대해 논의합니다.

> **수강생용 노트**
>
> 포괄적인 감사 추적은 에이전트가 규정 준수 범위 내에서 운영된다는 증거를 제공합니다. 모든 감사 추적에는 다음 5가지 필수 요소가 포함되어야 합니다. 도구 호출, 시스템 수정, 데이터 액세스를 포함하여 에이전트가 수행한 작업을 문서화하는 작업 로깅, 에이전트가 특정 결정을 내린 이유를 설명하는 추론 과정, 사용자 또는 업스트림 시스템을 불문하고 누가 작업을 승인했는지 보여주는 자격 증명 컨텍스트, 규정 요구 사항을 충족하는 정확한 타임스탬프가 포함된 시간 데이터, 여러 상호 작용에 걸친 확장된 작업에 대한 세션 추적 감사 요구 사항은 자율성에 비례합니다. 자율성이 낮은 에이전트는 기존 애플리케이션과 마찬가지로 로컬 활동 로그 및 변경 추적이 필요한 반면, 자율성이 높은 에이전트는 지속적인 행동 로깅, 시간 경과에 따른 패턴 분석, 규정 위반이 발생하기 전에 드리프트를 감지하기 위한 예측 모니터링이 필요합니다.

## 슬라이드 40. 자격 증명 관리 및 권한 부여

- 사용자 인증: OAuth 2.0, 인간 사용자를 위한 OpenID Connect
- 서비스 인증: 백엔드 시스템의 시스템 간 자격 증명
- 에이전트 인증: 에이전트 간 통신을 위한 자격 증명 인증
- 지속적 확인: 확장된 운영 전반에 걸친 지속적인 검증
- 자격 증명 컨텍스트 전파: 모든 상호 작용에서 호출자 자격 증명을 유지
- 규정 준수 가치: 모든 작업을 권한을 부여한 사람 또는 시스템까지 추적
- 추천 그래픽 필요

> **강사용 노트**
>
> 구체적인 예시를 통해 여러 인증 계층을 제시합니다.
>
> 장기 실행 작업을 위한 지속적인 확인 메커니즘을 살펴봅니다.
>
> 적절한 자격 증명 관리의 규정 준수 가치에 대해 논의합니다.

> **수강생용 노트**
>
> 자격 증명 관리는 규정 준수의 기본이며, 이를 통해 각 작업을 누가 승인했는지 증거를 확보할 수 있습니다. 인간 사용자의 경우 OAuth 2.0 및 OpenID Connect를 통한 사용자 인증, 백엔드 시스템의 시스템 간 자격 증명을 위한 서비스 인증, 에이전트 간 통신을 위한 에이전트 인증, 그리고 무엇보다 운영 시작 시 단일 인증이 아닌 확장된 에이전트 운영 전반에 걸쳐 지속적인 확인을 제공하는 지속적인 검증 등 여러 인증 계층이 필요합니다. 자격 증명 컨텍스트 전파는 모든 시스템 상호 작용에서 호출자 자격 증명을 유지하여 모든 작업에서 권한을 부여한 인간 사용자 또는 시스템까지 추적하는 명확한 책임성 체인을 생성합니다. 이를 통해 조사 또는 규제 검토 중에 감사 추적을 재구성하여 각 의사결정 지점에서 적절한 권한 부여를 입증할 수 있습니다.

## 슬라이드 44. 문제 1: 정답

- AgentCore Policy 권한 부여 흐름에서 Gateway가 사용자의 OAuth 토큰에 포함된 JWT 클레임을 처리하면 어떻게 됩니까?

| C. | 암호화되어 Gateway의 세션 캐시에 저장됩니다. |

### 3. 충돌 및 업데이트

- Agentic AI Lens 보안 기둥과의 **직접적 기술 충돌은 발견되지 않았습니다.** 본 모듈의 자격 증명·정책(Cedar)·네트워크 격리 서술은 Lens와 일관되며, 대부분의 차이는 위 2절의 "방어 모범 사례 구체화" 보강 항목입니다.
- 참고(프레임워크 정합): 본 모듈의 Security Scoping Matrix(대리권 없음/규정된/감독되는/전체)는 자율성 위험 분류용 보안 프레임워크이고, Agentic AI Lens 설계 원칙의 자율성 수준(observer/assistant/autonomous/orchestrator)은 아키텍처 설계용 분류입니다. 두 분류는 상충하지 않으며 상호 보완적으로 사용합니다.
