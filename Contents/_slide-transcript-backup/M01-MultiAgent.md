### 학습 목표
- 다중 에이전트 아키텍처가 필요한 시나리오를 분석한다.

### 핵심 개념

**1. 왜 다중 에이전트인가 — 단일 에이전트의 3가지 한계**
- **인지 부하 한계**: 여러 도메인(기술·제품·청구)을 한 에이전트가 처리하면 로직이 뒤섞여 오류가 연쇄된다.
- **컨텍스트 윈도우 고갈**: 대화·도구 출력·문서가 쌓이면 토큰 한계에 도달해 이전 정보를 '망각'하고 응답이 느려진다.
- **도메인 전문화 절충**: 일반 에이전트는 깊이가 없고, 과도하게 전문화된 에이전트는 엣지 케이스에 취약하다. 다중 에이전트는 "깊은 전문성 + 넓은 범위"를 동시에 달성한다.

**2. 다중 에이전트의 이점 (마이크로서비스 원칙과 동일)**
재사용성 · 격리 · 유지 관리성 · 확장성 · 내결함성 · 복원력. 핵심은 **관심사 분리** — 한 에이전트의 장애·변경이 전체로 번지지 않는다.

**3. 3가지 통신 패턴** (하나만 쓰는 게 아니라 혼합 사용)

| 패턴 | 핵심 | 언제 쓰나 | 구현 예 |
| --- | --- | --- | --- |
| 프레임워크 계층 | 중앙 오케스트레이션이 조정·상태를 관리 | 강력한 오류 처리·상태 관리가 필요한 엔터프라이즈 | Strands, LangGraph |
| 도구로서의 에이전트 | 전문 에이전트를 호출 가능한 도구로 래핑(느슨한 결합) | 여러 팀·사례에서 기능 재사용 | MCP |
| 에이전트 간(A2A) | 프레임워크 없이 직접 P2P 통신 | 초저지연, 플랫폼·조직 간 운영 | A2A 프로토콜 |

**4. Strands 오케스트레이션 3종**

| 방식 | 실행 흐름 | 적합한 문제 |
| --- | --- | --- |
| 워크플로 | 코드로 정의한 결정적 DAG(병렬·순차) | 반복 가능하고 예측 가능한 프로세스(예: 온보딩) |
| 그래프 | 노드·엣지 기반, 조건 분기·피드백 루프 허용 | 분기 로직이 있는 구조화된 프로세스 |
| 스웜 | 에이전트가 자율적으로 핸드오프(창발적 지능) | 다분야 협업이 필요한 열린 문제 |

**5. 메모리·상태 관리**
- 단일 에이전트는 상태가 단순하지만, 다중 에이전트는 **컨텍스트 단편화·동기화·일관성**이 핵심 난제다.
- **AgentCore Memory**: 단기(세션 내 대화)·장기(세션 간 지식) 이중 구조 + 에이전트 간 공유 + 세션 격리. 프레임워크 비종속.

### 꼭 기억할 것 (의사결정 기준)
다중 에이전트는 공짜가 아니다(조정 오버헤드·비용↑). 아래에 해당할 때 채택한다.
- 여러 도메인에 걸친 **심층 전문성**이 필요한가?
- 정교한 **조정**이 필요한가?
- 팀 간 **재사용** 기회가 있는가?
- 기능별 **독립 스케일링**이 이득인가?
- **내결함성·가용성**이 중요한가?

### 자주 하는 오해
- "에이전트가 많을수록 좋다" → 아니다. 단순 작업은 단일 에이전트 + 도구 몇 개가 더 낫다.
- "오케스트레이터가 모든 걸 중재해야 한다" → 단일 병목·장애점이 될 수 있다(→ 실무 심화의 arbiter 패턴 참고).
- "A2A가 가장 진보적이니 항상 낫다" → 인증·신뢰·복구를 직접 처리해야 하므로 보안·복잡성 비용이 크다.

> **강사용 노트**
>
> 수강생용 노트에 있는 예제를 참조하여 실제 사례를 제공합니다.

> **수강생용 노트**
>
> 기업 워크플로에서 AI 컨텍스트 윈도우가 용량에 도달하면 어려운 기술적 한계에 직면하게 됩니다. 최신 언어 모델은 유한한 컨텍스트 윈도우에서 작동하는데 윈도우는 빠르게 채워집니다. 복잡한 시나리오는 대화 기록, 도구 출력, 문서화 및 추론 단계로 인해 공간을 많이 소비합니다.
>
> 정보가 누적되면 어떤 컨텍스트를 보존, 압축 또는 폐기할지 우선순위를 정해야 합니다. 관련 정보가 제외되어 AI 의사결정의 일관성이 떨어지면 컨텍스트 저하가 발생합니다. 어텐션 메커니즘으로 인해 시퀀스 길이에 따라 계산 비용이 2배로 증가합니다.
>
> 이 고객 서비스 시나리오에는 200,000개 토큰 컨텍스트 윈도우 AI 어시스턴트가 있습니다. 먼저 아키텍처 설명(3,000개 토큰), 오류 로그(5,000개 토큰), 구성 파일(4,000개 토큰) 등 고객 설정 세부 정보부터 시작합니다. 어시스턴트는 문서(8,000개 토큰)를 로드하고 추론(5,000개 토큰)을 생성합니다. 이제 25,000개 토큰 또는 12.5% 용량에 도달했습니다.
>
> 문제 해결을 계속하면서 오류 로그, 스크린샷 및 이전 시도가 추가됩니다. 각 교환마다 대화 기록, 추론 프로세스 및 문서화 섹션을 유지하면서 컨텍스트를 추가합니다. 디버깅 라운드, 코드 검토, 솔루션 반복을 진행합니다.
>
> 광범위한 의견 교환 끝에 아키텍처 다이어그램(10,000개 토큰), 코드 조각(20,000개 토큰), 비교 분석(15,000개 토큰), 구현 토론(30,000개의 토큰)을 추가합니다. 이제 155,000개 토큰 또는 77.5% 용량에 도달했습니다.
>
> 컨텍스트가 제한에 가까워지면 3가지 중요한 문제에 직면합니다. 1번째, 우선순위 지정 때문에 어시스턴트에게 이전 대화 세부 사항을 상기시켜야 합니다. 2번째, 컨텍스트 저하로 인해 AI가 이전 아키텍처 세부 정보를 상실합니다. 3번째, 계산 속도 감소로 응답 시간이 2초에서 15초 이상으로 증가합니다. 품질이 저하됨에 따라 어시스턴트에게 이전 대화를 반복해서 상기시켜야 합니다. 컨텍스트 단편화는 응답 효과를 저하시켜 엔터프라이즈 AI 애플리케이션의 워크플로 비효율성을 초래합니다.

## 슬라이드 7. 도메인 전문화

**다이어그램 (D2)**

```d2
direction: right
single: "단일 에이전트 (절충)" {
  spec: 심층적 전문성
  gen: 광범위한 지원 범위
}
multi: "다중 에이전트 (장점 결합)" {
  orch: 오케스트레이터 에이전트
  cs: 고객 서비스 에이전트
  ret: 제품 반품 에이전트
  info: 제품 정보 에이전트
  orch -> cs
  orch -> ret
  orch -> info
}
single -> multi: "심층 전문화 + 광범위 지식"
```

- 다중 에이전트 솔루션: 각 에이전트의 장점을 결합

>
> 전문 스케일링 및 모놀리식 스케일링의 비용 이점에 대해 논의합니다.

> **수강생용 노트**
>
> 다중 에이전트 시스템의 확장성 패턴을 활용하여 수요에 따라 개별 기능을 규모 조정할 수 있습니다. 모든 태스크를 처리하는 모놀리식 에이전트의 규모를 조정하는 대신, 사용 패턴에 따라 특정 에이전트의 규모를 조정합니다.
>
> 청구 문의가 급증할 경우 기술 지원 기능은 표준 용량을 유지하면서 청구 에이전트만 규모 조정해야 합니다. 이러한 대상 지정 스케일링은 전체 시스템의 규모를 조정하는 것보다 비용 효율적이고 대응이 신속합니다. Amazon Bedrock AgentCore Runtime은 자동으로 리소스의 규모를 조정하고 리소스를 필요한 에이전트에 할당하므로 에이전트별로 수동으로 스케일링을 처리 또는 구성할 필요가 없습니다.
>
> 병렬 처리는 여러 에이전트가 태스크의 서로 다른 측면을 동시에 수행하기 때문에 자연스럽게 나타납니다. 이 예시에서는 코디네이터 에이전트가 사용자로부터 들어오는 청구분쟁을 분석한 다음, 동시에 3개의 에이전트에게 작업을 분배합니다. 이러한 에이전트는 각자 전문 작업을 수행하고 서로 통신하여 자신의 작업을 완료합니다. 오케스트레이팅 에이전트는 각 에이전트로부터의 입력내용을 합성하여 최종 응답을 준비합니다.
>
> 컴퓨팅 요구 사항에 따라 적절한 인프라에 다양한 에이전트를 배포하여 로드 분산이 정교해지면 비용을 최적화할 수 있습니다. GPU를 많이 사용하는 에이전트는 특수 하드웨어에서 실행되고 경량 코디네이션 에이전트는 표준 컴퓨팅 인스턴스를 사용합니다.

## 슬라이드 15. 일반적인 다중 에이전트 통신 패턴

- 프레임워크 계층
- 중앙 집중식 오케스트레이션 계층은 모든 에이전트의 상위에 위치하며 결정적 라우팅을 제공합니다.
- 선택 이유:
- 강력한 오류 처리
- 포괄적인 상태 관리
- 구현 예제:
- Strands SDK
- LangGraph
- 도구로서의 에이전트
- 주 오케스트레이터 에이전트는 에이전트를 도구로서 간접적으로 호출하고 느슨한 결합을 지원합니다.
- 선택 이유:
- 여러 사용 사례에서 공유할 수 있는 전문 기능

- 구현 예제:
- Model Context Protocol(MCP)

- 매우 짧은 대기 시간
- 구현 예제:

> **강사용 노트**
>

>
> 기본 시각적 예제를 사용하여 각 패턴을 설명합니다.
>
> 이러한 패턴을 다중 에이전트 아키텍처 기본 사항에 대한 이전 강의와 연결합니다.

> **수강생용 노트**
>
> 다중 에이전트 시스템은 서로 다른 아키텍처 요구 사항을 해결하는 3가지 기본 통신 패턴을 통해 조정합니다.
>
> 프레임워크 계층 통신은 중앙 시스템이 에이전트 상호 작용을 조정하고 워크플로 상태를 유지 관리하는 플랫폼 관리형 오케스트레이션을 제공합니다. 프레임워크 계층 통신에서는 플랫폼 자체가 에이전트 간 조정을 처리하여 태스크 위임, 메시지 전달, 상태 관리를 위한 기본 메커니즘을 제공합니다. 그러므로 다중 에이전트 협업을 위한 보다 체계적이고 통제된 환경이 조성됩니다.
>
> 도구로서의 에이전트 패턴은 표준화된 인터페이스를 통해 전문가 에이전트를 재사용 가능한 서비스로 취급하여 느슨한 결합을 지원합니다. 이 패턴은 잘 정의된 프로토콜을 통해 필요에 따라 간접적으로 호출할 수 있는 에이전트를 제공하므로 다양한 시스템에서 유연한 구성 및 통합이 가능합니다.
>
> A2A와 같은 에이전트 간 프로토콜은 프레임워크 중재 없이 직접적인 P2P 통신을 지원합니다. 에이전트는 자율적으로 협업하고, 태스크를 위임하고, 정보를 공유할 수 있습니다.
>
> 각 패턴은 확장성, 신뢰성 및 유연성 측면에서 뚜렷한 이점을 제공하며 단일 시스템 내에서 여러 패턴이 결합될 수 있습니다. 어떤 통신 패턴이 적절한지는 특정 사용 사례 요구 사항, 성능 요구 사항, 보안 제약 조건, 조직 성숙도 수준에 따라 달라집니다.
>
> 프레임워크 계층 통신은 강력한 오류 처리 및 포괄적인 상태 관리가 필요하고 확립된 플랫폼 기능 내에서 작동할 때 효과적이므로 신뢰성 및 유지 관리성이 우선시되는 엔터프라이즈 애플리케이션에 적합합니다.
>
> 도구로서의 에이전트 패턴은 여러 사용 사례에서 전문 기능을 공유하는 시나리오에 적합하며, 여러 팀이 동일한 에이전트 기능에 액세스해야 할 때 재사용을 촉진합니다.
>
> 사용자 지정 조정패턴, 지연 시간이 매우 짧은 상호작용 또는 다양한 플랫폼 또는 조직에서 운영되는 시스템이 필요한 경우에는 A2A 프로토콜을 고려하십시오. 대다수의 시스템은 여러 패턴을 사용하며 지연시간, 신뢰성, 보안, 유지관리 요구사항을 기반으로 각 특정 상호작용에 가장 적합한 접근방식을 선택합니다.

> **수강생용 노트**

> 도구로서의 에이전트 패턴에서는 전문 AI 에이전트가 다른 에이전트에서 사용할 수 있는 호출 가능한 함수(도구)로 래핑됩니다. 이를 통해 주 오케스트레이터 에이전트가 사용자 상호 작용을 처리하고 호출할 전문가 에이전트를 결정하고, 오케스트레이터가 호출한 전문 도구 에이전트가 도메인별 태스크를 수행하는 계층 구조가 생성됩니다.
>
> 이 접근 방식은 관리자가 각각 고유한 전문성을 보유한 전문가를 조정하여 복잡한 문제를 해결하는 인적 팀의 역학을 모방한 것입니다. 한 에이전트가 모든 것을 처리하려고 하는 대신 가장 적합한 전문가 에이전트에게 태스크를 위임합니다.
>
> 이 패턴에서는 전문가 에이전트를 잘 정의된 인터페이스를 갖춘 서비스로 취급하므로 다양한 상위 에이전트 및 워크플로에서 재사용할 수 있습니다. 여러 역할을 담당하는 모놀리식 에이전트를 구축하는 대신, 특정 기능에 집중된 전문가 에이전트를 생성하고 다른 에이전트가 간접적으로 호출할 수 있는 표준화된 인터페이스를 통해 노출합니다. 이 접근 방식은 느슨한 결합을 제공하여 한 에이전트가 변경되더라도 수정이 필요하지 않으며, 표준화된 인터페이스로 일관된 통합 패턴을 확보합니다. 핵심 과제는 여러 사용 사례에 사용할 수 있는 유연성과 신뢰할 수 있는 운영을 위한 특이성을 균형 있게 유지하는 인터페이스를 설계하는 것입니다.

- 아티팩트: 태스크가 완료될 때 생성되는 출력입니다. 각 에이전트는 사용자의 원래 요청을 처리하기 위해 협업하는 과정에서 아티팩트를 교환합니다.

> **강사용 노트**
>
> 직접 통신의 이점과 복잡성 간의 절충을 설명합니다.
>
> 현재 A2A 프로토콜 개발 현황 및 향후 잠재력을 소개합니다.
>
> P2P 에이전트 통신의 보안 문제에 대해 논의합니다.
>
> 신뢰성 및 감사 가능성에 대한 기업 요구 사항과 연결합니다.

> **수강생용 노트**
>
> Agent2Agent(A2A) 통신을 사용하면 프레임워크 중재 없이 에이전트 간에 직접적인 P2P 상호 작용이 가능하므로 지연 시간 감소, 유연한 상호 작용 패턴, 사용자 지정 조정 프로토콜과 같은 잠재적 이점을 얻을 수 있습니다.
>
> A2A는 클라이언트 에이전트와 원격 에이전트 간의 통신을 촉진합니다. 클라이언트 에이전트는 태스크를 구성하고 전달하는 역할을 담당하며, 원격 에이전트는 올바른 정보를 제공하거나 올바른 조치를 취하기 위해 해당 태스크를 수행합니다.
>
> 그러나 직접 통신은 에이전트가 자체적으로 인증, 권한 부여, 검색 및 오류 복구 메커니즘을 처리해야 하기 때문에 상당한 복잡성을 내포합니다. A2A 프로토콜은 엔터프라이즈급 보안 및 신뢰성을 유지하면서 직접 에이전트 상호 작용을 위한 표준화된 프로토콜을 제공하는 것을 목표로 하는 새로운 에이전트 간 통신 표준입니다. 구현을 위해서는 기업 환경에 필요한 관리 용이성을 유지하면서 이점을 달성할 수 있도록 보안, 신뢰성, 조정 패턴을 신중하게 고려해야 합니다.

> 에이전트 워크플로는 여러 AI 에이전트에 걸쳐 태스크를 구조적으로 조정하는 것으로, 각 에이전트는 정의된 순서 또는 패턴에 따라 전문 기능을 수행합니다. 워크플로는 복잡한 문제를 관리 가능한 구성 요소로 분해하고 전문가 에이전트에게 배포함으로써 태스크 실행 순서, 종속성, 정보 흐름에 대한 명시적 제어를 제공하여 특정 실행 패턴이 필요한 프로세스에 대해 신뢰할 수 있는 결과를 확보합니다.

> 종속성 관리
> 순차적 종속성: 특정 순서로 실행해야 하는 태스크
> 병렬 실행: 동시에 실행할 수 있는 독립적인 태스크
> 조인 포인트: 다음 단계로 진행하기전 여러 개의 병렬 실행경로가 하나로 합쳐지는 지점
> 정보 흐름
> 입력 및 출력 매핑: 한 에이전트의 출력을 다른 에이전트의 입력에 연결
> 컨텍스트 보존: 워크플로 전반에 걸쳐 관련 정보를 유지
> 상태 관리: 전체 워크플로 진행 상황을 추적

## 슬라이드 21. 그래프 패턴

**다이어그램 (D2)**

```d2
direction: right
research: 연구
analysis: 분석
fact: 팩트 체킹
report: 보고
research -> analysis
analysis -> fact
fact -> report
fact -> analysis: 피드백 루프
```

- 그래프 패턴은 다음과 같은 구조를 갖는 구조화된 결정적 워크플로의 원칙에 따라 작동합니다.
- 노드는 주기적 패턴으로 재방문할 수 있는 에이전트, 사용자 지정 노드 또는 다중 에이전트 시스템을 나타냅니다.
- 엣지는 노드 간의 종속성 및 정보 흐름을 정의합니다.
- 실행은 그래프 구조를 따르며 종속성을 고려합니다.
- 한 노드의 출력은 종속 노드의 입력이 됩니다.
- 연구
- 보고
- 팩트 체킹
- 분석

> **강사용 노트**
>
> 다음 페이지로 이동하여 생성할 코드와 이 패턴의 추가 예제를 소개하십시오. https://strandsagents.com/latest/documentation/docs/user-guide/concepts/multi-agent/graph/#creating-a-graph

> **수강생용 노트**
>
> 그래프란 에이전트, 사용자 지정 노드 또는 기타 다중 에이전트 시스템(예:스웜 또는 중첩된그래프)이 그래프의 노드로 구성되는 결정론적 방향성 그래프 기반의 에이전트 오케스트레이션 시스템입니다. 노드는 엣지 종속성에 따라 실행되며, 한 노드의 출력이 연결된 노드에 입력으로 전달됩니다. 그래프 패턴은 비순환(DAG) 토폴로지와 순환 토폴로지를 모두 지원하므로 피드백 루프 및 반복적 개선 워크플로가 가능합니다.
>
> 그래프 패턴은 다음을 제공합니다.
> 그래프 구조 기반의 결정론적 실행 순서
> 노드 간 엣지를 따라 출력이 전파됨
> 에이전트 간의 명확한 종속성 관리
> 중첩 패턴 지원(한 그래프를 다른 그래프의 노드로 사용)
> 결정론적 비즈니스 로직 및 하이브리드 워크플로를 위한 사용자 지정 노드 유형
> 동적 워크플로를 위한 조건부 엣지 순회(탐색)
> 실행 제한 및 상태 관리를 통한 순환 그래프 지원
> 텍스트, 이미지 및 기타 콘텐츠 유형의 처리를 위한 멀티모달 입력 지원

## 슬라이드 22. 스웜 패턴

**다이어그램 (D2)**

```d2
coder: 코더
architect: 아키텍트
reviewer: 검토자
researcher: 연구자
coder <-> architect
architect <-> reviewer
reviewer <-> researcher
researcher <-> coder
coder <-> reviewer
architect <-> researcher
```

- 스웜의 각 에이전트는 다른 에이전트에게 핸드오프할 시기를 결정할 수 있습니다.

- 다른 에이전트가 기여한 공유 지식
- 사용 가능한 모든 에이전트의 목록
- 코더
- 아키텍트
- 검토자
- 연구자

## 슬라이드 27. 복습: 에이전트가 메모리를 사용하는 방식

- 컨텍스트 인텔리전스
- 상황에 대한 이해와 패턴 인식을 통해 응답의 정확성과 관련성을 높입니다.
- 사용자 선호 사항
- 여러 세션에서 선호 사항과 과거 대화를 기억하여 상호 작용을 개인화합니다.
- 지식 보존
- 영구 메모리와 지속적인 학습 기능을 통해 정교한 문제 해결이 가능합니다.

> **강사용 노트**
>
> 고객 지원 시나리오의 구체적인 예를 사용하여 각 패턴을 설명합니다.

>

>
> 각 패턴을 학생들이 접할 만한 실제 애플리케이션에 연결하여 제시합니다.
>
> 이러한 패턴이 어떻게 함께 작용하여 포괄적인 에이전트 인텔리전스를 생성하는지 언급합니다.

> **수강생용 노트**
>
> 에이전트 메모리는 지능적인 상호 작용에 기여하는 3가지 뚜렷한 목적을 실행에 옮깁니다. 컨텍스트 인텔리전스는 방금 말한 내용을 기억하고 진행 중인 태스크를 추적하여 현재 세션 내에서 대화의 흐름을 유지합니다. 사용자 선호 사항은 명시된 기본 설정을 포착하고 행동 패턴을 추론하여 의사 소통 방식과 요구 사항에 맞게 응답을 개인화합니다. 지식 보존은 모든 상호 작용에서 언급된 중요한 사실, 개체, 상호 관계에 대한 지속적인 이해를 구축합니다. 예를 들어, 고객 지원 에이전트는 사용자의 현재 주문 번호(맥락)를 기억하고, 상대가 자세한 기술 설명(기본 설정)을 선호한다는 것을 알고 있으며, 회사 지점이 3곳이고 직원이 500명임을 기억할 수 있습니다(지식). 이 3가지 패턴이 결합되어 즉각적인 맥락과 장기적인 관계를 모두 이해하는 에이전트가 탄생합니다.

## 슬라이드 28. 다중 에이전트 시스템의 메모리 문제

- 단일 에이전트 시스템
- 에이전트는 다음과 같은 특성으로 자체 컨텍스트 및 기록을 유지합니다.
- 상태 관리를 분리
- 선형 실행 흐름
- 예측 가능한 행동
- 조정 오버헤드를 최소화
- 다중 에이전트 시스템
- 에이전트는 공유 메모리를 사용하여 상태를 관리하고 다음 기능을 제공합니다.
- 에이전트 간에 상태를 동기화
- 일관된 공유 메모리를 유지
- 성능 최적화
- 메모리 수명 주기를 처리
- 에이전트 메모리
- 공유 상태

> **강사용 노트**
>
> 설명을 위해 수강생용 노트에 있는 각 시스템의 예시를 참조하십시오.

> **수강생용 노트**
>
> 단일 에이전트 시스템은 메모리를 단순하게 처리합니다. 즉, 하나의 에이전트가 자체 컨텍스트 및 기록을 유지합니다. 예를 들어 개인 업무 관리자 에이전트는 사용자의 업무, 우선순위, 일정 선호도를 유지하면서 할 일 목록 및 일정을 관리합니다. 에이전트는 이 데이터의 최신 버전에 액세스할 수 있습니다.
>
> 다중 에이전트 시스템에서는 조정 문제가 발생합니다. 각 에이전트는 전체 태스크에 대한 부분적인 정보만 가지고 있으므로 컨텍스트가 단편화될 수 있습니다. 예를 들어, 심층 연구 다중 에이전트 시스템에서는 여러 에이전트가 연구, 분석, 문서 작성과 같은 다양한 태스크를 담당할 수 있습니다. 모든 에이전트가 태스크의 현재 상태를 인식하도록 원시 연구 데이터, 초안 문서, 생성된 그래프 및 차트 등이 저장된 공통 메모리를 유지합니다.
>
> 에이전트는 요청 및 워크플로 상태에 대한 컨텍스트를 공유하고 한 에이전트가 새로운 정보를 습득할 때 일관성을 유지해야 합니다. 또한 에이전트 간에 모든 메모리를 복제하지 않고도 성능을 최적화해야 합니다. 메모리 요구 사항은 에이전트 수 및 상호 작용 복잡성에 따라 기하급수적으로 증가합니다. 다중 에이전트 패턴은 공유 상태가 지속 또는 삭제되는 시점을 포함하여 메모리 수명 주기 관리도 고려해야 합니다. 이러한 문제를 해결하려면 공유할 정보, 공유 시기, 장애를 정상적으로 처리하는 방법에 대한 아키텍처 결정이 필요합니다.

> 기본 공유를 위한 Amazon Bedrock AgentCore 내장 세션 메모리
> 정교한 대화 관리 및 요약을 위한 Strands SDK
> 기업 통합 요구 사항을 위한 외부 스토리지

>
> 세션 격리는 보안 및 개인 정보 보호를 제공하고 지속성 계층은 상호 작용 간에 중요한 컨텍스트가 손실되지 않도록 합니다. 이러한 조합을 통해 개인화된 경험을 유지하면서 여러 동시 사용자를 처리할 수 있도록 확장할 수 있는, 프로덕션에 바로 사용할 수 있는 다중 에이전트 시스템을 구축할 수 있습니다.
>
> 프레임워크에 구애받지 않는 설계이므로 LangGraph에서 그래프 기반 패턴을 사용하든, Strands의 워크플로 패턴을 사용하든, 다른 다중 에이전트 아키텍처를 사용하든 관계없이 AgentCore Memory를 구현할 수 있습니다. 이러한 유연성 덕분에 메모리 관리 기능을 그대로 유지하면서 사용 사례에 적합한 패턴을 선택할 수 있습니다.

Strands SDK는 몇 시간 동안 지속되는 단기 캐싱부터 진행 중인 프로젝트를 위한 장기 스토리지에 이르기까지 유연한 지속성 옵션을 제공하며, 사용자가 다시 방문했을 때 컨텍스트를 검색하고 재구성하는 데 드는 복잡성(예: 새로운 정보를 기존 컨텍스트와 지능적으로 병합)을 처리합니다.

> @tool(context=True)을 사용하는 경우 ToolContext를 통해 invocation_state에 액세스합니다. 시스템은 이 상태를 도구 및 도구 관련 후크(예: BeforeToolCallEvent 및 AfterToolCallEvent)에 전파합니다. 도구 함수를 정의하면 invocation_state가 포함된 ToolContext 파라미터를 받게 됩니다. get() 메서드를 사용하여 user_id 또는 debug_mode와 같은 특정 값을 추출합니다. 이를 통해 현재 호출 상태 정보를 기반으로 도구의 동작을 조정하는 개인화된 컨텍스트 인식 도구를 생성할 수 있습니다. 애플리케이션에서 이 자동 상태 전파를 활용하여 보다 동적이고 사용자 맞춤형인 기능을 구축할 수 있습니다.

## 슬라이드 44. 문제 2: 정답

- Strands SDK와 함께 AgentCore Memory를 사용하는 다중 에이전트 시스템에서 모든 에이전트가 개별 자격 증명을 유지하면서 동일한 메모리 리소스에 액세스할 수 있도록 하려면 어떤 파라미터를 공유해야 합니까?

| 보기 | 응답 |
| --- | --- |
| A. | actor_id만 |
| B. | session_id만 |
| C. | memory_id 및 각 에이전트의 고유한 actor_id |
| D. | memory_id 및 각 에이전트의 고유한 actor_id가 포함된 session_id |

- 정답은 D입니다.

> **강사용 노트**
>
> 각 답변과 정답 또는 오답 이유를 검토하십시오.

> **수강생용 노트**
>
> A. 오답입니다. session_id 및 memory_id를 공유하지 않고 actor_id만 사용하면 에이전트가 동일한 메모리 리소스에 액세스할 수 없습니다.
>
> B. 오답입니다. memory_id 없이 session_id만 사용하면 에이전트가 특정 메모리 리소스에 연결되지 않습니다.
>
> C. 오답입니다. memory_id 및 다른 actor_id가 필요하지만 공유 session_id가 없으면 에이전트는 동일한 대화 세션에 액세스할 수 없습니다.
>
> D. 정답입니다. 슬라이드에 나와 있듯이, Strands SDK에서 AgentCore 단기 메모리를 공유하는 경우 에이전트는 '세션 ID를 공유하되 고유한 액터 ID를 가져야 합니다.' 예제 코드는 SESSION_ID 값은 동일하지만 에이전트마다 ACTOR_ID 값이 다르고 모두 동일한 memory_id에 연결되는 메모리 세션을 생성하는 방법을 보여 줍니다. 이를 통해 여러 에이전트가 개별 자격 증명을 유지하면서 동일한 메모리 리소스에 액세스할 수 있습니다.

### 2. 누락된 모범 사례 (본 모듈에 미수록 · 보완 권장)

- **AGENTREL04-BP01 arbiter(중재자) 에이전트 패턴**: 충돌 조정을 전담 arbiter에 집중시키고, 조정이 필요할 때만 이벤트 기반으로 활성화합니다. 전문 에이전트는 매 상호 작용을 P2P로 협상하지 않고 독립적으로 동작합니다. (본 모듈의 오케스트레이터 개념과의 차이는 3절 참고)
- **AGENTREL04-BP02 역량 분류(capability taxonomy) + AgentCore Registry**: 구조화된 역량 메타데이터와 시맨틱 검색으로 결정적 라우팅을 구동하고, 선호 에이전트가 불가할 때 자동 대체합니다. 본 모듈은 라우팅 로직을 언급하지만 정형 역량 분류·레지스트리는 다루지 않습니다.
- **AGENTREL04-BP04 복원력 있는 제어 평면(control plane)**: 조정 인프라(제어 평면)를 중복·내구성 있게 설계하여 조정 대상 에이전트만큼 신뢰성을 확보합니다.
- **AGENTREL01-BP01 복원력 있는 메시징 계층**: 내구성 있는 메시지 큐 등으로 통신 계층 자체의 복원력을 확보합니다(통신 패턴 소개를 넘어서는 인프라 관점).
- **AGENTREL06-BP04 멱등(idempotent) 태스크 실행 패턴**: 재시도·복구 시 중복 실행을 방지합니다.

### 3. 충돌 및 업데이트

- **오케스트레이터 vs. arbiter(중재자) 패턴 (신뢰성 관점의 정련)** — 슬라이드 11·15·17: 본 모듈은 오케스트레이터가 모든 위임과 결과 종합을 중재하는 모델로 제시합니다. Agentic AI Lens(AGENTREL04-BP01)는 대규모·고신뢰 다중 에이전트에서 **조정 전담 arbiter가 충돌 발생 시에만 활성화(이벤트 기반)** 하고 전문 에이전트는 독립적으로 실행하도록 권장합니다(오케스트레이터를 모든 메시지의 경유지로 두면 단일 병목·장애점이 됩니다). 도구로서의 에이전트/오케스트레이터 패턴 자체는 여전히 유효하나(Lens도 AGENTCOST01-BP03에서 하이브리드 슈퍼바이저로 인정), 프로덕션 신뢰성 강화를 위해 arbiter 패턴 + 역량 레지스트리(AGENTREL04-BP02) + 폴백 체인(AGENTREL04-BP03)으로 보완할 것을 권장합니다.
- 슬라이드 12의 "99.9% 가동 시간" 서술은 Lens 신뢰성 기둥과 상충하지 않아 그대로 유지합니다.
