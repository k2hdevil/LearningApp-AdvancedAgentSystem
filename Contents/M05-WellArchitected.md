## 파트 1. Well-Architected 기반과 5가지 설계 원칙

### 1.1 해결할 문제

에이전틱 AI 시스템 배포는 기존 애플리케이션과 **근본적으로 다릅니다.** 에이전트가 자율적으로 결정하고 비결정적으로 행동하기 때문에, 프로토타입에서 잘 돌던 것이 프로덕션에서 무너집니다. 다섯 가지 전환 과제가 있습니다.

- **자율적 의사결정** → 정책 기반의 강력한 거버넌스 필요 (모듈 3)
- **비결정적 행동** → 포괄적 모니터링·평가 필요 (모듈 4)
- **컨텍스트 관리** → 성능·비용에 직접 영향 (모듈 2)
- **다중 에이전트 조정** → 복원력 있는 통신 필요 (모듈 1)
- **지속적 학습** → 평가 프레임워크 필요 (모듈 4)

핵심 통찰은 **자율성 수준을 태스크 복잡성에 맞추고, 문제에 필요할 때만 대리권을 상향**하는 것입니다. 자율성은 목표가 아니라 트레이드오프입니다.

> **💡 팁 — 캡스톤의 프레이밍**: "이 모듈은 새 기술을 배우는 게 아니라, 지금까지 배운 것을 *프로덕션 관점으로 재조명*하는 것"이라고 시작하세요. "개념 증명 에이전트에서 프로덕션 시스템으로 갈 때 가장 큰 어려움은?"이라는 질문으로 학습자가 M01~M04를 스스로 소환하게 만들면 종합 효과가 큽니다.

### 1.2 고려해야 할 기술·프레임워크

#### (1) AWS Well-Architected Framework — 6기둥

Well-Architected Framework는 6개 기둥으로 클라우드 아키텍처를 일관되게 평가합니다 — 운영 우수성, 보안, 신뢰성, 성능 효율성, 비용 최적화, 지속 가능성. 이 기둥은 모든 워크로드에 적용되지만, 에이전틱 AI에는 **각 기둥마다 고유한 조정**이 필요합니다(파트 2에서 다룸).

#### (2) 자율성 스펙트럼 — 비에이전틱에서 에이전틱으로

에이전틱 AI는 단일 스위치가 아니라 **대리권의 스펙트럼**입니다. 태스크 복잡성이 커질수록 대리권도 커집니다.

```ascii
[자율성 스펙트럼]  단일 스위치가 아니라 대리권의 스펙트럼이다

┌─ 1) 비 에이전틱
│    챗봇
│    프롬프트 템플릿
│    프롬프트 엔지니어링 / RAG
│
├─ 2) LLM 증강 워크플로 (도구 사용)
│
└─ 3) 에이전틱
     자율 에이전트
     셀프 오케스트레이팅 시스템
     다중 에이전트

  1) --> 2) --> 3) 순서로 태스크 복잡성 / 대리권이 증가한다
```

#### (3) Agentic AI Security Scoping Matrix — 자율성 4수준

모듈 3에서 다룬 이 매트릭스는 자율성 수준에 따라 보안 요구가 점증함을 보여줍니다 — 대리권 없음 → 규정된 대리권(사람 승인) → 감독되는 대리권(사람 트리거·자동 실행) → 전체 대리권(자체 개시). **대부분의 프로덕션 시스템은 규정된/감독되는 대리권에서 시작**합니다.

#### (4) 5가지 설계 원칙 — Agentic AI Lens의 핵심

6개 기둥을 관통하는 5가지 설계 원칙이 에이전틱 아키텍처의 토대입니다. 각 원칙은 이 과정의 특정 모듈에서 이미 구체적으로 실천했습니다.

| # | 설계 원칙 | 요지 | 주 구현 모듈 |
| --- | --- | --- | --- |
| ① | **전문화·경계가 명확한 에이전트로 분해** | 선언된 범위·명시적 한계·명확한 권한의 단일 목적 에이전트가 평가·보안·확장·교체가 쉽다 | 모듈 1 |
| ② | **모든 행동을 엔드투엔드로 관찰·추적** | 추론·도구 호출·메모리·핸드오프를 단일 추적 체계로 수집해 비용·지연·품질·보안 질문에 동일 데이터로 답한다 | 모듈 4 |
| ③ | **에이전트 행동을 코드처럼 취급** | 프롬프트·도구 카탈로그·역할 정의·정책을 버전 관리 아티팩트로 다뤄 리뷰·테스트·롤백을 적용한다 | 모듈 1·5 |
| ④ | **자율성에 비례하는 인간 감독** | 자율성 수준·에스컬레이션 경로를 사전 정의하고, 결과 중대성에 따라 검토 깊이를 조정한다 | 모듈 3 |
| ⑤ | **명시적 계약에 근거한 자율 행동** | 스키마·레지스트리·구조화된 성공 기준·신뢰도 신호로 암묵적 가정을 대체한다 | 모듈 1·3 |

> **💡 팁 — 5원칙을 모듈에 매핑**: 각 설계 원칙을 이 과정의 모듈에 연결하면 "우리가 이미 이것을 배웠다"는 종합 효과가 극대화됩니다. 원칙 ①=모듈 1의 에이전트 분해, ②=모듈 4의 3계층 관찰성, ③=모듈 1의 에이전트 정의 파일(md), ④=모듈 3의 Scoping Matrix·HITL, ⑤=모듈 1의 통신 계약·모듈 3의 Cedar 정책. 학습자에게 "각 원칙을 어느 모듈에서 봤는지" 맞히게 하세요.

### 1.3 구현 요건 및 절차 — 설계 원칙 적용

1. **자율성 수준 판정**: 시스템을 자율성 스펙트럼과 Scoping Matrix에 매핑한다. "이 태스크에 정말 이만큼의 대리권이 필요한가?"를 묻는다.
2. **5원칙 체크**: 아키텍처 결정마다 5가지 설계 원칙을 통과하는지 점검한다 — 경계가 명확한가(①), 관찰 가능한가(②), 버전 관리되는가(③), 감독이 비례하는가(④), 계약이 명시적인가(⑤).
3. **Lens 선택**: 에이전틱 워크로드는 Agentic AI Lens를 1차 기준으로, Generative AI Lens를 보완으로 사용한다.
4. **기둥별 평가로 확장**: 6개 기둥 각각에서 에이전트 특화 고려사항을 점검한다(파트 2).

### 1.4 구현 예시 — 자율성에 비례하는 설계 결정

동일한 "환불 처리"라도 자율성 수준에 따라 설계가 달라집니다.
- **규정된 대리권(범위 2)**: 에이전트가 환불을 제안 → 사람이 승인 → 실행. 감독 원칙(④)이 강하게 적용, 모든 결정에 HITL.
- **감독되는 대리권(범위 3)**: 사람이 워크플로 트리거 → 에이전트가 정책 경계 내 자동 실행. Cedar 정책(⑤ 명시적 계약)으로 "$500 미만만 자동"을 강제, 관찰성(②)으로 사후 감사.

자율성을 한 단계 올릴 때마다 정책·관찰성·평가·거버넌스의 정교함을 함께 올려야 합니다.

> **💡 팁**: "자율성을 낮추는 것도 유효한 설계 결정"임을 강조하세요(모듈 3과 동일 메시지). 자동화 이득이 위험·거버넌스 비용을 정당화하지 못하면, 범위를 낮춰 HITL을 추가하는 것이 옳습니다.

### 1.5 모범 사례 (Well-Architected Agentic AI Lens)

- 🏛️ **5가지 설계 원칙(전체)**: 이 파트가 소개한 5원칙은 Agentic AI Lens 전체를 관통하는 토대다. 원칙 ①은 AGENTREL02·AGENTSUS01, ②는 AGENTOPS05, ③은 AGENTOPS02·03, ④는 AGENTSEC04·AGENTREL02-BP05, ⑤는 AGENTSEC02·AGENTOPS04와 연결된다.
- 🏛️ **책임 있는 AI 내재화**: Agentic AI Lens는 책임 있는 AI(투명성·제어 가능성·공정성·거버넌스)를 별도 관심사가 아니라 모범 사례 전반에 녹인다. 원본 슬라이드 8의 6개 원칙(관찰성·제어 가능성·진실성/강건성·공정성·투명성·거버넌스)은 이와 대응된다(문서 하단 매핑 참조).
- 🏛️ **자율성 판정이 모든 제어의 출발점**: 설계 원칙 ④에 따라 Scoping Matrix 판정이 이후 6기둥 제어의 강도를 결정한다.

## 파트 2. 6기둥별 에이전틱 AI 설계 전략

### 2.1 해결할 문제

6개 기둥은 모든 워크로드에 적용되지만, 에이전트의 자율성·비결정성·다중 구성 요소 특성 때문에 **각 기둥마다 에이전트 특화 조정**이 필요합니다. 기존 클라우드 아키텍처의 기둥 지식을 그대로 쓰면 에이전트 고유의 문제(추론 품질·토큰 비용·에이전트 간 장애 전파 등)를 놓칩니다. 이 파트는 각 기둥이 에이전트에 *어떻게* 달라지는지, 그리고 어떤 AWS 서비스로 구현하는지를 정리합니다.

```ascii
에이전틱 AI 시스템 (프로덕션)
  │
  │  6기둥으로 평가
  v
┌─ Well-Architected 6기둥
│
├─ 운영 우수성 (AGENTOPS)
├─ 보안 (AGENTSEC)
├─ 신뢰성 (AGENTREL)
├─ 성능 효율성 (AGENTPERF)
├─ 비용 최적화 (AGENTCOST)
└─ 지속 가능성 (AGENTSUS)
```

> **💡 팁 — 부록을 본문으로**: 원본 강의에서 6기둥 전략은 "부록(필요 시 참조)"이었지만, 심화 학습에서는 이것이 **핵심 종합 자료**입니다. 각 기둥을 이 과정의 모듈과 연결하세요 — 성능·비용=모듈 2, 보안=모듈 3, 운영 우수성=모듈 4, 신뢰성=모듈 1·4. 학습자가 "모든 모듈이 여기로 수렴한다"를 체감하게 만드는 것이 이 파트의 목표입니다.

### 2.2 고려해야 할 기술 — 기둥별 3대 고려사항

각 기둥의 대표 3대 고려사항과 AWS 접근을 정리합니다. (교차 참조: 각 기둥은 Agentic AI Lens의 해당 질문군에 대응)

#### (1) 운영 우수성 (AGENTOPS · 7질문·26BP)

| 에이전틱 AI 고려사항 | AWS 접근 | 관련 모듈 |
| --- | --- | --- |
| 다중 구성 요소 배포 | AgentCore Runtime 변경 불가 버전 관리 + AgentCore Memory로 버전 간 상태 유지 + CodePipeline·S3로 비-코드 아티팩트(프롬프트·구성) 관리 | 모듈 1·5 |
| 지속적 품질 평가 | AgentCore Evaluations로 시맨틱 정확성 평가(정확 일치 아님) | 모듈 4 |
| 다중 계층 관찰성 | AgentCore Observability로 CloudWatch 통합 모니터링·트레이스 시각화 | 모듈 4 |

에이전트 코드·프롬프트·모델·메모리·평가 데이터세트는 **각각 독립 진화하되 호환성을 유지**해야 합니다. AgentCore Runtime의 변경 불가 버전 관리가 완전한 구성 스냅샷을 만듭니다.

#### (2) 보안 (AGENTSEC · 9질문·30BP)

| 에이전틱 AI 고려사항 | AWS 접근 | 관련 모듈 |

### 2.3 구현 요건 및 절차 — 기둥별 평가

1. **자율성 판정 결과 반영**(파트 1): 판정한 대리권 수준에 따라 각 기둥의 요구 강도를 정한다.
2. **기둥 순회 평가**: 6개 기둥 각각에서 3대 고려사항을 점검하고, 해당 AWS 서비스를 매핑한다.
3. **교차 기둥 트레이드오프 인식**: 관찰성 심도(운영)↔비용, 자율성(성능)↔보안 등 상충을 명시적으로 조정한다.
4. **모듈 지식 소환**: 각 기둥의 구체 구현은 앞 모듈에 있다 — 필요 시 모듈 1~4의 절차를 재사용한다.

### 2.4 구현 예시 — 감독되는 대리권(범위 3) 전자상거래 에이전트의 기둥별 결정

PCI-DSS 규제·99.9% 가용성 요구의 전자상거래 지원 시스템(파트 3 시나리오)에 6기둥을 적용하면:
- **운영**: AgentCore Runtime 버전 관리 + Evaluations 온라인 평가(품질 게이트) + Observability 대시보드
- **보안**: Cedar 정책("청구 에이전트는 billing_tool만") + Cognito·Identity·IAM 3계층 + PrivateLink(PCI 데이터 격리)
- **신뢰성**: 다중 AZ + 회로 차단기 + 오케스트레이터 폴백 체인(단일 장애점 제거)
- **성능**: AgentCore Memory 외부화 + 프롬프트 캐싱 + 전문가 에이전트 병렬
- **비용**: 테일 기반 샘플링 + 프롬프트 캐싱 + 예산 경보
- **지속 가능성**: 저탄소 리전 + 종량제 + 로그 수명 주기

> **💡 팁 — 트레이드오프를 드러내라**: 기둥은 때때로 충돌합니다. "모든 트레이스를 캡처(운영 우수성)"하면 비용이 오르고, "완전 자율(성능·자동화)"은 보안·거버넌스 부담을 키웁니다. 학습자에게 "어떤 기둥을 우선할지는 비즈니스 맥락이 결정한다"를 강조하고, 위 전자상거래 사례에서 실제 트레이드오프를 토론하게 하세요.

### 2.5 모범 사례 (Well-Architected Agentic AI Lens)

- 🏛️ **운영 우수성 AGENTOPS01~07**: AGENTOPS03(AgentOps CI/CD·배포), AGENTOPS02(프롬프트·구성 수명 주기), AGENTOPS05(관찰성), AGENTOPS06(테스트·평가·검증)이 이 기둥의 핵심이다.

## 파트 3. 프로덕션 준비와 종합 아키텍처 설계 (캡스톤)

### 3.1 해결할 문제

설계 원칙(파트 1)과 6기둥 전략(파트 2)을 갖췄다면, 이제 **"이 시스템을 프로덕션에 배포할 준비가 되었는가"** 를 검증하고, 모듈 1~4의 모든 결정을 **하나의 아키텍처로 종합**해야 합니다. 개념 증명(PoC)과 프로덕션의 격차는 다음에서 드러납니다 — 부하 상황의 성능, 실제 공격 표면의 보안, 다중 에이전트 워크플로의 관찰성 격차, 규제 준수 입증. 이 파트는 이 과정 전체의 캡스톤입니다.

> **💡 팁 — 설계 실습이지 코딩 실습이 아니다**: 이 파트의 아키텍처 활동은 새 에이전트를 만드는 것이 아니라, *이미 정의된 에이전트를 중심으로 프로덕션 아키텍처를 설계*하는 것입니다. "PoC에서 프로덕션으로 갈 때 가장 큰 어려움은?"을 물어 학습자가 6기둥을 스스로 떠올리게 하세요. 흔한 함정 — 초기 과도 엔지니어링, 사후 보안, 관찰성 격차, 오케스트레이션 단일 장애점.

### 3.2 고려해야 할 기술·서비스

#### (1) 배포 준비 상태 — 4개 검증 영역

```ascii
┌─ 배포 준비 상태 검증 (4개 영역)
│
├─ 성능
│    부하 테스트 / 기준 설정 / 벤치마킹
│
├─ 보안
│    정책 테스트 / IAM 검토 / 취약성 스캔
│
├─ 모니터링
│    CloudWatch / X-Ray / Evaluations / Observability
│
└─ 규정 준수
     규제 요구 / 데이터 레지던시 / AWS Config
```

| 영역 | 검증 항목 | 관련 모듈 |
| --- | --- | --- |
| **성능** | 부하 테스트·기준선 설정·벤치마킹 | 모듈 2·4 |
| **보안** | 정책 테스트·IAM 검토·취약성 스캔 | 모듈 3 |
| **모니터링** | CloudWatch 대시보드·X-Ray 추적·AgentCore Evaluations·Observability | 모듈 4 |
| **규정 준수** | 규제 요구·데이터 레지던시·AWS Config | 모듈 3·4 |

#### (2) 엔터프라이즈 통합 모범 사례

기존 시스템과 통합할 때의 원칙:
- **관찰성 우선 설계**: 시스템이 단순할 때 모니터링·로깅을 심는다(모듈 4의 "관찰성 우선"과 동일).
- **MCP로 통신 표준화**: 에이전트-도구 통신을 MCP 기반으로 표준화해 상호 운용성·미래 대비를 확보(모듈 1·2).
- **AgentCore Gateway를 중앙 허브로**: 지점 간 통합 대신 중앙 통합 허브로 복잡성을 줄인다.
- **적절한 연결 관리**: RDS Proxy(DB), SQS(비동기), EventBridge(이벤트 라우팅)를 통합 패턴에 맞게 사용한다.

#### (3) 성숙도 기반 채택 로드맵 — 4단계

Agentic AI Lens는 성숙도 기반 학습 경로를 제시합니다.

```ascii
[성숙도 기반 채택 로드맵]  1) --> 2) --> 3) --> 4) 순서로 진행한다

┌─ 1) 첫 에이전트 구축 (기초)
│
├─ 2) 프로덕션 전환 (6기둥 검증)
│
├─ 3) 다중 에이전트 확장 (오케스트레이션 / 통신)
│
└─ 4) 기존 배포 강화 (최적화 / 거버넌스)
```

### 3.3 구현 요건 및 절차 — 배포 전 검증에서 종합 설계까지

**A. 배포 전 검증 (4영역)**
1. **성능**: 부하 테스트로 목표 처리량·지연을 검증하고, 적응형 기준선을 설정한다.
2. **보안**: 정책을 `LOG_ONLY`로 검증 후 `ENFORCE`, IAM 최소 권한 검토, 취약성 스캔·레드팀(AGENTSEC09).
3. **모니터링**: 3계층 관찰성·평가·대시보드·경보가 작동하는지 확인한다.
4. **규정 준수**: 규제 요구·데이터 레지던시·감사 추적 완전성을 검증한다.

**B. 종합 아키텍처 설계 (모듈 1~4 통합)**
1. **다중 에이전트·컨텍스트(M1·M2)**: 통신 패턴·오케스트레이션 선택, 컨텍스트 최적화(기록·선택·압축·분리), 장애 모드 설계.
2. **보안(M3)**: 자격 증명 전파·Cedar 정책·VPC 격리·감사 추적.
3. **관찰성·평가(M4)**: 지표·트레이스·평가 세분성·샘플링·피드백 루프.
4. **프로덕션 검증**: 위 4영역 체크리스트 통과.

### 3.4 구현 예시 — 전자상거래 지원 시스템 캡스톤

**시나리오**: 4개 전문가 에이전트(주문 관리·제품 추천·기술 지원·청구)를 오케스트레이터가 조정하는 다중 에이전트 시스템. 감독되는 대리권(범위 3), 민감 데이터(PII·결제), 99.9% 가용성, PCI-DSS 준수.

```ascii
사용자
  │
  │  1) 요청
  v
┌─ 오케스트레이터 에이전트
│
│  4) 위임
├──> 제품 추천 에이전트
│      5) 도구 호출 --> product_tool
├──> 청구 에이전트
│      5) 도구 호출 --> billing_tool
├──> 기술 지원 에이전트
│      5) 도구 호출 --> support_tool
├──> 주문 관리 에이전트
│      5) 도구 호출 --> order_tool
│
└──> 3) 사용자에게 응답
```

| ② 오케스트레이터 처리 | 분석·라우팅 | 의도 파악, 컨텍스트 최적화(요약 전달), 정책 평가, 결정 로깅 | M1·M2·M4 |
| ③ 오케스트레이터→사용자 | 응답 | 응답 검증, 콘텐츠 필터링, 감사 로깅, SLA | M3·M4 |
| ④ 오케스트레이터→에이전트 | 위임 | 에이전트 간 통신 정책, 네트워크 보안, 폴백 체인, 장애 격리 | M1·M3 |
| ⑤ 에이전트→도구 | 도구 호출 | 도구 액세스 정책(청구 에이전트=billing_tool만), VPC 경계, 데이터 분류 | M3 |

**프로덕션 배포 명세 (행동을 코드처럼 — 설계 원칙 ③)**

M01~M04의 결정을 하나의 버전 관리 명세로 종합합니다. 이 파일 자체가 리뷰·롤백 대상입니다.

```yaml
# 전자상거래 지원 시스템 프로덕션 배포 명세
# 설계 원칙 ③ "행동을 코드처럼": 이 명세는 Git 버전 관리·코드 리뷰·롤백 대상이며,
#                              모듈 1~4의 아키텍처 결정을 한 곳에 종합한다.
system:
  name: ecommerce-support
  autonomy_scope: 3               # 감독되는 대리권 (모듈 3 Scoping Matrix) → 제어 강도 결정
  compliance: [PCI-DSS]           # 규제 요구 → 감사 보존·네트워크 격리 강제
  availability_target: "99.9%"    # 신뢰성 목표 → 다중 AZ·회로 차단기

agents:                           # 설계 원칙 ① 전문화·경계 분해 (모듈 1)
  orchestrator:
    role_file: agents/orchestrator.md   # 정의를 코드에서 분리 (설계 원칙 ③)
    delegates_to: [order, product, tech, billing]
    fallback_chain: [order, product]    # 신뢰성: 폴백 체인 (AGENTREL04)
  billing:
    role_file: agents/billing_agent.md
    tools: [billing_tool]               # 보안: 도구 경계 (마커 ⑤, 최소 권한)

security:                         # 모듈 3
  identity:                       # 다중 계층 자격 증명 (권한 교집합으로 상승 방지)
    user_auth: cognito            # OAuth 2.0/OIDC
    agent_auth: agentcore_identity
    resource_auth: iam
  policy:
    engine: agentcore_policy      # Cedar 정책, 도구 호출을 결정적 시행
    mode: ENFORCE                 # LOG_ONLY로 검증 후 ENFORCE로 승격
    rules_file: policies/         # 예: "청구 에이전트는 billing_tool만", "$500 미만 자동 환불"
  network:
    subnet: private               # 프라이빗 서브넷 + NAT
    connectivity: privatelink     # PCI 데이터가 퍼블릭 인터넷 미경유

observability:                    # 모듈 4
  tracing: adot                   # 3계층(세션·트레이스·스팬) 계측
  evaluation:
    online_sampling_rate: 0.1     # 프로덕션 10% 샘플링
    evaluators: [Builtin.GoalSuccessRate, Builtin.Correctness, scope-adherence]
  alarms:                         # 루프 탐지·비용 보호
    - metric: Duration
      threshold_ms: 1800000       # 세션 30분 초과 시 경보 (루프 의심)
    - metric: ErrorRate
      threshold: 0.05             # 오류율 5% 초과

cost:                             # 모듈 2·4
  prompt_caching: true            # 정적 컨텍스트 재사용
  telemetry_retention: {detailed: 7d, aggregated: 30d, summary: 365d}  # 계층형 보존(PCI 1년)
# 이 명세 하나가 6기둥 결정을 종합한다 → 배포 파이프라인이 이를 읽어 일관되게 프로비저닝.
```

> **💡 팁 — 캡스톤의 종결**: 이 배포 명세가 "왜 이 과정의 모든 모듈이 필요했는가"를 한 화면에 보여줍니다. `autonomy_scope`(M3) 하나가 policy·network·observability의 강도를 결정하고, `agents`(M1)의 경계가 `policy`(M3)의 도구 제한과 맞물립니다. 학습자에게 이 명세의 각 줄이 어느 모듈에서 왔는지 추적하게 하면 완벽한 종합 복습이 됩니다.

### 3.5 모범 사례 (Well-Architected Agentic AI Lens)

- 🏛️ **프로덕션 준비 = 6기둥 통합 검증**: 4개 검증 영역(성능·보안·모니터링·규정 준수)이 6기둥을 실전 체크리스트로 구체화한다. 배포 전 이 4영역을 모두 통과해야 한다.
- 🏛️ **AGENTOPS06-BP01 다층 테스트·섀도 테스트 / AGENTSEC09 침투 테스트·레드팀 / AGENTOPS07-BP04 브레이크글래스 런북**: 배포 준비 체크리스트를 이 BP들로 보강한다 — 섀도 배포로 실트래픽 검증, 레드팀으로 공격 표면 검증, 브레이크글래스로 비상 대응.
- 🏛️ **성숙도 로드맵(4단계)**: 첫 에이전트 → 프로덕션 전환 → 다중 에이전트 확장 → 기존 배포 강화. 조직의 현재 단계를 판정하고 다음 단계로 나아가는 경로를 계획한다.
- 🏛️ **설계 원칙 ③ 행동을 코드처럼(AGENTOPS02·03)**: 배포 명세(YAML)를 버전 관리 아티팩트로 다뤄 리뷰·테스트·단계적 롤아웃·롤백을 적용한다. 이것이 캡스톤 예시의 핵심 실천이다.

## 파트 4. 과정 종합 체크리스트

이 모듈은 캡스톤이므로, 체크리스트도 과정 전체(모듈 1~5)를 종합합니다. 프로덕션 에이전틱 시스템을 설계·검토할 때 점검합니다.

- **자율성 판정 우선**: 시스템을 자율성 스펙트럼·Scoping Matrix에 매핑하고, 필요할 때만 대리권을 상향한다. 판정 결과가 이후 모든 제어의 강도를 정한다. (파트 1, 모듈 3)
- **5가지 설계 원칙 통과**: 아키텍처 결정마다 ①경계 분해 ②엔드투엔드 관찰 ③행동을 코드처럼 ④자율성 비례 감독 ⑤명시적 계약을 점검한다. (파트 1)
- **6기둥 순회 평가**: 운영·보안·신뢰성·성능·비용·지속 가능성 각각에서 에이전트 특화 고려사항을 점검하고 AWS 서비스를 매핑한다. 교차 기둥 트레이드오프를 명시적으로 조정한다. (파트 2)
- **다중 에이전트·컨텍스트(M1·M2)**: 통신 패턴·오케스트레이션·컨텍스트 최적화(기록·선택·압축·분리)·장애 모드를 설계한다.
- **보안(M3)**: 자격 증명 3계층 전파·Cedar 정책·VPC 격리·감사 추적을 구현한다.
- **관찰성·평가(M4)**: 3계층 관찰성·평가 세분성·샘플링·피드백 루프를 구성한다.
- **배포 전 4영역 검증**: 성능(부하·기준선)·보안(정책·IAM·취약성/레드팀)·모니터링(대시보드·평가·경보)·규정 준수(규제·레지던시·감사)를 통과한다. (파트 3)
- **행동을 코드처럼 종합**: 에이전트 정의·정책·관찰성·평가 구성을 버전 관리 배포 명세로 종합해 리뷰·롤백을 적용한다. (파트 3)
- **성숙도 로드맵 인식**: 조직의 현재 단계(첫 에이전트→프로덕션→다중 에이전트→강화)를 판정하고 다음 단계를 계획한다. (파트 3)
